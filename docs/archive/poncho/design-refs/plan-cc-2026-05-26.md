## Cómo lee CC este plan

Cada **sub-PR** tiene cinco bloques fijos:

1. **Goal** — qué tiene que pasar al final.
2. **Inputs** — qué archivos del repo o de `Downloads/Pantallas/` consume.
3. **Trabajo** — chunks atómicos en orden. Cada chunk = 1 commit. Cada chunk debe quedar verde en `pnpm test && pnpm build && pnpm biome check .` antes del siguiente.
4. **Verificación** — comando exacto que corre para validar antes de abrir el PR.
5. **Criterio de salida** — el resultado del comando que cierra el sub-PR.

**Sub-branches:** Fases 3 y 4 tienen sub-branches: `feat/poncho-3a-home-list`, `feat/poncho-3b-tabs-banners`, etc. Cada una sale de la anterior una vez mergeada (chained PRs).

Si un chunk falla, CC lo revierte con `git reset --hard HEAD`, registra el archivo en `docs/poncho/migration-blockers.md`, y continúa con el siguiente. Ningún chunk bloquea el sub-PR entero salvo que rompa build/typecheck.

# Cross-cutting policies (aplican a TODAS las fases)

1. **No tocar DB schema sin migración Drizzle.** Cualquier columna nueva (`tier2_public_enabled_until`, `pet_transfer_proposals`, etc.) abre PR independiente con migración + tests antes de la fase de UI.
2. **Reusar antes de crear.** Si un form ya existe (`VaccinationForm.tsx`), el sheet lo envuelve. No reescribir lógica.
3. **Tests obligatorios** por componente nuevo. Mínimo: 1 test de render por status + 1 test de interacción primaria.
4. **Append-only en commits.** Cada chunk = un commit firmado con mensaje convencional (`feat:`, `refactor:`, `chore:`).
5. **Sin nuevas dependencias** salvo Vaul (sheet lib) y `lucide-react` si todavía no está. Cualquier otra requiere ADR en `docs/superpowers/specs/`.
6. **Server components por default**, `"use client"` solo donde hay estado/efectos.
7. **A11y check** en cada fase: focus-visible + 44×44 touch target + WCAG AA contrast.
