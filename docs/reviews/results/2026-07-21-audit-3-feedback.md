# Level 3 Audit — Feedback & Uncertainty (2026-07-21)

Read-only audit. Scope: citizen surfaces (`app/(app)`, `app/(public)`, `app/(auth)`, `components/`), operator/gov/admin surfaces (`app/gob`, `app/admin`, `app/org`), and shared infra (`lib/infra`, `lib/ui`).

---

## 1. Button feedback states

**Coverage estimate: ~85% consistent at the primitive level, but raw `<button>`/`<a>` bypass is still large (377 tracked occurrences) and one operator/citizen parity gap exists.**

- `components/ui/Button.tsx` (`LnButton`, citizen tier) — single source of truth for hover/active/focus-visible/disabled/loading:
  - hover via variant maps (e.g. `Button.tsx:71` `hover:bg-[var(--color-ln-azul-700)]`)
  - pressed/active feedback: `Button.tsx:56-58` — `active:scale-[0.98] active:opacity-90`, explicitly added per "native-mobile audit §3" so touch users get feedback beyond hover-only styles
  - focus-visible: `Button.tsx:60` — `focus-visible:ring-[3px] focus-visible:ring-[var(--color-ln-celeste-050)]`
  - loading: `Button.tsx:44,121-136` — `loading` prop disables the button, sets `aria-busy`, and swaps in a spinner (`Button.tsx:80-87`)
- `components/ui/dashboard/OpButton.tsx` (operator tier) mirrors hover/focus-visible/disabled/loading (`OpButton.tsx:40-44,74-98`) — **but does NOT replicate the `active:scale`/`active:opacity` pressed-state rule that LnButton has**. This is a real citizen-vs-operator parity gap: operator console has no equivalent touch/pressed affordance, only hover + focus-visible.
- Both components are anchor-aware or button-only respectively: `LnButton` can render as a `<Link>` when `href` is passed (`Button.tsx:103-114`) to stay legal under WCAG 4.1.2; `OpButton` has no anchor mode.
- **Raw `<button>` bypass is tracked and ratcheted, not hidden**: `scripts/check-raw-buttons.mjs` enforces two separate baselines — operator (`app/gob`, `app/admin`, `app/org`): 52 raw `<button>`s (`check-raw-buttons.mjs:61`); citizen (`components/**`, `app/(app)`, `app/(public)`, `app/(auth)`): 325 (`check-raw-buttons.mjs:76`). The comments document deliberate exceptions (segmented toggles, pure text-links, `ConfirmDialog` focus-restore triggers that need a forwarded `ref` OpButton can't carry — e.g. `ReasignarButton.tsx:29`, `DevolverAlDuenoButton.tsx:22`, `RemoveMemberButton.tsx:21`). This means ~377 raw buttons still exist app-wide, most **without** LnButton/OpButton's focus-ring/active-state guarantees — they inherit only whatever ad hoc classes each call site wrote.
- Raw `<a href=` as CTA: comparatively rare and mostly used for genuine navigation/deep-links (e.g. `EventLedgerRow.tsx:123` "Ver situación a esta fecha", `EventTimelineList` attachment links) rather than styled CTA bypass — this is a smaller problem than raw `<button>`.

**Citizen vs operator**: both tiers have a working consolidation system (LnButton/OpButton) with an enforced ratchet script, which is more mature than typical codebases. The main gaps are (a) the missing pressed-state on OpButton, and (b) ~377 raw-button call sites still outside the system, concentrated in citizen surfaces (325 vs 52).

## 2. Post-mutation success feedback

**Coverage estimate: toast-based feedback is used in only 2 call sites app-wide (near 0%). The dominant pattern is a full-page reload (`navigateAfterActionSuccess`) that shows a changed page as the "confirmation," with no explicit toast/banner text on ~90%+ of mutating actions.**

- `components/Toaster.tsx:17-31` mounts sonner once in the root layout, but actual `toast.success/error/info` **call sites** are only:
  - `components/gob/NoticeToast.tsx:38-40` — fires from a `?notice=` query param (currently only wired for one message: "No tenés acceso a esta jurisdicción", error tone)
  - `components/panorama/PanoramaConsole.tsx:4996` — `toast.success("Descarga iniciada: panorama-mapa.csv")` on a CSV export click
  - No other `.tsx` file in the repo calls `toast.*` directly (verified via `from ["']sonner["']` import grep — only 3 files import it, and one of those, `Toaster.tsx`, only configures it).
- The app-wide convention is instead `navigateAfterActionSuccess` (`lib/ui/full-page-action-nav.ts:28-31`) — a deliberate architectural decision, not an oversight: Next.js 15.5.x's App Router has a documented production defect where a Server Action's own `redirect()` resolves but the client router silently drops the transition (see the module docblock, `full-page-action-nav.ts:1-27`, and `lib/ui/use-action-redirect.ts:1-19`). The fix is `window.location.assign()` — a full document reload — which is treated as "the confirmation IS the visible state change."
  - `app/admin/outbox/[id]/RetryOutboxButton.tsx:5-22` documents this tradeoff explicitly in a code comment: an earlier optimistic in-place update was **rejected** because it caused the exact "did it work?" confusion this pattern exists to prevent (stale SSR fields contradicting an optimistic success label).
- Net effect: most mutating actions (`AcceptTransferActions.tsx:51`, `GovtModerationActions.tsx:53`, `ModerationActions.tsx:46`, `DevolverAlDuenoButton.tsx:42`, `ReasignarButton.tsx:77`, `RemoveMemberButton.tsx:34`, `RevokeOrgActions.tsx:193`, `DeleteRuleButton.tsx:41`) give **no explicit success text** — they just reload/redirect and rely on the user noticing the list/row/badge changed.
- A minority DO show an explicit inline success message instead of (or in addition to) reload:
  - `app/org/[orgToken]/transferencias/recibidas/IncomingTransferActions.tsx:62-67` — `setDone(true)` renders "Transferencia aceptada."/"Transferencia rechazada." inline, **no page reload at all** (relies on `revalidatePath`)
  - `app/gob/organizaciones/RevokeOrgActions.tsx:70-76` — "Verificacion revocada. El titular de {org} fue notificado." then also reloads (`:193`)
  - `app/gob/usuarios/RevokeUserActions.tsx:64-69` — "Rol vet revocado. {target} fue notificado." — **no reload at all**, inconsistent with its sibling `RevokeOrgActions` which mirrors the same "ADR-3" pattern per its own comment but reloads
  - `components/BulkApprovalQueueList.tsx:374-401` — a genuine `ResultPanel` showing "{N} OK · {M} fallaron" plus per-item failure reasons for bulk approve/reject
- **Rough estimate**: sampling ~15 representative mutating action components across citizen, org, and gov/admin surfaces, roughly **2-3 of 15 (under 20%)** show an explicit textual success confirmation distinct from "the page changed." Toast usage specifically is ~0%. I could not exhaustively enumerate all ~70+ files under `app/actions/*` and `app/**/actions.ts` (76 files matched a `"use server"` grep) against their calling components in the time available — this is a sampled estimate, not a full census — but the pattern held consistently across every sample, including files from unrelated feature areas (transfers, moderation, decomisos, org membership, business rules), which is strong evidence it generalizes.

## 3. Irreversible-action confirmation

**Coverage estimate: ~80-90% of destructive actions I found are gated by either `ConfirmDialog` or an equivalent inline two-step pattern (mode-switch + explicit confirm button, sometimes with a mandatory reason/checkbox). Raw one-click destructive actions are rare in the samples read, but the app does NOT use one single mechanism — the `ConfirmDialog` modal, inline mode-switch panels, and required-reason-only gates all coexist.**

- `components/ui/ConfirmDialog.tsx` — accessible native `<dialog>` modal: automatic focus trap, Escape-to-cancel (`:92-101`), focus-restore to the trigger on close (`:116-124`, with a documented bug fix for a focus-stealing race across many rows — see the comment at `:105-115`), `pending` prop disables both buttons and shows "Procesando…" (`:192`), `tone` prop colors the confirm button (danger/warn/neutral, `:33-38`).
- Direct `ConfirmDialog` call sites found: `AcceptTransferActions.tsx`, `MpfExportGate.tsx`, `DevolverAlDuenoButton.tsx`, `ReasignarButton.tsx`, `DeactivateAccountDialog.tsx`, `AmendEventForm.tsx`, `SharesManager.tsx`, `LeaveOrgButton.tsx`, `InterventionActions.tsx`, `RevokeButton.tsx`, `RemoveMemberButton.tsx`, `DeleteRuleButton.tsx` (agenda), plus `OpBulkBar.tsx` (generic bulk-action confirm) and `BulkRevokeList.tsx`.
- A large second population of destructive actions use an **inline mode-switch pattern instead of ConfirmDialog**: click trigger → component swaps to a confirmation sub-view with a required textarea/checkbox → explicit "Confirmar X" button. Examples: `GovtModerationActions.tsx` (reject-as-abuse requires ≥10-char notes + an explicit "Entiendo que esta acción es irreversible…" checkbox, `:97-113`), `ModerationActions.tsx` (same pattern via `canSubmitModeration`, `:69`), `RevokeOrgActions.tsx`/`RevokeUserActions.tsx` (motivo + ≥1 evidence file + checkbox, `:113-267`), `DeleteRuleButton.tsx` (reglas — required reason textarea, no checkbox, `:44-99`), `IncomingTransferActions.tsx` (mode-switch, no checkbox, no ConfirmDialog).
- I did **not** find a genuinely one-click, no-confirmation destructive action in any file read directly (`LeaveOrgButton`, `RemoveMemberButton`, `RevokeUserActions`, `RevokeOrgActions`, `DevolverAlDuenoButton`, `ReasignarButton`, `DeleteRuleButton`, moderation actions — all gated one way or another). I cannot claim 100% coverage since dozens of destructive-sounding files (`WithdrawDisputeButton.tsx`, `CancelProposalButton.tsx`, `EndFosterButton.tsx`, `DeactivateGovtForm.tsx`, `RevokeLocalityRowActions.tsx`, `DeactivateAdminForm.tsx` and others) were located but not opened — flagging this as the biggest verification gap in this section.

### Confirmation asymmetries (safety-relevant)

1. **RESOLVED, but worth flagging as a past-incident pattern**: `AcceptTransferActions.tsx:31-36` contains an explicit code comment: *"Accepting a transfer is IRREVERSIBLE… it must be gated behind the same confirmation weight as rejecting. Previously accept fired on a single click while reject asked for a reason + a second confirm click — backwards (audit finding, safety pass 2026-07-19)."* This is the exact class of asymmetry this audit is designed to catch, already caught and fixed once — meaning the codebase is not immune to reintroducing it elsewhere. **Severity: was HIGH, now fixed; residual risk is regression, not current exposure.**
2. **Live stylistic asymmetry, low-severity**: in the current `AcceptTransferActions.tsx`, "Aceptar" now opens a full `ConfirmDialog` modal (`:133-143`, tone `warn`, explicit "no se puede deshacer" copy), while "Rechazar" opens an inline reason panel with its own "Confirmar rechazo" button (`:63-111`) — **not** a `ConfirmDialog`. Both require two clicks and show equivalent friction, so this is not a safety gap, but it means the same file uses two different confirmation *widgets* for two actions of matching severity. **Severity: LOW (cosmetic/consistency, not safety).**
3. **Cross-org transfer accept/reject (`IncomingTransferActions.tsx`) is internally symmetric but uses neither `ConfirmDialog` nor a checkbox-acknowledgment** — both accept and reject use the same bespoke mode-switch + button pattern. Symmetric, so not a safety asymmetry, but it means custody-changing actions in this file get **less** confirmation weight than the citizen-facing equivalent in `AcceptTransferActions.tsx` (no modal, no explicit "no se puede deshacer" copy on accept). **Severity: MEDIUM** — an org-to-org custody transfer is at least as consequential as an owner-to-owner one, but gets a lighter-weight confirmation UI.
4. **Mutation-feedback inconsistency between sibling files**: `RevokeOrgActions.tsx` calls `navigateAfterActionSuccess(window.location.href)` after success (`:193`) so the SSR "Verificada" pill updates; `RevokeUserActions.tsx`'s `RevokeVetForm.submit()` (`:171-185`) does **not** — it only calls `onDone()`, leaving the page un-refreshed. Both files' own comments claim to "mirror" the same ADR-3 structure. This isn't a confirmation-dialog asymmetry, but it is a **verifiable divergence in what the user sees after confirming an equally irreversible action** (org verification vs vet role revocation), worth flagging alongside the confirmation findings since it affects the same trust moment. **Severity: LOW-MEDIUM**.

## 4. "Who/when" surfacing

**Coverage estimate: strong on operator-facing audit/timeline surfaces (~90%+ of the ones sampled show literal actor + timestamp), much weaker on citizen-facing surfaces (~30-40%) where the pet-events timeline shows a provenance *badge* (confidence tier) instead of a literal actor name.**

- Operator side — literal "who + when" is a designed convention:
  - `app/admin/libro/EventLedgerRow.tsx:56,90-119` — every row shows `actorLabel` (role-based, e.g. "Veterinario"), a "Verificado" check icon when applicable, an "vía organización" marker, **both** `occurredAtLabel` ("ocurrió …") and `recordedAtLabel` ("se registró …") — explicitly to "reinforce the model" that occurred-at and recorded-at can differ.
  - `app/gob/maltrato/[id]/Timeline.tsx:46-54` — every timeline entry shows `formatDateTime(event.occurredAt)` plus `· {event.actorName}` when present.
  - Amendment chains also carry actor + timestamp per entry (`EventLedgerRow.tsx:152-166`).
- Citizen side — `components/.../EventTimeline.tsx` (pet profile / libreta) shows a **provenance badge** (`ownerConfidenceDisplay(libretaConfidenceTier(...))`, `:98-108`) which encodes "who attested this" as a confidence tier/label (e.g. verified-org vs self-reported) but does **not** print a literal actor name or "por Juan Pérez" the way the operator ledger does — only `formatDateTime(event.occurredAt)` is shown as plain text (`:148-150,162-164`). An owner sees *that* something was confirmed by a verified party and *when* it happened, but not literally *by whom* (individual name), unlike the operator view of the same underlying event data.
  - This is a defensible product choice (citizen view may deliberately abstract away internal actor identities), but it is a real coverage gap relative to the operator tier, and it means the "pet_events already stores actor+timestamp" data model advantage is **not symmetrically surfaced** across citizen vs operator UI.
- No explicit "última actualización por X, el <fecha>" banner pattern was found on pet profile headers, moderation case headers, or transfer record headers — the who/when is per-event-row (ledger/timeline), not a persistent "last modified by" summary line at the top of a record. I did not check every moderation/transfer page (`ResolveDisputeForm.tsx`, `InvestigationActions.tsx` etc. were located but not opened) so this could be present elsewhere; flagging as unverified rather than asserting absence everywhere.

## 5. Progress / pending / uncertainty during async actions

**Coverage estimate: single-action pending state (disabled button + "…ando" label) is close to universal (~90%+) in every component sampled. Multi-step wizards mostly DO show "Paso X de Y" + a progress bar. Bulk operations have a genuinely good partial-failure pattern in at least one place. No component showed a bare inert UI with zero feedback during an async call.**

- **Single-action pending**: every mutating component read uses `useTransition`'s `isPending`/`pending` to (a) disable the trigger button and (b) swap its label to a present-progressive Spanish verb — "Procesando…", "Enviando…", "Cancelando…", "Eliminando…", "Revocando…", "Programando…" (e.g. `AcceptTransferActions.tsx:108`, `GovtModerationActions.tsx:134`, `ModerationActions.tsx:111`, `DeleteRuleButton.tsx:83`, `RetryOutboxButton.tsx:53`). `ConfirmDialog` itself also shows "Procesando…" on its confirm button when `pending` (`ConfirmDialog.tsx:192`) and disables both buttons (`:166,182`). `useTransition`/`isPending`/`startTransition` appear across a very large number of files (grep count too large to enumerate exactly, but consistent in every sampled action component).
- **Multi-step wizards**: several citizen wizards show literal "Paso X de Y" plus a visual step-progress bar, e.g. `app/(app)/mis-mascotas/[publicToken]/perdida/MarkLostWizard.tsx:126-227` (`totalSteps`, `stepLabels`, a bar of filled/unfilled segments per step, `:211-226`), `app/(auth)/signup/SignupForm.tsx:75,179` ("Paso 1/2 de 2"), `app/(app)/mis-mascotas/[publicToken]/eventos/atestar-raza-peligrosa/DangerousBreedAttestationForm.tsx:98,189`. Other wizards (`ClaimWizard.tsx`, `DenunciaWizard.tsx`, `FosterVolunteerWizard.tsx`, `IntakeForm.tsx`) matched a step-related grep but weren't opened to confirm the exact same "Paso X de Y" text is present — likely yes given the shared `use-step-focus.ts` hook referenced by `MarkLostWizard.tsx:26`, but unverified for each file individually.
- **Bulk operations**: `components/BulkApprovalQueueList.tsx` is the standout — its `ResultPanel` (`:374-401`) shows "{N} OK · {M} fallaron" with per-item failure reasons and a `bulkActionId` for traceability, explicitly designed (per its own file comment, `:1-23`) because generic `OpBulkBar` couldn't express partial failure. `OpBulkBar.tsx` itself (the generic primitive used elsewhere) shows only an aggregate pending spinner-less state (button disabled, no per-item breakdown) — so partial-failure legibility exists in at least one place but is **not** the generic bulk primitive's default behavior; other bulk consumers of `OpBulkBar` (not individually audited) likely get only pass/fail as a whole, not per-item results.
- **Route-level loading states**: `app/gob/**/loading.tsx` exists for `loading.tsx`, `vigilancia/loading.tsx`, `usuarios/loading.tsx`, `perdidas/loading.tsx`, `maltrato/loading.tsx`, `cola/loading.tsx`, `analytics/loading.tsx` — Next.js Suspense skeletons for slower gov routes. I did not check whether `app/admin` and `app/org` have equivalent per-route `loading.tsx` coverage — flagging as unverified breadth (only `app/gob` was enumerated).
- No evidence of optimistic UI (`useOptimistic`) was found in any file read; the codebase's explicit stance (per `RetryOutboxButton.tsx`'s comment) is that optimistic UI was tried and **rejected** in favor of full-reload-as-confirmation, for the reason described in §2. This is a coherent, intentional design choice, not an oversight — but it does mean uncertainty during the async gap itself is only "button disabled + spinner label," never a richer in-progress preview of the outcome.

## Cross-cutting gaps & recommended shared patterns

1. **No shared "mutation feedback" convention exists.** Three different patterns coexist for "what does the user see after a successful mutation": (a) full-page reload with no text (majority), (b) inline `setDone(true)` text banner with no reload (`IncomingTransferActions`, `RevokeUserActions`), (c) toast (2 call sites total). None of these is wrong per se — (a) is a deliberate, well-reasoned fix for a real Next.js router bug — but the *choice* between them appears to be made ad hoc per component rather than by a documented rule. Recommend a short ADR/convention doc stating: "silent full-reload is the default for full-page CRUD; components that intentionally stay mounted after success (no reload) MUST render an explicit inline confirmation string," and auditing `RevokeUserActions.tsx` against `RevokeOrgActions.tsx` as the first concrete fix (§3 asymmetry #4).
2. **`ConfirmDialog` rollout is not yet a hard fence.** It coexists indefinitely with the inline mode-switch pattern for equally destructive actions (moderation reject/spam, revoke-org/revoke-user, delete-rule). This is arguably fine as design pluralism (checkbox-acknowledgment is arguably *stronger* than a plain ConfirmDialog for the highest-stakes actions), but there's no written rule for when to use which. Recommend documenting: "ConfirmDialog for single-field-or-simpler irreversible actions; mode-switch + mandatory reason/checkbox for actions requiring an audit-log justification" — and then auditing the ~15+ destructive-action files not yet opened in this pass (`WithdrawDisputeButton.tsx`, `EscalateDisputeForm.tsx`, `EndFosterButton.tsx`, `DeactivateGovtForm.tsx`, `DeactivateAdminForm.tsx`, `RevokeLocalityRowActions.tsx`, `CancelProposalButton.tsx`, and others located but unread) against that rule.
3. **OpButton is missing LnButton's pressed-state rule.** A one-line fix (`active:scale-[0.98] active:opacity-90` added to `OpButton.tsx`'s `base` string, mirroring `Button.tsx:56-58`) would close the citizen/operator touch-feedback parity gap in §1.
4. **Toast infrastructure is mounted but essentially unused.** Either commit to toast as the standard success-feedback layer (and start using it broadly, especially for actions like `IncomingTransferActions`'s inline "done" text, which is a natural toast candidate) or remove the unused-but-configured `Toaster` mount as dead weight — right now it's configured for a convention the app doesn't follow.
5. **Citizen-facing "who" is weaker than operator-facing "who" for the same underlying event data.** Since `pet_events` already carries actor identity, consider whether citizen pet-profile timelines should show the literal org/vet name (not just a confidence badge) for events the owner didn't personally log — this directly serves the "verifiable credential" trust story the product is built on.

- This audit sampled ~35-40 files directly (full reads) out of a much larger surface (600 toast-adjacent-pattern grep hits across 179 files; 76 files matching a `"use server"` grep; 147 files matching an `LnButton|OpButton` grep). Sub-dimension 2's percentage and sub-dimension 3's "no one-click destructive action found" claim are **sampled estimates**, not exhaustive counts — flagged inline above wherever this applies.
