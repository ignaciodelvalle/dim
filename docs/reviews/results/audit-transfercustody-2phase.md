I audited the four in-scope files against all six lenses and wrote the results to `docs/reviews/results/audit-transfercustody-2phase.md`. Summary of the real findings (terse form is in the file):

**HIGH**
1. **Race/idempotency gap** — `reject`/`cancel`/the 30-day auto-expire cron never take the `pg_advisory_xact_lock` that `acceptCrossOrgTransfer` uses, and accept discards `closeCase()`'s return value. A reject/cancel/expire that commits in the window between accept's early status check and its own `closeCase` call still lets accept finish the ownership flip — the case ends up `closed/cancelled` while custody was *also* transferred, contradicting the immutable event log. The sibling `return-to-owner` module gets this right (every writer takes the same lock); this new flow only applied it to accept.
2. **`to_role` escalation** — nothing stops a `shelter_custody`-only source from proposing `to_role=owner` to any verified org, including another shelter/rescue_network — violating "refugios are never owner in DIM" with no DB backstop either.
3. **Silent permanent-ownership consent** — the receiver's incoming-proposal inbox never shows `to_role`/`from_role`; "Confirmar aceptación" is generic regardless of whether the receiver is agreeing to temporary custody or becoming the pet's permanent legal owner.

**MED** — foster-cascade in accept reads the active foster row pre-tx and never re-verifies it under the lock (unlike case status), and the sibling `end-foster.ts` writer has no lock/guard either — together they can double-close/double-emit `foster_ended`.

**LOW** — `transferCustodyAction` skips the `validateOrgTokenMatch` guard every sibling cross-org action has; direct handoff doesn't check destination `status==="active"` (propose does); dead `closeOwnershipById` helper left behind.

Confirmed clean: the consent bypass itself is closed (no remaining unilateral flip), double-accept is correctly guarded, the event schemas are consistent, and no legitimate same-org path was broken by the reroute.

2. `src/modules/transfers/application/transfer-custody.ts:108-121` + `src/modules/transfers/domain/direct-transfer-rules.ts:24-34` + `src/modules/transfers/infrastructure/transfers-repository.ts:423-439` (`findReceiverOrg` never selects `orgType`) — **HIGH** — nothing stops a source org holding only `shelter_custody` (a temporary custodian) from proposing `to_role=owner` to ANY verified destination, including another `shelter`/`rescue_network` org. This both (a) lets a non-owner source grant permanent ownership it never legally held, and (b) lets a shelter/rescue_network destination become `role=owner`, directly violating the documented invariant "Refugios are never owner in DIM — they hold shelter_custody until adoption finalizes" (AGENTS.md §Organizations). No DB constraint backstops this either (no CHECK on `ownerships.role='owner'` vs `organizations.org_type`). Fix: require `fromRole === "owner"` for `to_role=owner` proposals, AND/OR reject `to_role=owner` when `destination.orgType` is in `{shelter, rescue_network}`.

3. `app/org/[orgToken]/transferencias/recibidas/page.tsx:77-93` + `app/org/[orgToken]/transferencias/recibidas/IncomingTransferActions.tsx:70-98` — **HIGH** — the receiver's incoming-proposal inbox never selects or renders `to_role`/`from_role` from the proposal payload, and the "Confirmar aceptación" dialog text is generic ("La custodia pasa a tu organización. Esta acción no se puede deshacer.") regardless of whether the proposal requests temporary `shelter_custody` or permanent `owner`. Combined with finding #2, a receiver can click "Confirmar aceptación" and become the pet's permanent legal owner with zero disclosure that this is what they agreed to (contrast with `TransferCustodyForm.tsx:84-94`, which DOES label this distinction for the proposer). Fix: select `to_role`/`from_role` in the `handshakeRows` query and render an explicit "Vas a convertirte en dueño/a permanente" warning before allowing accept when `to_role==="owner"`.

4. `src/modules/transfers/application/accept-cross-org-transfer.ts:147-151` vs `172-178` — **MED** — `findActiveFosterRow` (and the upfront `fosterEndedEventId`) is read BEFORE the transaction and is never re-verified once the advisory lock is acquired, unlike the case status which IS re-checked under the lock at 172-178. A concurrent "Finalizar tránsito" (`end-foster.ts`) on the same pet can end/replace the same foster row in that window; accept will still close it via the stale id and emit a second, redundant `foster_ended` event. Fix: re-read `findActiveFosterRow` for the same ownership id inside the tx, right after the lock/status check, before calling `closeFosterOwnership`.

5. `src/modules/foster/application/end-foster.ts:63-77` + `src/modules/foster/infrastructure/foster-repository.ts:806-809` (`insertEndFoster`) — **MED** — no `pg_advisory_xact_lock` and no `endedAt IS NULL` guard on the UPDATE; contributes directly to finding #4's exploitability since neither writer that can close a foster row on this pet serializes against the other.

6. `src/modules/transfers/actions.ts:636-657` + `src/modules/organizations/infrastructure/authz-resolver.ts:164-166` — **LOW** — `transferCustodyAction` never validates the resolved active org against the `orgToken` route param (`TransferCustodyInput` has no `sourceOrgToken` field, no `validateOrgTokenMatch` call), unlike every sibling cross-org action (`propose`/`accept`/`reject`/`cancel` all call it). `requireCapability("custody.transfer")` with no org id picks `memberships[memberships.length-1]`, so a coordinator with `custody.transfer` in two orgs can silently act as the wrong one (fails closed via `findPetUnderOrg`, but produces a confusing "Mascota no encontrada" instead of a clear wrong-org error). Fix: add `sourceOrgToken` to the input and call `validateOrgTokenMatch` like the sibling use-cases.

7. `src/modules/transfers/application/transfer-custody.ts:116-121` — **LOW** — destination lookup checks `destination.verified` but not `destination.status === "active"` (contrast `propose-cross-org-transfer.ts:103-105`, which checks both). A suspended/dissolved org can still be proposed as a direct-handoff destination and its (former) coordinators notified. Fix: add the same `status !== "active"` guard.

8. `src/modules/transfers/infrastructure/transfers-repository.ts:692-694` (`closeOwnershipById`) — **LOW** — dead code: no production writer calls it since `transferCustody` stopped doing the flip itself (only referenced from `transfers-repository.test.ts`). Harmless today but it's an unguarded close-by-id (no `endedAt IS NULL` check) sitting unused — delete it so a future writer doesn't reach for it outside the accept flow.

Clean:
- Consent bypass (lens 1): `transferCustody` itself no longer touches `ownerships` — it only opens the handshake case + emits `custody_transfer_proposed`; the flip lives exclusively in `acceptCrossOrgTransfer`. No remaining unilateral path found.
- Double-accept (lens 3): correctly guarded — both accepts take the same advisory lock, the loser's in-tx `caseStatusById` re-check sees `closed` and throws.
- `custody_transferred`/`custody_transfer_proposed` schemas (`lib/events/event-schemas.ts:1167-1205,1476-1499`): `from_role`/`to_role` enums, XOR refinements on from/to actor — consistent, no gap.
- Authz for propose/accept/reject/cancel (lens 4, aside from #6): `validateSenderOrgScope`/`validateReceiverOrgScope` canonical-column-with-drift-detection pattern is sound and applied uniformly across accept/reject.
- Same-org / internal moves (lens 6): `validateDestinationNotSource` still blocks same-org direct handoff; no legitimate pre-existing caller of the old unilateral `transferCustody` found broken by the reroute (single caller, `TransferCustodyForm.tsx`, already aligned to the new flow).
