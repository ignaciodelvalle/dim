Report written to `docs/reviews/results/26-ownership-trust-chain.md`. Summary of the 9 findings:

**HIGH (5)**
1. `expire-pet-transfers.ts:56` — expiry cron does a blind `updateTransferStatus` with no `expectedStatus`, unlike accept/reject/cancel; can overwrite an already-resolved transfer back to `"expired"`.
2. `accept-cross-org-transfer.ts` — case status checked once outside the tx, never re-locked/re-checked inside it → concurrent accept/reject/expire can double-apply (duplicate custody + duplicate event).
3. `cases-repository.ts::closeCase` — check-then-act (`SELECT` then unconditional `UPDATE`), no `WHERE status='open'` guard, propagates the TOCTOU race into every module that closes a case.
4. `owner-accept-return.ts` — the one writer in the return-to-owner handshake that skips the advisory lock every sibling takes; a cancelled proposal can still get executed if it races an owner's accept.
5. `transfer-custody.ts` — direct org→org handoff is fully unilateral (no receiver consent at all), inconsistent with the two-phase propose/accept flow that exists for the same kind of move.

**MED (2)**
6. `submit-free-claim.ts` — "free" claim finalizes instantly on knowledge of a chip/tattoo code alone, no waiting period or notice, reachable even when a dormant (deactivated, not ended) prior owner exists.
7. `org-reject-owner-return.ts` — missing the same lock its sibling `owner-reject-return.ts` explicitly added to avoid racing an accept.

**LOW (2)**
8. Dispute "escalated" state lives only on `cases.status`, never on `custody_disputes.status` — the two records can disagree.
9. Only SLA is a 365-day stale-notification; no shorter initial-triage deadline.

Confirmed the audit's overall theme: the transfer modules that were built with the lock+re-check discipline (`accept-pet-transfer`, `propose-cross-org-transfer`, chip-match confirms, `org-accept-owner-return`, `owner-reject-return`, foster expiry) are solid — the vulnerabilities cluster in the paths that drifted from that established pattern.
an `UPDATE ... WHERE id=?` with no `status='open'` predicate on the UPDATE itself · **HIGH** · Every caller that relies on `closeCase` for atomic idempotent closing (cross-org accept, direct `transferCustody`, dispute resolution, return-to-owner) inherits a TOCTOU window where two concurrent closers both read "open" and both update, producing duplicate downstream effects. Make the guard part of the UPDATE: `.where(and(eq(cases.id, id), notInArray(cases.status, ["closed","merged"])))` and branch on `rowCount`.

4. `src/modules/return-to-owner/application/owner-accept-return.ts:204-297` · This is the one writer in the return-to-owner handshake that does **not** take `pg_advisory_xact_lock(hashtext(pet.id))` — `propose-return-as-refugio`, `owner-propose-return-to-org`, `actor-cancel-proposal`, `owner-reject-return` (which explicitly comments "without it a reject can race an accept") and `org-accept-owner-return` all take it · **HIGH** · An owner's accept can interleave with a concurrent actor cancel/reject: the actor's locked transaction cancels the proposal and commits, then the owner's un-locked transaction (which read the proposal as "pending" before that commit) proceeds anyway and completes the transfer — a cancelled proposal gets executed after the fact. Add the same advisory lock + in-tx `hasPendingProposal` re-check used by every sibling before executing the transfer.

5. `src/modules/transfers/application/transfer-custody.ts:71-247` (`transferCustody`) · Direct org→org custody handoff is fully unilateral: the source org (holding the `custody.transfer` capability, grantable to any member, not admin-only) atomically closes its ownership and opens a new one on the destination org — the only destination check is `verified=true`, no acceptance step at all · **HIGH** · This coexists with a two-phase propose/accept flow (`propose-cross-org-transfer.ts` → `accept-cross-org-transfer.ts`) built specifically to require receiver consent for the same kind of move, so the trust model is inconsistent: one path can dump a pet (and its full medical/legal history) on a verified org that never agreed to receive it. Route `transferCustody` through the same handshake/case pattern, or at minimum require an explicit receiver-side confirmation before the ownership flip.

6. `src/modules/pets/application/claim/submit-free-claim.ts:20-129` (+ `lookup-for-claim.ts:40-123`) · Claiming a pet with no active custody ("free") finalizes instantly on nothing more than knowing its 15-digit microchip number or tattoo code — no photo, no waiting/objection period, no notice to anyone (there may be no one left to notice: a deactivated owner's ownership rows are never ended per `self-deactivate-personal-account.ts`, so this path is reachable even when a real prior owner still "exists" but is dormant) · **MED** · Add a short objection window (e.g., queue the claim and notify the last-known owner/org if one is discoverable, even a deactivated one) or require a corroborating artifact before granting outright ownership instead of only a code match.

7. `src/modules/return-to-owner/application/org-reject-owner-return.ts` (whole file) · No advisory lock or in-tx re-check, unlike its sibling `owner-reject-return.ts` which explicitly locks for this reason · **MED** · An org's reject can land after an owner's accept already executed the transfer (item 4), appending a spurious `custody_transfer_cancelled` event onto a pet whose custody already moved. Add the same `pg_advisory_xact_lock(hashtext(pet.id))` + `hasPendingProposal` re-check.

8. `src/modules/custody-disputes/application/escalate-dispute.ts:1-8` vs `src/modules/cases/application/escalate-stale-disputes.ts:89-95` · "Escalated" is a real, guarded state transition on `cases.status`, but `custody_disputes.status` has no equivalent value (comment: "the only valid statuses are open / resolved / withdrawn") — a manually-escalated dispute stays `status='open'` on the dispute record itself, with the escalation visible only as a `note_added` pet event + audit log row · **LOW** · Add `"escalated"` to the `custody_disputes` status enum (or have `resolveDisputeUseCase`/detail pages read the linked `cases.status` instead of the dispute row) so the two records can't silently disagree on lifecycle state.

9. `src/modules/cases/application/escalate-stale-disputes.ts:9-10,41` · The only enforced dispute SLA is a 365-day "stale" notification to authorities — there is no shorter initial-triage deadline and no consequence beyond a warning notification (the dispute stays open indefinitely, `pets.inCustodyDispute` never auto-resolves) · **LOW** · Define a second, shorter SLA for first arbiter response (e.g., 30/60 days) distinct from the year-long stale flag, so an unattended dispute surfaces well before it's a year old.
