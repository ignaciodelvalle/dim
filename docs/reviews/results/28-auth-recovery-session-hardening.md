Wrote the audit to `docs/reviews/results/28-auth-recovery-session-hardening.md` — 13 findings (2 HIGH, 6 MED, 3 LOW, 2 clean confirmations). Key take:

**Real gaps found:**
- **Login is unthrottled** (`login.ts:31`) — no per-account lockout, no app-level rate limit; relies solely on GoTrue's per-IP config which lives only in the local `supabase/config.toml` with no evidence it's mirrored on the hosted project (findings #1, #6 — both HIGH).
- **Password-reset request has no rate limit** either, unlike every other public form in the codebase which uses the existing `enforceRateLimit` helper (#2).
- **Signup leaks account existence** via `"Ya existe una cuenta con ese correo"`, and `enable_confirmations=false` means testing an email costs nothing (#3).
- **GoTrue's own password policy (6 chars, no complexity) is weaker than the app's 8-char check** — and since the anon key is public, the app-level check is bypassable via direct API calls (#4).
- **Leaked-password protection is still off** — already tracked in your own cutover doc as a pending dashboard toggle, just re-confirming it's still open (#5).
- **No session revocation on privilege downgrade** — revoking a vet/deactivating a govt/admin never calls `auth.admin.signOut`; mitigated today because every guard re-checks the DB fresh, but it's a missing defense-in-depth layer (#7).
- **No absolute session timeout** configured (#8).

**Confirmed clean:**
- Logout is genuinely reliable and portal-independent (#50/#48 fix holds — masthead + admin/gob/org layouts all own their own sign-out).
- Reset-token handling itself (entropy/expiry/single-use, no enumeration) is solid.
- Mi Argentina stub is safe — 404s when unconfigured, no half-wired trust.
- Cookie flags use secure `@supabase/ssr` defaults, nothing weakened.

7. Session — no revocation on privilege downgrade. `src/modules/organizations/application/revocations/revoke-vet-role.ts`, `revoke-org-verification.ts`, `revoke-govt-locality.ts`, `admin-institutional/deactivate-govt.ts`, `deactivate-admin.ts` all mutate `profiles`/`govt_assignments` and audit-log the action, but **none call `supabase.auth.admin.signOut(targetUserId, "global")`** — a revoked vet's or deactivated govt/admin's live Supabase session (JWT + refresh token) is never invalidated at the IdP. Mitigated today because every guard re-checks `profiles.deactivatedAt`/role fresh per request (`lib/infra/auth-guards.ts:96-107`, confirmed non-cached across requests), but it's a missing defense-in-depth layer: any future guard gap, direct PostgREST call, or long-lived client-side cache would serve a de-authorized actor. LOW-MED. Fix: add `supabaseAdmin.auth.admin.signOut(targetUserId, "global")` as a post-tx step in each of the 5 revocation/deactivation writers, alongside the existing best-effort notification insert.

8. Session — no absolute lifetime ceiling. `supabase/config.toml:266-271` (`[auth.sessions]` `timebox`/`inactivity_timeout`) both commented out — combined with `enable_refresh_token_rotation=true` (config.toml:166) a session self-renews forever with no forced re-authentication. A leaked refresh-token cookie for an `admin`/`govt` account stays valid indefinitely. LOW-MED. Fix: set `[auth.sessions] timebox = "24h"` (or similar) at minimum for institutional roles; if that's a bigger product change, at least track it as a known gap rather than leaving it silently unset.

9. `app/auth/callback/route.ts:20,28-31` — `nextParam` is read straight off the query string and used verbatim as the redirect target when present (`hasExplicitNext ? nextParam : ...`), unlike `loginAction`/`logoutAndReturnAction` which both sanitize via `safeReturnTo()` (`lib/infra/role-landing.ts`). No current caller passes attacker-controlled input here (all `redirectTo`/`next` constructions in the repo are server-side constants), so this is not exploitable today, but it's the one auth redirect path that doesn't match the established `safeReturnTo` convention. LOW. Fix: route `nextParam` through `safeReturnTo()` for parity/defense-in-depth.

10. Mi Argentina SSO stub — clean. `app/auth/miarg/callback/route.ts:31-33` 404s when `MIARG_OIDC_ISSUER`/`CLIENT_ID` are unset and 501s with a labeled TODO otherwise; `isMiArgOidcEnabled()` gate means no half-wired trust exists today. Forward note for Item 25b (not a current bug): the file's own TODO list doesn't call out binding the `state` param to a server-set anti-CSRF cookie/nonce (only "validate state" is listed) — when 25b lands, verify `state` is checked against a value stored server-side at the initiating redirect, not just checked for presence.

11. Logout reliability (#50/#48 regression check) — clean. Every chrome surface owns its own `logoutAction` form independent of `/cuenta` rendering: citizen masthead (`components/layout/AppCitizenMasthead.tsx:301`), admin (`app/admin/layout.tsx:90`), gob (`app/gob/layout.tsx:57`), org (`app/org/[orgToken]/layout.tsx:82`). No portal's sign-out depends on a page body rendering. `logoutAction`/`logoutAndReturnAction` (`src/modules/auth/application/logout.ts`) call `supabase.auth.signOut()` unconditionally with no auth precondition, so it can't itself hang.

12. Password-reset token handling — clean. Entropy/expiry/single-use are delegated to Supabase GoTrue (PKCE `code` in `resetPasswordForEmail` → `exchangeCodeForSession`, consumed once, `otp_expiry=3600s`), which is appropriate — the app doesn't try to roll its own token scheme. The request form correctly returns the identical generic message on both the account-exists and Supabase-error paths (`request-password-reset.ts:31-35`, covered by `__tests__/password-reset.test.ts:76-98`) — no enumeration on the reset path itself (contrast with #3, which is the signup path).

13. Cookie flags — clean. `lib/supabase/server.ts` / `lib/supabase/client.ts` pass no custom cookie options, so `@supabase/ssr` defaults apply (`httpOnly`, `secure` on HTTPS, `sameSite=lax`) with nothing in the app overriding them weaker.
