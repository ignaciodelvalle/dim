## Healthy — verified solid

### 1. The panorama API surface enforces the full institutional invariant set, not just role
- **Property**: all five `/api/panorama/*` route handlers resolve the caller through one shared gate (`resolveInstitutionalPanoramaActor`) that runs maintenance, session, erasure, deactivation, shift-expiry, role in {admin,govt} AND accountType==='institutional' — the exact set the page guard's `loadActiveInstitutionalProfile` enforces, answered with a status code instead of a redirect.
- **Path**: `app/api/panorama/_guard.ts:71`
- **Guard**: `scripts/check-authz-guards.ts` (`INSTITUTIONAL_GUARDS` lists `resolveInstitutionalPanoramaActor` at `:129`; `findRouteGuardViolations` treats `app/api/panorama/` as an operator route at `:907`; the `ROUTE_HANDLER_GUARDS` rule at `:701` reads the handler body only). Refuter verified the guard call is present in all 5 route files and confirmed `_guard.ts:75-91` runs the full chain. **Guard verified: yes** (with one caveat noted below).
- **What would break it**: a sixth panorama route added without the call, or a handler that resolves the actor itself with a bare `getUser` + role check — exactly what the three original routes did and what caused the 2026-07 self-minted-admin CRITICAL.
- **Evidence**: `rg -n "resolveInstitutionalPanoramaActor" app/api/panorama -g 'route.ts'` → all 5 route files call it (`[layer]/route.ts:47`, `kpis:32`, `rule-changes:50`, `scope:43`, `unit-history:74`). `_guard.ts:75-91` → `requireLiveUser()` then role/accountType check → 403.
- **Refuter caveat (not a defect in this property)**: `requireLiveUser` is in `AUTH_GUARDS` but not in `PERSONAL_TIER_GUARDS`, so a hypothetical sixth panorama route gated by `requireLiveUser` alone would satisfy both fence rules with no personal-tier guard — a fence gap for a route that does not exist today.

### 2. The mobile v1 surface derives identity from the verified bearer token, never from the request body
- **Property**: every non-public `app/api/v1` handler builds a client from the `Authorization` header and passes the raw token explicitly to `requireLiveUser({supabase, accessToken})`, so the token is validated by `getUser(jwt)` rather than an undocumented supabase-js internal flag.
- **Path**: `app/api/v1/me/caretaker-grants/route.ts:37`
- **Guard**: `scripts/check-authz-guards.ts` `ROUTE_HANDLER_GUARDS` rule (`:701`) plus the dedicated `lint:api-v1` fence in `pnpm verify`. **Guard verified: partially** — the refuter found the `guardedBy` attribution is wrong: `scripts/check-api-v1-envelope.ts` (the actual `lint:api-v1` script) fences the response envelope, not auth; the real backstop is `check-authz-guards.ts:701` (any guard call), which would not catch an `accessToken`-less `requireLiveUser()` call.
- **What would break it**: a v1 handler reading a `userId`/`petId` owner from the JSON body and trusting it, or one calling a bare `client.supabase.auth.getUser()`.
- **Evidence**: per-file sweep of all 33 `app/api/v1/**/route.ts` files — 28 non-exempt files, 39 handlers, each pairs `createClientFromBearer(...)` with `requireLiveUser({ supabase: client.supabase, accessToken: client.token })`. Zero hits for `body.(userId|actorUserId|ownerUserId)`. 5 files legitimately exempt via `@no-auth-required` (auth/login, auth/signup, auth/password-reset, localities, and `pets/[publicToken]/credential/route.ts` — the refuter found this fifth exemption was missing from the finder's list).

### 3. Decomiso execution fails closed for a scopeless govt and validates the animal's jurisdiction before the write
- **Property**: `executeDecomisoAction` refuses a govt with zero active jurisdictions before touching any data, then runs `validateExecuteDecomiso`, which carries jurisdiction-scope and double-seizure checks on both subject-kind branches.
- **Path**: `app/actions/decomiso.ts:109`
- **Guard**: none automated for the scoping itself (`requireDecomisoPrincipal`'s own doc says scope is the caller's responsibility) — this is a hand-written check, not fence-enforced. **Guard verified: n/a (none claimed)**, but the refuter independently confirmed `jurisdictionScopeContains` (`lib/domain/jurisdiction-canonical.ts:196-201`) is itself fail-closed on an empty jurisdiction list — a second independent backstop.
- **What would break it**: treating `jurisdictions === []` as universal scope, the way `fetchQueueHealthScoped` does (see A01-2) — here it would let a scopeless govt seize an animal anywhere in the country under Ley 14.346.
- **Evidence**: `decomiso.ts:109-114` returns the "No tenés jurisdicciones activas" error before `resolveGovtOrgForUser` (`:117`) or any write; siblings gate identically at `:381`/`:447`. `execute-decomiso.ts:168-175` and `:192-202` both call `jurisdictionScopeContains`. Refuter flags the in-repo test as tautological: `__tests__/decomiso-execute-action.test.ts:584-611` defines its own local `pairInScope` helper and asserts against that, never calling the real action or `jurisdictionScopeContains` — so no test exercises the `:109` zero-jurisdiction refusal despite the file header claiming it does.

- Kind: security
- Path: `lib/infra/live-user.ts:324`
- Exploit: any owner or vet on a personal account calls `selfDeactivatePersonalAccountAction(reason)` (`app/actions/profile-self-service.ts:62` → `self-deactivate-personal-account.ts:49`), which only sets `profiles.deactivated_at` and writes an audit row — no `signOut`, no token revocation. `requireLiveUser` (`live-user.ts:324`) gates the DEACTIVATED refusal on `accountType === "institutional"` only, so `requireUserOrRedirect`, `requirePetAccess`, `requireAlivePetAccess`, and `requireCapability` all keep passing. A deactivated vet holding an org membership (commonly `accountType: "personal"` per `authz-resolver.ts:141-148`) keeps `event.write`. No cross-tenant reach, no privilege gain — the actor only continues acting as themselves, which is why HIGH not CRITICAL.
- Evidence: `rg -n "deactivatedAt|deleted_at" app lib src --glob '*.ts' --glob '*.tsx' -g '!*.test.ts' | rg -v admin-institutional` → `live-user.ts:324: if (profile?.accountType === "institutional" && profile.deactivatedAt != null)`; comment at `:319-323` states personal `deactivated_at` "is today a bookkeeping flag that nothing reads for access"; `self-deactivate-personal-account.ts:44-64` only updates the column + inserts an audit row; `login.ts:220` only refuses `isDeactivatedInstitutional`; `DeactivateAccountDialog.tsx:45` comments "Reload so the layout guard redirects to /login" — a lockout that does not exist.
- Refuter notes: reproduce — CONFIRMED, HIGH. correctness — CONFIRMED, HIGH. impact — CONFIRMED, HIGH, adds that the cross-tenant leg (org staffer on `accountType: "personal"`) is real and that `middleware.ts` has no deactivation read at all.
- Fix: decide the personal-deactivation policy in `requireLiveUser`, not per-guard — either widen `:324` to check `deactivatedAt != null` for every accountType plus build the missing landing screen (the code comment already names this gap), or make `selfDeactivatePersonalAccountForUser` refuse until that screen exists.
