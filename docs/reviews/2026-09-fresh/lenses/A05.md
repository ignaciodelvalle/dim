**A05-2 — The subject-rights coverage fence cannot express one-sided coverage — a table reached by ONE RPC is counted as covered**
- Kind: fence-gap
- Path: `scripts/check-subject-rights-coverage.ts:197`
- Exploit: `checkClassification` (line 249) never requires a table to be in BOTH `IN_EXPORT` and `IN_ERASE`, and `gapCount` (line 369) counts only `KNOWN_GAP` — whose own definition is "neither RPC reaches it." So a table reached by exactly one function reads as full coverage. Live one-sided tables in `0208` (export body 190-396, erase body 414-1059): `pet_identifications` (217), `custody_disputes` (241/243), `organization_memberships` (363/365) — export only; `case_events` (669), `libreta_share_tokens` (914) — erase only. A sixth table, `attachments`, sits in `EXEMPT` (line 175) with a reason that itself admits it holds the subject's data — the exact false statement the fence's own header (line 60) says a fourth list exists to avoid.
- Evidence: `rg -n '^\s+"(case_events|libreta_share_tokens|custody_disputes|organization_memberships|pet_identifications)",' scripts/check-subject-rights-coverage.ts; rg -n '...' db/migrations/0208_...sql` → fence lines 109/115/119 (IN_EXPORT, ends 127) and 132/139 (IN_ERASE, starts 130); the five tables land on opposite sides in `0208`.
- Refuter notes: correctness — not refuted, medium confidence, HIGH. reproduce — not refuted, high confidence, MED (tie-break: asymmetry is partly on-screen via inline comments and the CI print at line 466). impact — not refuted, medium confidence, HIGH. Majority HIGH.
- Fix: split into a per-table `{export, erase}` classification, each side `covered | exempt(reason) | gap(reason)`, failing on any side left unclassified; move `attachments` out of `EXEMPT` into an explicit "covered in TypeScript" state with its export side declared a gap.
