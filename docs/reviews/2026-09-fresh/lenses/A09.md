## Ground truth

Branch `main` at `d7dbf25f7`, audited 2026-09-02, 51 files read (`filesReadCount: 51`; see Coverage for the list).

Scope: the `ownerships` table and every transition that changes who holds a pet — transfers (2-phase), rehome including sponsorship, adoption, caretaker grants and their expiry, foster, return-to-owner, custody-disputes, decomiso, and cross-org transfers. For each transition: who may initiate and accept, whether the counterparty is verified (and cannot be forged by id), idempotency and double-accept, what the public credential shows mid-transition, and which events are written. `src/modules/custody-disputes` has no infrastructure layer — this lens finds where its writes actually go. Ownership caches (`pets.*` columns, `ownerships`) versus the event spine.

What's new since the prior runs: rehome sponsorship; caretaker grants (finalize ends caretaker grant); custody disputes module; decomiso (seizure) flow; return-to-owner; mobile-initiated transfers via `/api/v1`; cross-org transfers.

Priors triaged: 9, carried from `docs/reviews/results/26-ownership-trust-chain.md` and `docs/reviews/results/26-ownership-trust-chain-rerun.md`. 7 closed, 2 still-open (re-filed below as A09-3, A09-4).

### Claimed healthy, not verified

**The P2P accept re-asserts the sender is still the single active owner, under the transfer row lock, before any destructive write** (`src/modules/transfers/application/accept-pet-transfer.ts:130`) — REFUTED as stated. The refuter reproduced the claimed guard (`findTransferByIdForUpdate` FOR UPDATE + `findActiveOwnerOwnership` identity check, both before `closeOwnerOwnerships`) but showed it only protects against an **already-committed** custody move: `acceptPetTransfer` takes no pet advisory lock, and `findActiveOwnerOwnership` (`transfers-repository.ts:195-208`) is a plain `SELECT` with no `.for("update")` — unlike every sibling custody mover (decomiso, dispute resolution, return-to-owner, adoption, foster closers), which all serialize on `pg_advisory_xact_lock(hashtext(petId))` (`src/modules/rehome/README.md:142-149`). Under READ COMMITTED, an accept whose reads land while a decomiso is in flight can pass the check, then its `closeOwnerOwnerships` UPDATE blocks on the decomiso's row lock, re-evaluates to 0 matched rows after commit, and `insertOwnerOwnership` still lands — `ownerships_one_active_owner_per_pet` does not fire because the decomiso already ended the prior owner row. This is the same defect class the rehome README documents as fixed one file over. **This item is folded into no separate finding in this pass** (it surfaces the same race-condition family the healthy items above show is fixed elsewhere in the codebase, but was not itself re-filed as a numbered finding here — flag for a follow-up pass if the PO wants it tracked).

## Findings (CONFIRMED)

### HIGH

**A09-1 — An UNCONFIRMED e-mail address is accepted as the addressee proof that moves titularidad and grants caretaker access**
Kind: security · `src/modules/transfers/domain/owner-transfer-rules.ts:124`
Exploit: Alice initiates a transfer to `bob@gmail.com`, an address with no account — `initiate-pet-transfer.ts:118-123` stores `to_owner_id = NULL`, `to_owner_email = 'bob@gmail.com'` (7-day window). Mallory, who knows the address, signs up with it: `enable_confirmations = false` in prod (`supabase/config.toml:221`, confirmed by `app/api/v1/auth/signup/route.ts:26` — "PO decision 2026-07-10"), so GoTrue issues a session with no mailbox proof. `GET /api/v1/me/transfers` lists the pending transfer for her (`list-transfers-for-user.ts:111-116`, same `validateRecipientMatch` predicate) including its `transferToken`. `POST /api/v1/me/transfers {command:'accept'}` passes `validateRecipientMatch`'s e-mail arm (`owner-transfer-rules.ts:130-133`, a bare case-insensitive string compare with no `email_confirmed_at` check anywhere in the chain — confirmed absent by `rg` across non-test files) and titularidad moves to Mallory, `custody_transferred` appended naming her. Same shape on caretaker grants (`accept-caretaker-grant.ts:80-82`), where the prize is write access plus the caretaker's name/phone on the public lost-mode credential.
Evidence: `rg -n 'enable_confirmations' supabase/config.toml` → `221:enable_confirmations = false`; `rg -n -A11 'export function validateRecipientMatch' src/modules/transfers/domain/owner-transfer-rules.ts` → `130: if (args.toOwnerId !== null) { 131: return args.toOwnerId === args.callerId; } 133: return args.toOwnerEmail.toLowerCase() === args.callerEmail.toLowerCase();`; `initiate-pet-transfer.ts:118` `toOwnerId = await repo.findUserIdByEmail(toEmail)`; `route.ts:145,217` `callerEmail: live.user.email`.
Refuter notes: 3/3 refuters CONFIRMED at HIGH (not CRITICAL — needs the target's address AND the target not yet registered; the toggle is PO-gated, not code). One refuter added a narrowing detail: the web initiate path fires `inviteUserByEmail` (`actions.ts:166-181`) which would pre-create the auth user, but it's wrapped in a swallowing try/catch and the native/API path skips it entirely (`commands.ts:355-365`), so the window is fully open on API-initiated transfers regardless.
Fix: gate the e-mail fallback arm on the accepting account's `email_confirmed_at` being non-null (id arm unaffected), or bind the invitation to a single-use secret delivered to the address rather than exposing `transferToken` to any account matching the string. Turning `enable_confirmations` ON closes it at the root (tracked PO item #65, currently priced only as an enumeration leak — re-price with this custody consequence attached). Also reword `lib/infra/live-user.ts:103-105`, which currently reasons about token authenticity as if it cleared the addressee arm.
fixClass: po-decision · priorStatus: new

### MED

**A09-2 — The P2P transfer accept ends caretaker arrangements and then drops the notification fan-out its own repository returns for that purpose**
Kind: bug · `src/modules/transfers/application/accept-pet-transfer.ts:160`
Exploit: Ana's caretaker Beto (90-day grant, physically holding the dog) loses access silently when Ana sells to Carla. `closeOwnerOwnerships` correctly ends Beto's row and emits `caretaker_ended`, and returns `{ endedCaretakerGrants }` precisely so the caller can run `notifyCaretakersOfHandoff` — but `accept-pet-transfer.ts:160-163` discards the return value entirely and passes no `actorUserId`. The four sibling hand-offs (foster convert, adoption finalize, dispute resolve, decomiso) all call `notifyCaretakersOfHandoff`; zero call sites exist in `src/modules/transfers`. No test can see this: the repository-level test drives `closeOwnerOwnerships` directly and asserts only rows/grant/event; the use-case test pins the two-argument call shape with a mock resolving `undefined`.
Evidence: `rg -n 'closeOwnerOwnerships' -A3 src/modules/transfers/application/accept-pet-transfer.ts` → `160: await repo.closeOwnerOwnerships(161: transfer.petId, 162: tx, 163: );` (return discarded, no 3rd arg); `rg -n 'notifyCaretakersOfHandoff' --glob '!*.test.ts'` → def `end-pet-ownerships.ts:413`; callers `foster/.../convert-foster-to-owner.ts:122`, `adoption/.../finalize-adoption.ts:361`, `custody-disputes/.../resolve-dispute.ts:409`, `app/actions/decomiso.ts:234`; zero in `src/modules/transfers`.
Refuter notes: 3/3 CONFIRMED at MED (row and event still close correctly — this is a missing notification plus an unattributed spine event, not a wrong-role access).
Fix: destructure `{ endedCaretakerGrants }` in `accept-pet-transfer.ts`, pass `{ actorUserId: user.id, now }`, hoist the fan-out out of the transaction, call `notifyCaretakersOfHandoff` after commit exactly as `finalize-adoption.ts:361` does. Update `use-cases.test.ts:485`'s two-argument assertion in the same change.
fixClass: code-sdd · priorStatus: new

### LOW

**A09-3 — `custody_disputes.status` still cannot say 'escalated', so the dispute row and its case disagree on lifecycle**
Kind: bug · `db/schema.ts:3644` · priorId: 8 (still-open)
Exploit: `escalate-stale-disputes.ts:100-101` moves `cases.status` to `escalated`, but the CHECK constraint (`custody_disputes_status_valid`, `in ('open','resolved','withdrawn')`) forbids the dispute row from following, so it stays `open`. Any reader keyed off `custody_disputes.status` — including `resolveDisputeUseCase`'s own guard — cannot tell an escalated file from an untouched one. One refuter correction: the manual `escalate-dispute.ts` path does NOT touch `cases.status` at all (only a `note_added` event + audit log), so the two-record disagreement is specifically a cron-path defect, not both paths — this narrows but doesn't change the verdict.
Evidence: `db/schema.ts:3644` `sql`${table.status} in ('open','resolved','withdrawn')``; `db/schema.ts:3988` `CASE_STATUSES = ["open","escalated","closed","merged"]`.
Fix: add `'escalated'` to the CHECK (forward-only migration, recount next free NNNN at write time) and to the status union, or make the dispute detail view / `resolveDisputeUseCase` read lifecycle from the linked `cases` row and treat `custody_disputes.status` as resolution-outcome only.
fixClass: code-sdd

**A09-4 — The only dispute SLA is a 365-day warning notification with no consequence and no first-response deadline**
Kind: debt · `src/modules/cases/application/escalate-stale-disputes.ts:45` · priorId: 9 (still-open)
Exploit: a dispute opened today produces no deadline signal for a year, and the year-mark produces only a notification (line 131) — nothing closes, reassigns, or auto-resolves `pets.inCustodyDispute`. Because the dispute flag hard-refuses every custody writer, an unattended dispute is an indefinite titularidad freeze. Scored LOW: fail-safe not fail-open, and opening a dispute already costs a private identifier plus an evidence file.
Evidence: `escalate-stale-disputes.ts:1` "escalate custody_dispute cases open for >365 days"; `:45` default 365; `:131` notification body only. `ls app/api/cron` → 26 routes, this is the only dispute-facing one.
Fix: add a shorter first-response SLA (30/60 days) addressed to the assigned arbiter, distinct from the 365-day stale flag; surface days-open on the dispute queue. PO to decide consequence of a missed first-response deadline.
fixClass: po-decision

**A09-5 — Ownership drift detection covers only the caretaker role — owner, foster and shelter_custody rows have none**
Kind: debt · `scripts/detect-pet-cache-drift.ts:30`
Exploit: the detector's own header names the gap: "every OTHER ownership role (owner / foster / shelter_custody) still has no drift detection at all." The role that actually answers "who holds this animal" — `role='owner'` — is a dual-write with no detector, unlike the `pets.*` column half (`CHECKED_COLUMNS` in `lib/infra/rederive-pet-cache.ts:137-178` does cover `inCustodyDispute`/`status`). Declared debt, self-documented, not a hidden defect.
Evidence: `scripts/detect-pet-cache-drift.ts:30-31,120` — "KNOWN GAP... SCOPED TO caretaker"; only drift kind emitted is `pet_caretaker_ownership_drift` (:188).
Fix: extend `checkPetOwnerships` to the `owner` role first (re-derive from `custody_transferred`/`ownership_claimed`/`adoption_finalized`/`decomiso`, report a set difference under a new kind), then foster/shelter_custody. Reuse the existing per-pet advisory lock and read-only posture.
fixClass: code-sdd

**A09-6 — custody-disputes has no infrastructure layer and its writes go straight to `@/db` — and no fence polices that anywhere**
Kind: convention · `src/modules/custody-disputes/application/resolve-dispute.ts:34`
Exploit (answering the brief directly): yes, the dispute module's application layer writes straight to `@/db` — all 8 of its files that write do. NOT unique to custody-disputes: 43 application files across 9 modules do the same (auth 3, cases 6, custody-disputes 8, decomiso 6, events 1, notifications 1, return-to-owner 12, service-offerings 5, welfare 1), and `scripts/check-dependency-direction.ts` polices only the between-module axis, not application→`@/db`. Practical cost is testability, not security — this is also how A09-2's blind spot arose (transfers/caretakers use-cases take an injected `repo` and are unit-testable against a fake; dispute use-cases need a live DB).
Evidence: `fd . src/modules/custody-disputes -e ts` → only `application/` + `domain/`; `rg -l 'from "@/db"' src/modules/*/application/*.ts | ... | uniq -c` → per-module counts above.
Fix: either accept `application → @/db` as the repo's documented norm (say so in AGENTS.md), or fence it — extend `check-dependency-direction.ts` with an application-layer check plus an explicit allowlist of the 43 current files so the count can only shrink.
fixClass: fence-candidate
