**A08-2 — The override audit row records no pre-image, so an audited ledger rewrite is unreconstructable.**
Kind: debt. `db/migrations/0127_pet_events_append_only.sql:54`. Prior: #5, still-open.

The trigger permits it; the audit row logs only `operation`/`pet_event_id`/`pet_id`/`event_type`/`occurred_at` (no `payload`, no `notes`), and on UPDATE every `coalesce(new.X, old.X)` resolves to NEW, so even `event_type`/`occurred_at` are logged post-rewrite. No record anywhere holds the old value.
Evidence: `rg -n -C 2 "jsonb_build_object" db/migrations/0127_pet_events_append_only.sql` → `:54-60` operation/pet_event_id/pet_id/event_type/occurred_at only.
Refuter notes: correctness — not refuted but downgraded to LOW: flagged that the naive fix (`'old', to_jsonb(old)`) would be a HIGH privacy defect against the one live consumer of the hatch, `0129_erase_subject_data_event_pii_redaction.sql:112-131` (PII redaction), which must not be reversed by preserving a pre-image forever; also no app/src/lib code path opens the hatch, only manual DBA action. reproduce — not refuted, MED, cites an independent prior review scoring the same gap MED. impact — not refuted, MED, confirmed via `db/triggers.sql:143-154`/`229-235` live definitions, no later migration replaces the function.
Fix: add `'old', to_jsonb(old)` / `'new', to_jsonb(new)` (or at minimum old/new `payload`, `notes`, `occurred_at`, `event_type`) to both `jsonb_build_object` calls in a new migration — **but scope it to exclude/redact PII fields specifically, per the correctness refuter's caveat about the erase-subject-data consumer** — and mirror in `db/triggers.sql`; add an append-only test asserting the pre-image is present. fixClass: code-sdd.

## Refuted

**A08-5 — "pet_events FKs declare ON DELETE SET NULL, a promise the append-only trigger can never keep, and a live profiles DELETE runs into it."** Finder's claim: `db/schema.ts:1292-1294` declares `onDelete: "set null"` on `recorded_by_user_id`, and `claim-stub-profile.ts:207` deletes a stub `profiles` row inside a transaction with no override GUC, so the FK cascade would collide with the append-only trigger and roll back an owner's pet-claim. All three refuters (correctness, reproduce, impact) refuted it unanimously, high confidence: `src/modules/pets/application/stub-claim/claim-stub-profile.ts:36` sets `const STUB_CLAIM_ENABLED: boolean = false`, and lines 61-67 return an explanatory error ("El reclamo por DNI está temporalmente pausado") *before* any DB call or the transaction at line 207 — the delete is unreachable dead code, held pending Mi Argentina identity verification (file header, lines 11-19). No other `delete(profiles)` call site exists in `src`/`app`/`lib`/`db`/`scripts` outside tests. The schema-declaration mismatch (`ON DELETE SET NULL` vs. the trigger's actual behavior) is real but latent, with no live path — filed as a nit-level observation, not a MED bug.
