## Healthy — verified solid

### 1. Unconditional anon/authenticated reads are catalog-enumerated, and the single exception was verified column by column
- **Property**: no RLS-enabled public table exposes a SELECT/ALL policy to `anon`/`authenticated`/`public` whose `USING` clause is absent or trivially `true`, except `time_slots.SELECT` — and `time_slots` carries no column that identifies a person.
- **Path**: `__tests__/rls/read-path-matrix.test.ts:47`
- **Guard**: `__tests__/rls/read-path-matrix.test.ts` (catalog sweep, assertion at line 144; stale-allowlist check at 155) — refuter confirmed the guard directly (`guardVerified: true`, high confidence).
- **What would break it**: adding a person-shaped column to `time_slots` (e.g. `booked_by_user_id`) would silently turn the allowlisted public read into a leak — the allowlist is keyed on the table, not its column set.
- **Evidence**: `rg -ni 'using\s*\(\s*true\s*\)' db/ supabase/` → one hit, `db/migrations/0086_track_rls_in_migrations.sql:597` (`time_slots read publicly ... using (true)`); `db/schema.ts:2925-2939` shows `time_slots` columns (id, service_offering_id, rule_id, starts_at, ends_at, capacity, bookings_count, status, timestamps) — no person-identifying column; zero `FOR ALL` policies anywhere in `db/migrations`.

### 2. The intentional-open-write allowlist is empty, and a third test forbids it from going stale
- **Property**: no RLS-enabled public table exposes an unconditional INSERT/UPDATE/DELETE/ALL to `anon`, `authenticated` or `public` — and any allowlist entry that stops matching a real live policy is itself a test failure.
- **Path**: `__tests__/rls/write-path-matrix.test.ts:49`
- **Guard**: `__tests__/rls/write-path-matrix.test.ts` (`INTENTIONAL_UNCONDITIONAL_WRITES = {}` at lines 49-77; main assertion 177-180; stale-exception test at 183) — refuter confirmed the guard directly (`guardVerified: true`, high confidence).
- **What would break it**: a policy written as `WITH CHECK ((1 = 1))` or `USING (true AND true)` slips past `isUnconditional()`, which compares the deparsed clause to the literal string `"true"` (line 118) — also flagged as a nit below.
- **Evidence**: three original `with check (true)` write policies in 0086 (pets INSERT :85, welfare_reports INSERT :429, welfare_report_attachments INSERT :443) are all closed — 0175:55, 0173:60, 0099:68 respectively; refuter independently re-derived this rather than trusting the finder's list.

### 3. The signed-upload bucket ships deny-all to callers, with a replay-time assertion that says out loud it is the weaker half
- **Property**: `uploads-staging` (migration 0206) is private, size- and MIME-capped at the object store, and carries no `storage.objects` policy naming `anon`, `authenticated` or `public` — writes reach it only through a service-role-minted signed URL, which does not consult RLS at all.
- **Path**: `db/migrations/0206_uploads_staging_bucket.sql:140`
- **Guard**: the migration's own replay-time `DO` block (`raise exception` at 0206:124, :137, :155) plus `scripts/check-storage-write-policies.ts` — refuter confirmed the guard directly (`guardVerified: true`, high confidence).
- **What would break it**: the `DO` block runs at migration replay, not per commit, and only at 0206's position in the replay — a caller-facing policy added by a *later* migration is invisible to it; the static fence (`check-storage-write-policies.ts`) would only catch a bucket-name-only predicate, not one scoped with `auth.uid()`.
- **Evidence**: `rg -ni 'create policy' db/migrations/0206_uploads_staging_bucket.sql` → no matches; `rg -ni 'uploads-staging' db/migrations/*.sql | rg -v 0206` → no matches (nothing later references the bucket); `lib/infra/pet-photo-upload.ts:177-179` mints the signed URL via `createAdminClient().storage.from(STAGING_BUCKET).createSignedUploadUrl`.

### 4. The denuncia identity/content split survived a DROP VIEW: both views are security_invoker and 0210 restates the grants 0186 set
- **Property**: `public.welfare_report_content` and `public.welfare_report_reporter_identity` are created `WITH (security_invoker = true)`, so the caller's own RLS on `welfare_reports` applies through the view; the reporter-identity side is revoked from `PUBLIC`, `anon` and `authenticated` outright, and when 0210 had to `DROP` and recreate the content view it restated both the `REVOKE` and the asymmetric `GRANT` rather than relying on Postgres to carry them.
- **Path**: `db/migrations/0210_welfare_content_view_observed_symptoms.sql:21`
- **Guard**: **none** — no CI fence enumerates views (see A02-3); refuter marked `guardVerified: false` explicitly, and this is the honest state.
- **What would break it**: dropping `security_invoker` on a future recreate would make the view execute as its owner and return every denuncia to any authenticated caller, and nothing in CI would notice.
- **Evidence**: `0210:19-21` `DROP VIEW IF EXISTS public.welfare_report_content; CREATE VIEW ... WITH (security_invoker = true) AS`; `0210:76-78` `-- Grants restated from 0186 - DROP VIEW discarded them.`; `0186:73-74` / `0186:130-131` both views created `security_invoker`; `0186:166` `REVOKE ALL ON public.welfare_report_reporter_identity FROM PUBLIC, anon, authenticated` with no `GRANT` after; only 0186 and 0210 reference either view, and 0210 is the highest-numbered migration in the repo.

### Claimed healthy, not verified

- **The anon-RPC-oracle class is closed by catalog enumeration** (`__tests__/rls/function-hardening.test.ts:168`) — **refuted** by one refuter (medium confidence, `guardVerified: true` for the SELECT-side enumeration itself). What's refuted is the claim's last conjunct — "each subject-rights migration re-asserts the REVOKE PUBLIC / REVOKE anon / GRANT authenticated trio" — three migrations (0059, 0087, 0106) replay only `REVOKE ALL FROM PUBLIC` + `GRANT authenticated`, with **no** `REVOKE EXECUTE ... FROM anon`, which is the exact 0114 trap the claim says is universally avoided. Harmless today (all three predate 0114 and `CREATE OR REPLACE` preserves the ACL), but stated as an invariant of every replace when it is not one.
- **Tables added after 0130 ship RLS on, SELECT-only, with an explicit `TO authenticated` and no write policy at all** (`db/migrations/0189_pet_caretaker_grants.sql:191`) — **refuted** (high confidence, `guardVerified: false`). Only `pet_tags` (0169) and `pet_caretaker_grants` (0189) are actually SELECT-only. The policies that do exist are correctly scoped (not an exposure), but the claim mischaracterizes the posture as uniform when it is not, and no fence asserts absence-of-write-policy at all (`check-rls-coverage.ts` / `coverage.test.ts` only assert `relrowsecurity`).

## Findings (CONFIRMED)

### HIGH

#### A02-1 — `pet_events` PostgREST INSERT admits forged provenance (`author_role` / `author_verified`), permanently, in the append-only spine
- **Kind**: security
- **Path**: `db/migrations/0190_titular_only_rls.sql:140`
- **Prior**: 5, still-open
- **Exploit**: any authenticated account with an active non-caretaker ownership on one pet can `POST /rest/v1/pet_events` with `author_role: "govt"`, `author_verified: true`, `author_organization_id: null` for a non-titular-only event type (e.g. a vaccination). All three conjuncts of the 0190 `WITH CHECK` pass — nothing constrains `author_role`/`author_verified`/`recorded_by_user_id`. No `BEFORE INSERT` trigger and no `CHECK` constraint pair those columns (`db/triggers.sql:192-199` only wires `pet_events_no_update`/`pet_events_no_delete`). `computeConfidence` (`lib/events/event-confidence.ts:64-74`) then ranks the forged row `institutional_verified`/`professional_verified`, which `credential-badges.ts:169-182` renders on the public credential and `lib/projections/pet-compliance.ts:328-343` uses to clear compliance obligations. With no UPDATE/DELETE policy on `pet_events`, the forgery is permanent. HIGH not CRITICAL: no actor-role escalation, and the pets are the attacker's own — but the forged credential is consumed by third parties (public page, compliance gate, surveillance dashboard).
- **Evidence**:
  - `rg -n -A15 'CREATE POLICY "Pet events insertable by active owner' db/migrations/0190_titular_only_rls.sql` → `:140-155` `WITH CHECK (author_organization_id IS NULL AND EXISTS(ownerships ...) AND (NOT (event_type = ANY (public.titular_only_event_types())) OR public.has_titular_write_access(...)))`
  - `db/schema.ts:1295` `authorRole ... .default("owner")`; `:1302` `authorVerified ... .default(false)`
  - `lib/events/event-confidence.ts:67-74` `if (authorRole === "govt" && authorVerified) return "institutional_verified"` / `if (authorRole === "vet" && authorVerified) return "professional_verified"`
  - `db/triggers.sql:192-199` only `pet_events_no_update` / `pet_events_no_delete`; no GRANT/REVOKE on `pet_events` anywhere in `db/*.sql`
- **Refuter notes**: 3/3 votes CONFIRMED HIGH, all independently reproduced end-to-end (correctness, reproduce, impact lenses). One noted the write-up's example event type (`"rabies_vaccination"`) is not in the actual `EVENT_TYPES` catalog — which if anything strengthens the finding, since the policy doesn't constrain `event_type` against the catalog either.
- **Fix**: forward-only migration — rewrite the `pet_events` INSERT policy's `WITH CHECK` to pin provenance to what the caller actually is (`author_role = 'owner' AND author_verified = false AND recorded_by_user_id = (SELECT auth.uid())`), or drop the PostgREST INSERT policy entirely and route owner-emitted events through the existing Drizzle server action that runs `validateEventPayload`. Add a paired probe to `__tests__/rls/matrix.data.ts` so the property is behaviourally fenced.
- **fixClass**: code-sdd
