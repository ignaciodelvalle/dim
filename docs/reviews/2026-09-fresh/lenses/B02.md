# B02 — app -> db boundary: direct drizzle access from app/ and lib/ versus src/modules

> Snapshot: `d7dbf25f7` (`main`) · Audit: 2026-09-fresh · Lens B02

## Ground truth

- Branch: `main`, SHA `d7dbf25f7`, checked 2026-09-02.
- 12 files read directly (see Coverage); everything else is regex-derived and spot-checked.
- **No written rule governs app/ -> db reads.** `docs/architecture/hexagonal-lite.md` is scoped to the write path only: its layer table (lines 60-65) names four layers — `domain/`, `application/`, `infrastructure/`, `actions.ts` — all inside `src/modules/*`, and its one prose rule, `hexagonal-lite.md:58`, is "dependencies point inward: `actions.ts` and `infrastructure/` are the only layers that touch the framework and the database." Read literally that bans page reads, but `page.tsx` never appears in the document — the sentence is scoped to the module diagram above it. A negative sweep confirms this: `rg -n -i "page-level (read|import)|reads? (directly )?from (the )?(db|database)|pages? may (read|not)" docs/architecture docs/superpowers AGENTS.md` returns zero lines.
- What IS written is an endorsement of the status quo: `AGENTS.md:1024` — "Server-side reads via Drizzle bypass RLS by design — the public credential page at `/p/{public_token}` continues to work because its server component goes through Drizzle, not supabase-js." And `scripts/check-dependency-direction.ts:135`, describing custodia-temporal as adding zero module edges because "the owner cockpit reads caretaker state via a PAGE-level import (app/** is outside the module graph) rather than through a `pets` use-case — that import is the one edge that would invert this fence."
- Enforcement that does exist is narrower still: `biome.json:67-71` fences `src/modules/*/domain/**` and bans `@/db`, `drizzle-orm`, `next*`, `server-only`; `biome.json:91-95` fences `src/modules/*/application/**` and bans only `next*`/`server-only`/`@/lib/supabase/server` — **not** `@/db`. Verified directly in `biome.json`, not via AGENTS.md's paraphrase. No `noRestrictedImports` scope covers `app/` or `lib/` at all.

## The decision the PO must make

Should `app/` (and `lib/`) keep issuing Drizzle queries directly, or must all database access — reads included — go through `src/modules`? This sets the fence baseline for any future `check-app-db-boundary.ts`: whichever answer is chosen, it decides whether ~150 existing files are grandfathered debt or a burn-down list, and whether apps/mobile (0 direct db imports, reaching the server exclusively through `api/v1`) is the shape every future read must match.

## Shapes found

1. **`page.tsx`: a named read helper for the main query, plus an inline drizzle select for a side lookup.** read, 101 files (`rg -lU --multiline '<op-re>' app -g "page.tsx" | wc -l`). Example: `app/gob/cola/page.tsx:41-61`, `app/(public)/p/[publicToken]/page.tsx:141-142`, `app/(app)/cuenta/page.tsx:72-73,108-109`. The dominant shape by an order of magnitude: 131 of the 141 files with an inline `db.select` also import `@/lib/infra` in the same file — this is topping up a helper's result, not bypassing the read tier. 132 of 145 read-touching files never write.

2. **Screen/Lens component (non-`page.tsx`) issuing its own query.** read, 12 files (`rg -lU --multiline '<op-re>' app -g "*.tsx" -g "!page.tsx" | rg -v test`). Example: `app/gob/moderacion/ModeracionQueueScreen.tsx`, `app/admin/govts/GovtsScreen.tsx`, `app/(public)/p/[publicToken]/CredentialStreamedSections.tsx`. Ten are `*Screen.tsx`/`*Lens.tsx` console components one directory below a thin page; the rest are Next.js special files (`opengraph-image.tsx`) that a route-convention glob would miss entirely. `layout.tsx` count is 0 — that shape doesn't exist here.

3. **Cron `route.ts` as an unencapsulated job body with a `cronRuns` ledger write.** write, 9 files (`rg -lU --multiline '<write-re>' app -g "route.ts" | rg cron | wc -l`). Example: `app/api/cron/purge-scan-events/route.ts:40-43`, `app/api/cron/drain-outbox/route.ts`, `app/api/cron/auto-expire-approvals/route.ts`. The route authorizes, INSERTs a `cronRuns` row, delegates real work to `lib/infra`, then UPDATEs the ledger row closed — `cronRuns` is 18 of roughly 36 write-op hits across all of `app/`, i.e. job bookkeeping, not domain state.

4. **`api/v1` colocated command module — a de-facto hexagonal module living inside `app/`.** mixed, 6 db-issuing files (`rg -lU --multiline '<op-re>' app/api/v1 | rg -v test`; corrected from explorer's 7). Example: `app/api/v1/pets/[publicToken]/events/writers.ts`, `app/api/v1/me/caretaker-grants/commands.ts`, `app/api/v1/appointments/query.ts`. `app/api/v1/pets/[publicToken]/profile/payload.ts` is the exception that proves the rule: it issues **no** db op — it imports `src/modules/pets/application/read/owner-pet-detail-queries.ts` directly (`payload.ts:22`), the one file in `app/` that already gets its data purely through a module use case.

5. **Fat server action still issuing its own drizzle, alongside a use-case call.** mixed, 14 files in `app/actions/` (`rg -l "from ['\"]@/db" app/actions | rg -v test | wc -l`) plus 7 colocated `actions.ts`/`action.ts` files outside `app/actions` (corrected from explorer's 5 — `app/admin/libro/actions.ts:46-47` and `.../microchip/reemplazar/action.ts:38-39` were missed). Example: `app/(public)/p/[publicToken]/encontre/action.ts:347-348`, `app/actions/bulk-pet-events.ts`, `app/org/[orgToken]/adopciones/[appEventId]/page.tsx:326`. 66 of 70 `app/actions/*.ts` files already call `@/src/modules`; only ONE non-test file in all of `app/` inserts into the event spine (`petEvents`) — `encontre/action.ts`.

## Options

**A — Reads are an accepted pattern from `app/`; writes must go through `src/modules`.**
Consequence: ratifies what the code and `AGENTS.md:1024` already depend on. Write side is nearly free — 22 non-test writers, only 1 touches the spine. Cost: 132 read-only files stay unreusable by apps/mobile (0 db imports, 23 `api/v1` refs) — duplication doesn't shrink, it just stops growing on the write axis.
Baseline: `scripts/app-db-boundary-baseline.json` with a `writes` array (22 paths, table-annotated so `cronRuns (ledger)` is visually distinct from `petEvents (SPINE)`) and `spineWriters` pinned at 1. No `reads` array — reads are permitted, not baselined.
Fence sketch: new `scripts/check-app-db-boundary.ts`, shaped like `check-application-fence.ts`/`check-db-budget.ts` (30 precedents exist). Scan `app/**/*.{ts,tsx}` minus tests — not a route-convention glob (12 db-touching files are neither `page.tsx` nor `route.ts` nor `layout.tsx`). Strip comments/strings first. Multiline-tolerant write detection (naive single-line regex finds 6 files where the true count is 17 — the codebase formats `await db\n  .insert(`). Non-vacuity: assert >0 app files scanned, a synthetic `db.insert(pets)` gets flagged, every baseline path still exists.
Cost: low — days, not weeks.

**B — All database access goes through `src/modules`; `app/` imports use cases and readers only.**
Consequence: the clean answer, with a working precedent (`owner-pet-detail-queries.ts`, shared by the owner page and `app/api/v1/.../profile/payload.ts`). But it is 154 non-test files, and not a file move: 131 of 141 inline-select files already call a `lib/infra` helper in the same file, so what moves is the leftover supplementary query — a per-file judgment call, not a mechanical relocation. By route group (excl tests): `app/(app)` 36, `app/org` 34, `app/gob` 21, `app/admin` 14, `app/(public)` 12, `app/actions` 6, `app/api` 4, plus 5 singletons. Cheapest slice: the 6 `api/v1` files. Hardest: the 12 Screen/Lens components with no `api/v1` twin to justify extraction. B also says nothing about `lib/`'s own 88 read + 21 write files — and `hexagonal-lite.md:337` explicitly blesses `lib/metrics` as "infrastructure-adjacent: it reads `@/db`," so B either silently contradicts a blessed pattern or is really option C.
Baseline: `scripts/app-db-boundary-baseline.json` listing all 154 files grouped by route group, `total` asserted non-increasing, paired with a written migration order (as the strangler backlog is tracked per `hexagonal-lite.md:171-172`).
Fence sketch: same scanner, widened predicate — any `db` import from `@/db` inside `app/` is a violation (schema-table-only imports, 40 of the 204, stay legal — no boundary value in banning a type reference). Add: prove `drizzle-orm` operator imports (151 files: `eq`, `and`, `inArray`) go to zero alongside `db` imports, or the fence certifies a boundary query fragments still cross. Resolve first that `owner-pet-detail-queries.ts` sits in `application/` and imports `@/db`/`drizzle-orm` directly (lines 24, 39) — which `hexagonal-lite.md:63` forbids — before moving 154 files into a shape the document doesn't describe.
Cost: high — weeks, judgment-heavy.

**C — Reads must go through a NAMED read tier (`lib/infra`, `lib/metrics`, `lib/analytics`, or `src/modules/*/application/read/`); writes go through `src/modules`.**
Consequence: the middle path the data actually supports, and closer to shipped than A or B — the read tier already exists and is dominant (422 app files import `@/lib/infra`; 131 of 141 inline-select files call it in the same file). C asks for ~141 supplementary queries to move one directory down, not 132 file migrations. `lib/` is already organized into exactly three sanctioned dirs (infra 59, analytics 22, metrics 17) plus two strays. Keeps `AGENTS.md:1024`'s credential guarantee intact and `hexagonal-lite.md:337`'s `lib/metrics` blessing coherent. Does NOT serve mobile — a read in `lib/infra` is as unreachable from `apps/mobile` as a read in a page. Stepping stone to B, not a substitute — but makes B cheap later, since a named function is trivially relocatable and an inline JSX-adjacent select is not.
Baseline: `inlineReads` array of the 141 files with per-file query-site counts (so 3→1 selects registers as progress), plus the `writes` array from A, plus a `sanctionedReadTiers` allowlist (4 entries) the fence asserts is non-empty.
Fence sketch: as in A for writes; second rule flags any `db.select`/`db.execute` inside `app/**` unless baselined. Two extra non-vacuity guards: (1) each sanctioned dir must currently export ≥1 drizzle-issuing function, so a rename can't silently empty the allowlist (the `check-application-fence.ts:17-20` lesson: an exemption that outlives its violation stops the ratchet — that list said 46 when truth was 44); (2) path-anchor the allowlist to `lib/` and `src/modules/` and reject `app/**`, because `app/gob/acciones/_lib/worklist-io.ts` and `app/admin/auditoria/_lib/load-audit-data.ts` already exist in exactly the loophole shape (a co-located `_lib/` inside `app/`) — decide up front whether they're compliant or the first two burn-down entries.
Cost: medium — the norm is adoptable immediately; the 141-file catch-up is optional and incremental.

### Recommendation

Take option A now, as a write-only fence, and put the read decision on a separate clock — they are not the same question, and one is nearly free. The write half lands this week over 22 files, with one genuinely dangerous entry: `app/(public)/p/[publicToken]/encontre/action.ts` is the last non-test file in `app/` that inserts into the event spine; pinning that at 1 protects invariant #2 more than any amount of read-path tidying. Everything else in the write column is cron ledger bookkeeping (`cronRuns` = 18 of ~36 write hits) and audit inserts — named exceptions with their table annotated, not laundered into a generic list.

The read half is the uncomfortable honest answer: the codebase has already decided, `AGENTS.md:1024` depends on the decision, and 131 of 141 files already call the read tier in the same breath as their inline query — declaring reads illegal today opens a 132-file burn-down against a boundary the repo has been contradicting deliberately and successfully for a year. But it isn't free: with apps/mobile at 0 db imports and 23 `api/v1` call sites, every page-only read is a read that gets written twice. So: ratify A as the fence, adopt C's norm going forward ("a new supplementary select in a `page.tsx` goes into the `lib/infra` helper the page is already calling") — costs new work nothing, keeps B affordable if mobile later forces it.

One correction needed regardless of which way this goes: `src/modules/pets/application/read/owner-pet-detail-queries.ts` imports `@/db` and `drizzle-orm` from inside `application/` (lines 24, 39), which `hexagonal-lite.md:63` explicitly forbids. The one existing read-path migration does not fit the written write-path rule — the read path needs its own row in that table before anyone migrates a second file into it.

**Checker's notes (assessmentHolds: true):** 24 of 28 recomputed counts match exactly, including every number the argument rests on (132:22 app read/write split, the per-op breakdown, 101 `page.tsx`, 12 non-page, 0 `layout.tsx`, 9 cron writers, exactly 1 spine writer, 66/70 `app/actions`, 422 `@/lib/infra` importers with 131 overlapping inline-select, 0 mobile db imports vs 23 `api/v1`). Four corrections, none reversing the recommendation: (1) "18 tables written" was a hit-count, not a distinct-table count — true value 11, and the point (`cronRuns` dominates) is unweakened; (2) colocated `actions.ts`/`action.ts` db-touchers is 7 not 5 — two reads were missed, strengthening the "route-convention globs miss files" warning; (3) `api/v1` db-issuing files is 6 not 7 — `profile/payload.ts` issues zero db ops and should be counted as an already-migrated consumer, which is the strongest single piece of evidence for the recommendation's C-norm, not part of the problem set; (4) only 1 biome scope bans `@/db` (not 2) — verified directly in `biome.json`, and the load-bearing conclusion ("nothing fences app/ or lib/") is unaffected.
