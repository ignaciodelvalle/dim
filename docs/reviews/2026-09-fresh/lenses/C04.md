### The UTC schedule does not slice an Argentine day in half
- **Property**: The daily bag fires at 04:00 UTC = 01:00 ART, the same calendar date in both zones (Argentina is UTC-3 with no DST), so no job's "today" window straddles a boundary; slot materialization converts local clock times through the rule's stored timezone rather than the server's.
- **Path**: `lib/infra/slot-materialization.ts:148`
- **Guard claimed**: `scripts/check-timezone-dates.ts` (`pnpm lint:timezone`, in the verify chain) — **refuter found this guard does NOT cover the property** (`guardVerified: false`): it only bans bare `toLocaleDateString`/`toLocaleString`/`Intl.DateTimeFormat` calls lacking a `timeZone` option, a formatting ratchet with an empty baseline. It cannot fire on `setUTCHours`, `toISOString().slice(0,10)`, `date_trunc`, or a `vercel.json` schedule edit. The nearer candidate, `cron-schedule-single-source.test.ts:82-84`, only pins `vercel.json` against the registry constant relatively — moving both schedules to the same new UTC hour together would stay green while breaking the UTC-date==ART-date premise.
- **Why still VERIFIED as healthy**: the property is true at this SHA by direct arithmetic and is more load-bearing than a decorative note — `slot-materialization.ts:102-113` enumerates days with `setUTCHours(0,0,0,0)`/`getUTCDate()` before interpreting each date string in the rule's timezone, and `lib/infra/notifications.ts:238` / `lib/infra/outreach-reminders.ts:145` key dedupe buckets off `now.toISOString().slice(0,10)` — all correct only because the run fires at 04:00 UTC.
- **What would break it**: shifting the dispatcher's schedule into the 00:00-03:00 UTC window (00:00-00:59 ART previous day) would flip several `today` computations to the wrong calendar date, and nothing in the current fence set would catch that shift.
- **Evidence**: `vercel.json:5-10` (`0 3 * * *`, `0 4 * * *`); `slot-materialization.ts:102-113,148,163-164`; `notifications.ts:238`; `outreach-reminders.ts:145`.

### Claimed healthy, not verified

**Double invocation of the daily dispatcher does not double-deliver or double-write** (claimed path: `app/api/cron/drain-outbox/route.ts:78`) — **REFUTED** by the correctness refuter, high confidence:

`drain-outbox` does NOT claim rows the way the healthy claim states. The `FOR UPDATE SKIP LOCKED` lock is scoped to a transaction containing only a `SELECT`, which then commits (`route.ts:83-96`; the route's own comment at 80-81 says the lock "releases on commit before per-row delivery runs"). Rows keep `status='pending'` through the entire delivery loop (103-133); `deliverOutboxRow` runs at 106 and status only advances to `delivered` at 109-117, AFTER the side effect. A second overlapping run entering during that window re-selects the same still-`pending` rows — nothing is locked, so `SKIP LOCKED` skips nothing — and re-delivers them. The window is the full batch loop (`BATCH_SIZE` 50 with per-row network delivery), not a microsecond race. The repo demonstrates the correct pattern elsewhere and names this exact failure mode: `surveillance-repository.ts:494-515` claims via a single `UPDATE ... SET status='processing' ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`, commented "status='processing' prevents re-claim after the lock releases." So of the "two delivery drains" in the original claim, only `process_eno_queue` is disjoint-safe; `drain-outbox` is not. `deliverOutboxRow` has no idempotency key (plain-inserts an `audit_log` row, `outbox-drainer.ts:86-100`), and no advisory lock exists on `/api/cron/daily` itself. The `materialize_slots` half of the original claim IS solid (`onConflictDoNothing` on a real unique index, `db/schema.ts:2942-2944`) — only the drain-outbox half is false. The cited guard (`__tests__/cron-drain-outbox-route.test.ts`) has no overlap/disjointness test; "SKIP LOCKED" appears in it only as a comment inside a mock.

This item is **not** carried forward as healthy; it is effectively subsumed by the refutation above (no separate finding ID was assigned in this run's data — flag for the next audit to file it as a real finding, since it describes a live double-delivery hazard on `drain-outbox`).
