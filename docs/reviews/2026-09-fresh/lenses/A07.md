**A07-2 — Avatar upload enforces its 2 MB cap on a caller-supplied NUMBER, never on the blob it actually uploads**
`src/modules/pets/application/profile/upload-avatar.ts:31` · kind: bug
Exploit: any authenticated account calls the `uploadAvatarAction` Server Action (`app/actions/profile.ts:58-65`) with a real 100 MB `fileBlob` but a spoofed `fileSize: 1`. The zod schema at `upload-avatar.ts:31` validates the caller-supplied NUMBER against `MAX_FILE_SIZE_BYTES`, not `fileBlob.size` — line 62 reads the real blob and line 63 uploads it via `createAdminClient()` (service role), bypassing the `auth.uid() = owner` bucket policy entirely. The `avatars` bucket declares no `file_size_limit` (migration 0171). `mimeType` is likewise trusted with no magic-byte check, unlike `lib/infra/uploads.ts:71`. MED not HIGH: bucket is private, so this is unbounded storage write, not disclosure or escalation.
Evidence: `rg -n "fileSize|mimeType|fileBlob" app/actions/profile.ts src/modules/pets/application/profile/upload-avatar.ts` → `profile.ts:58-62` (four independent wire fields); `upload-avatar.ts:31` (`fileSize: z.number().max(MAX_FILE_SIZE_BYTES, ...)`); `:62-63` (`fileBlob.arrayBuffer()` then `.upload(storagePath, arrayBuffer, { contentType: mimeType })`); `0171_avatars_bucket.sql:22-24` (bucket insert, no size/mime columns).
Refuter notes: 3/3 confirmed high confidence. One refuter corrected the overstated ceiling — `next.config`'s `serverActions.bodySizeLimit` is `"50mb"`, not the finding's implied 100 MB, so the real ceiling is ~25x the declared cap rather than unbounded; immaterial to the defect.
Fix: derive both `fileSize` and `mimeType` from the blob inside `uploadAvatarForUser`/`defaultStorageUpload` — check `fileBlob.size` and run bytes through `detectRasterMime` (already used at `pet-photo-upload.ts:389`), dropping `fileName.split('.').pop()`.
fixClass: code-sdd

## Nits

- `lib/domain/revocation-evidence-path.ts:38` — `extractExtension`'s docblock says "lowercase-safe file extension" but the function never lowercases (returns `fileName.slice(dot + 1)` verbatim); the returned string is unbounded and may contain `/`. Traversal is structurally impossible (the segment after the LAST dot cannot itself contain a dot), so the bound is accidental, not asserted — the docblock's claim is simply false.
- `lib/infra/welfare-uploads.ts:206` — `inferExtension` has the same shape: extension comes from the client filename ahead of the mime fallback, so the mime-derived branches (208-217) are dead for any filename containing a dot. Same accidental traversal bound. Deriving from the validated mime first (the rule `lib/media/validate.ts:67-70` states and `lib/infra/uploads.ts:84` follows) would make the bound deliberate.
- `lib/infra/pet-photo-upload.ts:421` — `confirmPetPhoto` writes `uploadedByUserId` as the CONFIRMING user, which need not be the account that minted the ticket and PUT the bytes: any co-holder of the same pet can confirm another co-holder's staged object. Not a security issue (both hold photo-write), but the attachments row's attribution can be wrong and nothing documents this.
- `src/modules/welfare/actions.ts:757` — the MPF export bakes 7-day signed evidence URLs into a PDF that travels to the fiscal authority — an unauthenticated bearer link to cruelty-complaint evidence that outlives any authorization check. This is a deliberate, DISCLOSED decision (`lib/analytics/welfare-exports.ts:653` prints the validity note inside the PDF itself), recorded here so a future reader doesn't rediscover it as a surprise.
