## Healthy — verified solid

### Owner phone and last-seen location are never fetched on a non-disclosing lost credential
- **Property**: when `disclosePhoneWhenLost` / `discloseLastLocationWhenLost` are off, the loader substitutes a SQL `null` literal into the `SELECT` list, so the value never leaves Postgres; the ownership join carries `role='owner'` so a temporary caretaker's phone cannot ride the titular owner's consent onto the public page.
- **Path**: `src/modules/pets/application/read/load-public-credential.ts:237` (also `:229-230`, `:281-282`, `:327`).
- **Guard**: `__tests__/public-token-pii-contract.test.tsx` and `__tests__/api-v1-credential-route.test.ts` — guard verified **false** on the specific "fetch not render-time redaction" half. The refuter found the fetch-gating property is real (also confirmed independently on the sibling `encontre/page.tsx:142-161` path, and on the `role='owner'` predicate via `__tests__/public-credential-owner-row-role.test.ts:108`), but no test would fail if the conditional projections were collapsed into a plain `.select()` — the named guards test the render-time gate, not the SQL projection.
- **What would break it**: collapsing the two conditional SELECT branches into one `.select()` of the whole row (the payload builder still gates at render, but the PII is one JSX line away in process memory); or dropping the `role='owner'` predicate at `:259-261`.
- **Evidence**: `rg -n "disclosePhoneWhenLost|discloseLastLocationWhenLost|locationLat" src/modules/pets/application/read/load-public-credential.ts` → `237: phone: showPhone ? profiles.phone : sql<string | null>`null``, `281-282`/`327-328` same for lat/lng.

### x-real-ip is not a client-choosable rate-limit key through the edge these limiters run behind
- **Property**: every per-IP ceiling keys on `callerIp()`, which prefers `x-real-ip` and otherwise takes the LAST `x-forwarded-for` hop (never the first, client-supplied one). A rotated-header run against `dim-staging` produced the same ceiling as the fixed-header control (60×401 then 20×429 vs 59×401 then 21×429) — a client-supplied header does not survive Vercel's edge.
- **Path**: `lib/infra/rate-limit.ts:188` (real-ip preference `:196-197`, last-hop walk `:208-211`, measurement `:88-97`, re-run recipe `:121-129`).
- **Guard**: `__tests__/caller-ip.test.ts` (`:62-68` pins precedence and asserts `not.toBe("FAKE-ATTACKER-IP")`) plus the recorded staging measurement. Guard verified **true** — a `split(",")[0]` regression would turn that assertion red.
- **What would break it**: exposing the origin without a rewriting proxy in front of it (then `callerIp` believes whatever arrives), or re-keying onto the last-XFF-hop branch against a CDN that hasn't been measured — the file itself flags that branch as UNVERIFIED against any CDN (`:56-59`, `:133-139`) rather than overclaiming it.
- **Evidence**: `rg -n "const realIp|segments.length - 1|DO NOT take the first" lib/infra/rate-limit.ts` → `196`, `208`; `playwright.staging.config.ts:23`: "THE x-real-ip HEADER BELOW IS INERT AGAINST STAGING. Measured 2026-08-26."

**A03-1 — `no-store` allowlist has drifted from the force-dynamic public set (`/t/[serial]`, `/refugios*`), and its fence asserts the drift is correct**
- Kind: fence-gap. Path: `lib/infra/public-cache-policy.ts:40`.
- Exploit: an owner revokes a physical chapa (or the pet is soft-deleted). `/t/{serial}` is `force-dynamic` but middleware never stamps `Cache-Control: no-store` on it, so a shared/CDN cache may retain the previous 307 or status page — the exact class this policy file exists to prevent. Bounded: the redirect target `/p/{token}` IS no-store and 404s for an erased pet. Same gap on `/refugios/[orgToken]`, which additionally renders a viewer-dependent variant (`page.tsx:118-128`, admin/coordinator banner) — the cookie-dependent-variant hazard the policy already names for `/casos/`. The fence's own test (`__tests__/public-cache-policy.test.ts:47`) positively asserts `/refugios` is NOT no-store, while the file's docblock (`:6-7`) claims the allowlist "covers every privacy-sensitive public route."
- Evidence:
  ```
  rg -ln 'export const dynamic = "force-dynamic"' 'app/(public)' app/libreta app/r
  → app/(public)/t/[serial]/page.tsx, app/(public)/refugios/[orgToken]/page.tsx, app/(public)/refugios/page.tsx (uncovered)
  rg -n '/refugios' __tests__/public-cache-policy.test.ts
  → 47: "/refugios", inside it.each(...)("does NOT mark %s as no-store")
  NO_STORE_PREFIXES = /p/, /libreta/compartir/, /adoptar, /casos/, /denuncias/codigo/, /denuncias/seguimiento; NO_STORE_EXACT = /perdidas
  ```
- Refuter notes: all 3 refuters CONFIRMED (high/medium/medium confidence). One caveat raised by two refuters: `force-dynamic` and `no-store` are not strictly the same property (the policy file itself explains the distinction), and `refugios/page.tsx:19-21` uses `force-dynamic` purely because CI builds have no DB — so a naive tree-derived fence would over-fire. That caveat is why severity stays MED, not why the finding is wrong.
- Fix: derive the fence from the tree instead of a hand list (walk `app/(public)/**` + `app/libreta/**` + `app/r/**` for `force-dynamic`, assert each route satisfies `isPublicNoStoreRoute` with an explicit exemption map). Then add `/t/` and `/refugios` to `NO_STORE_PREFIXES`, or move the two `/refugios` pages off `force-dynamic` if they're genuinely cacheable.
- fixClass: code-sdd. priorStatus: new.

**A03-2 — Anonymous write actions are keyed `(endpoint:token, ip)` only — no IP-less per-token global cap**
- Kind: security. Path: `src/modules/pets/application/sighting/report-pet-sighting.ts:145`.
- Exploit: an attacker holding one known lost-pet token (posters, WhatsApp, the `/perdidas` listing) can hand-post any of three anonymous server actions. Precedent for the missing pattern already exists in-repo (`submit-org-contact.ts:99-100` pairs a per-IP bucket with an IP-less `org_contact_org:${org.id}` daily cap), which strengthens rather than weakens the finding.
- Evidence:
  ```
  report-pet-sighting.ts:145  enforceRateLimit(`sighting:${publicToken}`, ip, {maxPerMinute:1, maxPerHour:10})
  notify-owner-of-found-pet.ts:100  enforceRateLimit(`found_notify:${publicToken}`, ip, {1,10})
  encontre/action.ts:162  enforceRateLimit(`finder_possession:${publicToken}`, ip, {1,10})

  ```
- Refuter notes: all 3 refuters CONFIRMED at high confidence. `notify-owner-of-found-pet.ts:187` confirms the reportId is a fresh `randomUUID()` per submission with a comment stating dedupe is deliberately absent, so nothing downstream caps fan-out. Impact bounded to in-app notification rows (`createNotificationsBulk`), not paid email/SMS.
- Fix: add a second, IP-less bucket keyed on the token alone alongside the existing per-`(token,ip)` one in all three call sites, e.g. `enforceRateLimit(\`sighting_token:${publicToken}\`, publicToken, { maxPerHour: 30 })`.

**A03-3 — Two anonymous token-resolving routes carry no per-IP budget at all: `/refugios/[orgToken]` and `/r/invite/[token]`**
- Kind: security. Path: `app/(public)/refugios/[orgToken]/page.tsx:107`.
- Exploit: a script GETs `/refugios/{orgToken}` in a loop from one address; each hit fires three unthrottled queries (org profile + a 24-row adoption listing join + 9 public offerings) with zero limiter in the path, and none of the query modules use `unstable_cache`. `/refugios` publishes every org's `publicToken` (`refugios/page.tsx:158-160`), so no guessing is needed — the directory hands over the whole target list. `/r/invite/{token}` is the same shape: one unthrottled indexed read per attacker-supplied token, with four distinguishable outcome branches (not-found / accepted / revoked / expired) — an unbounded state oracle. - Evidence:

**A03-G1 — `robots.txt` `Disallow: /r` blocks the entire public shelter directory the sitemap advertises**
- Kind: bug. Path: `app/robots.ts:83`.
- Exploit: robots.txt `Disallow` values are prefix matches (RFC 9309 §2.2.2), not path-segment matches. The bare `"/r"` entry therefore matches `/refugios` and `/refugios/{orgToken}` in addition to its intended target `/r/invite/{token}`. `app/sitemap.ts:88-93` emits `deepLinkUrl(SITE_URL,"shelter",{orgToken})` = `/refugios/{token}` for every verified `shelter`/`rescue_network` at priority 0.8 (`packages/contract/src/links/deep-link-map.ts:144`), so Googlebot fetches the sitemap, sees N shelter URLs, then is told it may not crawl any of them — the file's own comment three lines earlier (`:44`) names `/refugios` as deliberately open. The redundant sibling entries `"/registro"` (:66) and `"/recuperar"` (:68) — both already covered by a segment-aware `/r` — show the author was thinking in segments, not prefixes. No data exposure, no access-boundary change: MED not HIGH.
- Evidence:
  ```
  rg -n '"/(r|t|libreta)",' app/robots.ts
  → 81: "/libreta", 82: "/t", 83: "/r"
  rg -n 'shelter:' packages/contract/src/links/deep-link-map.ts
  → 144: shelter: { webPath: "/refugios/:orgToken", appPath: null, access: "public" }
  ls app/(public)/refugios → [orgToken]  loading.tsx  page.tsx
  ```
- Refuter notes: 3/3 CONFIRMED (high confidence each) — reproduce, correctness, impact lenses all independently verified the prefix-match mechanics and the sitemap/robots collision.
- Fix: change `"/r"` → `"/r/"` and `"/t"` → `"/t/"` (segment-terminated), then add a test cross-checking every URL shape `app/sitemap.ts` can emit against `robots()`'s disallow array for accidental prefix matches.
- fixClass: code-sdd. priorStatus: new. lenses: [A03].

- Evidence:
