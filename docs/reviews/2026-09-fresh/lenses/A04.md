## Healthy — verified solid

### Both login budgets are spent before GoTrue, and the fence asserts their relationship rather than their digits
- Property: an attacker cannot get a fresh login budget by switching transport, and cannot invert the IP/email derivation by editing one number — both `/api/v1` and the web form call one `login()` that spends the per-IP then the per-email bucket BEFORE any credential check, and a test pins `LOGIN_IP_LIMIT === LOGIN_EMAIL_LIMIT × LOGIN_SIMULTANEOUS_CALLERS` on both windows.
- Path: `src/modules/auth/application/login.ts:160`
- Guard: `__tests__/api-v1-auth-routes.test.ts` — refuter verified the guard is real and non-vacuous (high confidence).
- What would break it: a new transport calling `signInWithPassword` directly, or raising `LOGIN_EMAIL_LIMIT` without `LOGIN_IP_LIMIT` (the fence catches the second; nothing catches the first).
- Evidence: `login.ts:161` `await enforceRateLimit("auth_login_ip", input.callerIp, LOGIN_IP_LIMIT);` `:162` `await enforceRateLimit("auth_login_email", emailRateLimitKey(email), LOGIN_EMAIL_LIMIT);` `:168` `const auth = await deps.auth();` — the client is constructed only after both budgets pass. `__tests__/api-v1-auth-routes.test.ts:322-323` `expect(LOGIN_IP_LIMIT.maxPerMinute).toBe((LOGIN_EMAIL_LIMIT.maxPerMinute ?? 0) * LOGIN_SIMULTANEOUS_CALLERS)`.

### The password-reset request cannot enumerate accounts, because there is nothing to branch on
- Property: an address with an account and one without take a byte-identical path out of `requestPasswordReset` — the GoTrue result is never bound to a name, the success arm carries no fields at all, and the only two error codes are `missing_fields` and `rate_limited`.
- Path: `src/modules/auth/application/password-reset/request-password-reset.ts:160`
- Guard: `__tests__/password-reset.test.ts` — refuter verified (high confidence).

### The mobile 401 policy is one refresh and one retry, and it never retries a shift expiry
- Property: a native client cannot be driven into a refresh loop and cannot outlive an account refusal — `auth_expired` refreshes once and retries once, `session_shift_expired` signs out with no refresh attempt at all, and a 403 `account_deactivated`/`account_erased` ends the session immediately.
- Path: `apps/mobile/src/api/client.ts:254`
- Guard: `apps/mobile/src/api/client.test.ts` — refuter verified (high confidence).

- Property: the refresh token is never written to AsyncStorage, is stored with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` (excluded from device backup / does not travel to a new phone), and the app has no deep-link session-ingestion path — `detectSessionInUrl` is off and nothing calls `Linking.getInitialURL`/`addEventListener` to feed a session.

### MED

**A04-1** — `updatePasswordAction` accepts ANY live session, not a recovery session — password change with no current-password proof
- Kind: bug · Path: `src/modules/auth/application/password-reset/update-password.ts:23`
- Exploit: an attacker holding a live session cookie for victim V (shared/kiosk browser, unlocked laptop, copied cookie) calls `getUser()` at `:23`, which proves only that SOME session exists — no AAL/amr/recovery-type check anywhere in the file, and `secure_password_change = false` removes GoTrue's reauth backstop too. `:43 updateUser({password})` succeeds with no current-password proof; `:58 signOut({scope:"others"})` then evicts V from every other device.
- Evidence: `rg -n "recovery session|getUser|updateUser\({ password" update-password.ts` → `:23 } = await supabase.auth.getUser();` `:43 await supabase.auth.updateUser({ password });`. `supabase/config.toml:223 secure_password_change = false`. `rg currentPassword app src components` → no matches.
- Refuter notes: correctness — refuted:false, high; reproduce — refuted:false, high; impact — refuted:false, high (all three confirm; the file header's claim of "re-verifies recovery session" is contradicted by the code).
- Fix: require proof of the recovery flow (AAL/amr check) or of the current password (re-verify via `signInWithPassword`); flip `secure_password_change` to `true` on config.toml and the hosted project; correct the file's misleading header.
- fixClass: code-sdd

**A04-2** — `logoutAction` discards `signOut`'s error — the exact auth-js failure `/turno-vencido` and the mobile client handle terminally
- Kind: convention · Path: `src/modules/auth/application/logout.ts:11`
- Exploit: GoTrue returns 5xx (or the connection drops) while a user clicks "Cerrar sesión" — auth-js 2.105.4's `_signOut` returns `{error}` without reaching `_removeSession()` unless the failure is 401/403/404/session-missing, so SSR cookies survive; `logout.ts:11` binds nothing and redirects to `/` anyway. `logoutAndReturnAction` (`:24`) is the worse instance: its only caller is the public finder flow `FinderInPossessionForm.tsx` on `/p/{token}/encontre`, whose whole purpose is signing out on a stranger's phone.
- Evidence: `logout.ts:11` `await supabase.auth.signOut();` `:24` same, unbound. `turno-vencido/route.ts:109` `const { error } = await supabase.auth.signOut({ scope: "global" });` `:133 if (error) return shiftSignOutFailedResponse();`. `supabase-auth.ts:71-79` documents the same auth-js failure mode.
- Refuter notes: correctness — refuted:false, high; reproduce — refuted:false, high; **impact — refuted:true, medium** — `app/page.tsx:51-86` redirects a still-live user straight back into their portal (a visibly failed logout, not a silent one), and `FinderInPossessionForm.tsx:145-166` re-renders the "Tenés una sesión iniciada" banner on the return page — impact lens argues the failure is loud, not silent, and the only genuinely silent redirect target (deactivated-institutional fallthrough) is separately locked out by `live-user.ts:324`. Kept CONFIRMED MED on the strength of the two confirming votes and the real un-refuted mechanism (unchecked error, wrong convention vs. the repo's own established pattern); the impact vote is recorded as a dissent, not a majority refutation.
- Fix: bind the result in both functions and stop redirecting on failure, mirroring `turno-vencido/route.ts:133`; if a redirect must happen, delete `sb-*` cookies explicitly first (web equivalent of mobile's `dropLocalSession()`).
- fixClass: code-sdd

**A04-3** — Recovery OTP is 6 digits valid for a full hour, and code redemption has no app-level budget
- Kind: security · Path: `supabase/config.toml:227`
- Exploit: the app's two recovery budgets (`PASSWORD_RESET_EMAIL_LIMIT` 5/hr, `PASSWORD_RESET_IP_LIMIT` 12/min) bound only issuance (`request-password-reset.ts:143-148`). Redemption goes device→GoTrue directly (`session-store.ts:622`, anon key ships in the binary), bypassing `enforceRateLimit` entirely. Search space 10^6, window 3600s, only ceiling is GoTrue's `token_verifications=30/5min/IP`; a ~1400-address botnet covers half the space inside one code's lifetime, success = full account takeover.
- Evidence: `supabase/config.toml:204 token_verifications = 30` `:227 otp_length = 6` `:229 otp_expiry = 3600`. `session-store.ts:622-625 client.auth.verifyOtp({ email, token, type: "recovery" })` — no `enforceRateLimit` in the file. `session-store.ts:509-518` documents the gap itself: "the brute-force bound on a six-digit code is GoTrue's token_verifications ... not ours."
- Refuter notes: correctness — refuted:false, medium (hosted-project ceiling unverifiable, code-side claim fully confirmed); reproduce — refuted:false, medium; impact — refuted:false, high.
- Fix: shorten `otp_expiry` to ~600s (confirm on hosted project too, config.toml is dev-only); raise `otp_length` to 8; longer-term, redeem through `/api/v1` so it spends a per-email budget like every other auth act.
- fixClass: po-decision
