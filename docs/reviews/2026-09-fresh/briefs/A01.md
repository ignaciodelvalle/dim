## Method

1. **Enumerate the surface.**
   - Server actions: `rg -l '"use server"' app src` — every export in each matched file is an independently-addressable action.
   - Route handlers: `rg -l '^export async function (GET|POST|PUT|PATCH|DELETE)' app --glob 'route.ts'`
   - RSC pages/layouts under the five app groups named in scope.
   - Service-role sites: `rg -n 'SERVICE_ROLE|serviceRole|service_role' app src lib scripts`

2. **One command per claim.** Every assertion in your output needs a `rg -n` or targeted `Read` that a stranger can re-run verbatim. Quote the actual output, never a remembered number.

3. **Count with the fence's own method.** For `scripts/check-authz-guards.ts`: read the rule definitions (guard lists, globs, regexes) directly, don't infer behavior from the docstring. For each rule, ask: what pattern makes an offender pass silently? Then search the tree for that pattern (e.g. a bare `auth.getUser()` call, a mutation on a table the rule's regex doesn't match).

4. **Exploit or mutation per finding.** State the concrete actor, their starting state, the exact call sequence, and the resulting effect. For a fence-gap finding (no live offender), state the smallest hypothetical addition that would slip through, and confirm no live offender exists today with a repo-wide grep.

5. **At least 3 healthy items, each with a verified guard.** A healthy claim needs: the property in one sentence, path:line, what mechanism guards it (a fence script, a compile-time type, a hand-written check), and what would break it if changed. Don't just assert "this looks fine" — trace the actual guard chain from entry point to the check that would refuse the request, and if a fence is claimed, confirm by reading the fence's own rule that it actually covers this call site (not just that a fence with a plausible name exists).

6. **Triage every prior**, not just the ones that look interesting — an old finding marked still-open two audits running is worth surfacing even if unglamorous.

7. **Severity rubric:**
   - CRITICAL: cross-tenant data exposure or privilege escalation reachable by an unauthenticated or low-privilege actor with no precondition beyond having any account.
   - HIGH: privilege/access anomaly for an authenticated actor acting as themselves (no cross-tenant reach, no privilege gain) — e.g. a control that should apply doesn't; or a narrower cross-tenant leak requiring a specific precondition.
   - MED: cross-jurisdiction/cross-tenant leak of aggregate/non-PII data, or a fence gap with no live offender but a plausible near-term one, or a disarmed non-PII abuse control.
   - LOW: debt/convention/fence-gap with no live offender and low likelihood of one appearing, or a report-only mechanism that never enforces.
