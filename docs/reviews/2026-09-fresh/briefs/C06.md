# C06 brief — Build, deploy and environment matrix

Reproduce the C06 lens (`docs/reviews/2026-09-fresh/lenses/C06.md`) by hand, or hand this file to a fresh read-only agent that has not seen the original workflow.

## Contract

- Read-only: never open `.env*` files (name env keys, never values), never run `pnpm`/`npm`/`vercel` commands that build, deploy, migrate, or write to any database — local or remote. `rg`/`sed -n`/`git show`/`node -e` for static inspection only.
- Every claim needs an `evidenceCmd` and its literal output pasted in, plus a repo-relative path with forward slashes and a line number.
- State positives as facts with their guard, not hedges — "X is true, guarded by Y at path:line" — same evidentiary bar as a finding.
- No number from memory. Re-run the command, quote the output.

## Scope and lens

Map the deploy matrix with commands, covering six areas:

1. **Vercel** — `vercel.json` (crons, functions config), the Next build, which env vars the app requires at build vs runtime (open `lib/env*` or the zod env schema, list keys by NAME ONLY), how staging vs production differ (`NEXT_PUBLIC_SITE_URL` handling — known trap: an empty string makes the hero QR encode a relative URL).
2. **EAS** — `apps/mobile/eas.json` profiles (development/preview/production), `apps/mobile/app.config.ts`: which secrets/ids are read from env vs hardcoded, whether the API base URL per profile points at staging or production, whether Sentry DSN handling is safe.
3. **Supabase remotes** — how migrations reach staging and production (`package.json` scripts `deploy:staging` / `migrate`, `scripts/*migrate*`); the known fact that production is behind staging by migrations 0209+0210 and PO-gated; whether anything in CI could apply a migration to a remote without a human.
4. **GitHub workflows** — enumerate `.github/workflows/*.yml`; for each: trigger, what it runs, whether it's required/advisory, which secrets it needs. Check `scripts/check-ci-lint-parity.ts` — does CI run the same fences as `pnpm verify` (`package.json:79`), and is `pnpm test:verified` (`package.json:126`) what CI actually runs (vs plain `pnpm test`).
5. **Seed hygiene** — `scripts/check-seed-hygiene.ts`, `check-seed-ids.ts`, `check-catalog-drift.ts`, `hygiene-rules.ts`: what they assert, whether wired (`rg` the `lint:*` keys in `package.json` and `.github/workflows`), whether a demo seed can reach a remote.
6. **`scripts/qa-up.ps1`** — what it checks and assumes (ports, containers, build freshness), whether any step could touch a remote.

Deliverable: at least three verified properties an official-facing deck could cite about deploy discipline (e.g. migrations forward-only and immutable with the fence that pins it; CI gate composition; secrets never in the repo — name the fence).

## Priors

None — this is the first lens to cover build/deploy/environment (see `whatsNew` in the original lens data: Expo/EAS Android pilot, mobile Sentry, `verify:mobile`, signed-upload buckets, scheduled-fence-refs fence, and `test:verified` replacing `pnpm test` as the DoD are all new since the last review pass and previously uncovered).

## Method

1. Read `vercel.json`, `package.json` scripts (`verify`, `deploy:staging`, `db:*`, `test:verified`, `verify:mobile`), and the zod env schema (`lib/infra/env.ts`) — list env var NAMES only.
2. Read `apps/mobile/eas.json`, `apps/mobile/app.config.ts`, `apps/mobile/src/config/api.ts`; `rg -c '"env"' apps/mobile/eas.json` to check per-profile env blocks; check `git show <sha>:apps/mobile/src/config/api.ts` for the default API base.
3. Read `scripts/migrate.ts` in full — dotenv load order, `--strict` drift handling, `Destino: [LOCAL]`/`[REMOTO]` banner. Cross-check against `docs/ops/staging-deploy.md` for the documented invocation procedure (does it set `DATABASE_URL` before running `deploy:staging`?). Read `scripts/_db-target.ts` and `scripts/db-bootstrap.ts` for the `--allow-remote` writer guard.
4. `rg --files .github/workflows` then read each workflow file for triggers, `run:` steps, `secrets.*`/`vars.*` references, and `DATABASE_URL` values (local vs `secrets.STAGING_DATABASE_URL`). Cross-reference every `ref:` pin against `scripts/check-scheduled-fence-refs.ts`'s `DEPLOY_REF` constant and its history comment.
5. Verify CI/DoD parity mechanically:
   ```
   node -e "const p=require('./package.json');const g=p.scripts.verify.split('&&').map(s=>s.trim().replace(/^pnpm\s+/,'')).filter(n=>n.startsWith('lint:')||n.startsWith('verify:'));const w=require('fs').readFileSync('.github/workflows/ci.yml','utf8').split('\n').map(l=>l.replace(/#.*$/,'')).join('\n');const inCi=new Set([...w.matchAll(/pnpm\s+((?:lint|verify):[a-z0-9-]+)/g)].map(m=>m[1]));console.log(g.length, g.filter(n=>!inCi.has(n)))"
   ```
   Confirm CI's test step is `pnpm test:verified -- --coverage` (not `pnpm test`), and read `scripts/run-verified-suite.ts` + (ideally, unlike this lens) `scripts/check-suite-coverage.ts` to confirm the verdict is derived from a filesystem census of test files, not from vitest's own report.
6. Read seed-hygiene scripts and `rg` their `lint:*` wiring in `package.json` and `.github/workflows/ci.yml`.
7. Read `scripts/qa-up.ps1` in full; `rg` for any non-`localhost` host, `https://`, `vercel`, or secret literal.
8. For every candidate finding or healthy claim, write the exact command and paste its literal output — never approximate a count or line number.
9. Send every finding and every healthy claim through one independent correctness refuter (5 for a CRITICAL survivor). A refuter must re-run the evidence command independently, actively search for a mitigating guard the finder may have missed, and either confirm, refute (with its own reason and evidence), or reduce severity with justification.

## Output

Produce two files:
- `docs/reviews/2026-09-fresh/lenses/C06.md` — fixed section order: Ground truth, Verdict, Healthy — verified solid (+ Claimed healthy, not verified), Findings (CONFIRMED, grouped by severity), Refuted (+ Unverified), Prior triage, Nits, Coverage (+ collapsed filesRead list).
- `docs/reviews/2026-09-fresh/briefs/C06.md` — this file.

### Severity rubric

- **CRITICAL** — a remote (staging or production) database, secret, or user-facing credential surface can be corrupted, exposed, or bypassed with no human in the loop.
- **HIGH** — a deploy or migration path can ship broken or untested code to a remote environment under normal (non-malicious) operator use, or a guard that should be fatal is silently advisory in a path that matters.
- **MED** — a real gap exists (a check that doesn't run, a default that's the wrong shape) but is bounded by an adjacent guard, requires an uncommon precondition, or affects a non-production environment only.
- **LOW** — doc/reality drift, a convention breach, or a gap closed by a second independent mechanism (e.g. `actions/checkout` failing loudly on a bad ref).
- **NIT** — worth fixing, not worth a severity-graded finding.

When a refuter is torn between two severities, they vote the lower one and say why in the reason field. A finding is CONFIRMED only if not refuted; its `finalSeverity` is the refuter's vote, which may differ from the finder's initial `severity`.
