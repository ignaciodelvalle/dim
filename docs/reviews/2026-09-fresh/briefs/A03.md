## Method

1. **Enumerate the public surface.** `rg -ln "export const dynamic|export async function GET|export async function POST" "app/(public)" app/r "app/api/v1"` plus a directory listing of `app/(public)/**` and `app/r/**`. For each route found, classify: read-only page, write action (form/server action), or JSON API.

2. **Per claim, run the exact command and quote the exact output.** Never paraphrase a grep result — copy the lines. Every finding and every healthy claim needs an `evidenceCmd` + literal `evidenceOutput`.

3. **Throttle coverage, counted with the fence's own method.** Read `__tests__/public-token-throttle-coverage.test.ts` first — it already enumerates every DIM-credential-token resolver and requires a guard. For each finding candidate, check: (a) does `enforceRateLimit` (or `isPublicTokenReadThrottled`) appear in the route file at all — `rg -n "enforceRateLimit|isPublicTokenReadThrottled" <file>`; (b) is it a single window or two (`maxPerMinute` + `maxPerHour`); (c) does it run BEFORE the first DB read that could be expensive or disclose an existence oracle, or after; (d) is the key `(endpoint, ip)`, `(endpoint:token, ip)`, or IP-less (`(endpoint:entity, "any")`) — the last is a *stronger* pattern used deliberately in `src/modules/organizations/submit-org-contact.ts:99-100`, worth checking as precedent for any "should have an IP-less cap" finding.

4. **Check whether the route is even inside an existing fence's scope.** `__tests__/public-token-throttle-coverage.test.ts` scopes itself to files resolving a public *credential* token (its `LOOKUP`/`DOOR` markers, e.g. `publicPetByToken(`, `findPetByPublicToken(`, `lookupPublicCredential(`) — routes resolving a different kind of token (org token, invite token, tag serial) can be completely outside its scan and therefore unguarded with no fence noticing. Read the fence's own marker list before concluding "there must be a fence for this."

5. **Cache headers.** Read `lib/infra/public-cache-policy.ts` for the allowlist (`NO_STORE_PREFIXES`, `NO_STORE_EXACT`, `isPublicNoStoreRoute`) and find its one consumer with `rg -n "isPublicNoStoreRoute|NO_STORE_CACHE_CONTROL"`. Then independently enumerate every `force-dynamic` public page with `rg -ln 'export const dynamic = "force-dynamic"' "app/(public)" app/libreta app/r` and diff the two lists by hand — the allowlist is hand-written and can silently drift from the force-dynamic set (this is exactly what A03-1 found). Also check for viewer-dependent (cookie/session-gated) render variants on any force-dynamic-but-cacheable-looking route — those need no-store even without PII, because a CDN could serve one visitor's variant to another.

6. **Fail-open vs fail-closed.** Read the limiter primitive `lib/infra/rate-limit.ts` (`consumeOrThrow`) to establish what it does on infra failure (throw, and whether that throw is a `RateLimitError` or a plain `Error` — callers must be able to distinguish "over budget" from "limiter broke"). Then `rg -n "instanceof RateLimitError" -B3 -A3` across every route calling `enforceRateLimit` to see which catch blocks swallow the plain-`Error` case and `return true` (allow) vs rethrow (deny). Do not assume fail-open is confined to any one surface — check each call site independently; this lens found it is an `/api/v1`-wide convention, documented per-call-site, not a credential-only exception.

7. **IP-key derivation behind Vercel.** Read `callerIp()` in `lib/infra/rate-limit.ts` — does it prefer `x-real-ip`, and how does it walk `x-forwarded-for` (first hop = client-supplied/spoofable, last hop = edge-appended)? Check for a positive-control measurement already on file (`playwright.staging.config.ts` comments, or a recorded staging experiment) before proposing a new live probe — re-running a rate-limit probe against a shared staging environment should be a deliberate, announced action, not a routine brief step.

8. **Severity rubric** (apply consistently):
   - **CRITICAL**: unauthenticated PII disclosure at scale, or an oracle that fully bypasses auth/ownership.
   - **HIGH**: PII disclosure bounded to one record/session but exploitable without rate limiting, or a fail-open that removes a real control.
   - **MED**: missing/weak throttle or cache-header gap on a non-PII-disclosing surface, or a fence-scope gap that hides a real (but bounded) exposure; a fence that positively asserts an incorrect property.
   - **LOW**: convention drift, missing defense-in-depth with no demonstrated path to harm, hygiene.
   - Note when a caveat (token-space size, requiring a second factor like session-matched email, existing bounded blast radius) is what keeps a finding at MED instead of HIGH — state it explicitly rather than silently downgrading.

9. **Exploit or mutation per finding.** Write the concrete attacker action and its bounded/unbounded consequence — not "this could be a problem" but "N requests from M addresses yields X rows/notifications against one victim record," with the actual numbers from the code (rate limit values, token alphabet size, etc.).

10. **Healthy items — minimum 3, each with a verifiable guard.** For every candidate "this is solid," name the exact test file/line that would fail if the property broke, and try to break it: comment out the gating condition mentally and ask which named test goes red. If none would — mark `healthyStatus: NOT VERIFIED` and say what does exist (e.g. a payload-level guard, not a fetch-level one) rather than dropping the claim. Distinguish "the underlying security property holds" from "the claim as stated is literally true" — these can differ (see the DEN-second-generator case in this lens).

11. **Triage every prior finding** against the current SHA with a fresh command, not the old evidence. `closed` needs a positive citation of the fix in place; `still-open` needs the same gap reproduced; `not-reproducible` needs an explanation of why the prior claim no longer applies (route removed, refactored away, etc.).

## Gap round

A completeness-critic pass found that no file at the `app/` root was ever opened in the base pass: A03's own `areasRead` lists `app/(public)`, `app/actions`, `app/api`, `app/r`, `app/libreta` and `middleware.ts`, but never `app/sitemap.ts`, `app/robots.ts` or `app/manifest.ts`. Confirm this gap yourself before treating the rest of this section as settled:

```
ls app/*.ts app/*.tsx
→ error.tsx  global-error.tsx  layout.tsx  manifest.ts  not-found.tsx  page.tsx  robots.ts  sitemap.ts
rg -n "throttle|rateLimit|consume|budget" app/sitemap.ts app/robots.ts
→ only an unrelated comment in robots.ts
```

**Why it matters**: the credential model rests on the public token being unguessable (`CLAUDE.md` invariant 1). A crawlable, unthrottled route that lists thousands of tokens per request converts unguessable into published, and simultaneously hands an anonymous caller three uncapped DB queries.

**Additional scope for this round** — read `app/sitemap.ts` in full (97 lines; it declares `export const dynamic = "force-dynamic"` at :13 and runs three concurrent DB queries at :51-65 with `SITEMAP_PAGE_SIZE = 5000` at :34) and answer:

1. Is `/sitemap.xml` reachable by an anonymous caller, and does `middleware.ts`'s matcher exempt it?
2. Does it emit the full public-token list of every pet in `status='lost'` and every adoption listing (`deepLinkUrl(SITE_URL, "credential", { publicToken })` at :82) — an offline enumeration of the credential namespace?
3. What does Next's per-request caching actually do for a `force-dynamic` metadata route on Vercel, and can a caller bypass it with a query string or `Cache-Control`, turning three 5000-row queries into a DB-load amplifier? (This is a read-only audit — do not probe a live deployment to answer it; state what the repo declares, and flag the gap between "declared" and "observed" explicitly.)
4. Does `app/robots.ts` advertise `/sitemap.xml`, and does it disallow anything that would otherwise be crawled? Check `Disallow` values as PATH-PREFIX matches per RFC 9309 §2.2.2, not path-segment matches — a bare `"/r"` matches `/refugios` too, not just the intended `/r/invite/{token}`.

Also re-check the base pass's healthy claim that a repo-walking fence proves every public-token resolver carries a guard: does that fence (`scripts/check-db-budget.ts`, `__tests__/public-token-throttle-coverage.test.ts`) have any rule that would ever look at a metadata route that only *emits* tokens rather than *resolving* one? Read each fence's own scope statement/marker list before concluding either way — this round found one fence structurally out-of-scope by design (token-resolution only) and the other in-scope but under-triggering (a fan-out-count threshold missed by one element), which are different defects with different fixes.

Extend Method step 3's throttle-coverage check and step 5's cache-header check to `app/sitemap.ts`, `app/robots.ts`, and `app/manifest.ts`, and extend Method step 10 (healthy items) to the sitemap's payload shape — check field-by-field whether PII the underlying query selects (name, phone, location, microchip) reaches the emitted `{url, lastModified, changeFrequency, priority}` object literal, and whether any test would fail if a field were added to it.
