## Method

1. **Enumerate the surface.** Grep-first, then read:
   - `rg -n "jurisdiction" lib/domain lib/infra lib/metrics lib/analytics --type ts -l` to find every jurisdiction-aware module.
   - `rg -n "requireCapability|requireCapabilityForOrgToken" src/modules app/actions -l` for org-tenant capability checks.
   - `rg -n "orgToken" app/org --type tsx -l` for every org-portal page.
   - `rg -n "province|locality" app/gob --type tsx -l` for every gob sub-view taking a jurisdiction axis.
   - `rg -n "resolvePanoramaRequestScope|jurisdictionScopeContains|jurisdictionPairClause|narrowGovtScope" src/modules/panorama app/api/panorama -l` for the Panorama guard surface.
   - Read `package.json`'s `verify` script chain to find every `lint:scope*`, `lint:authz*`, `lint:locality*` fence, then read each fence script named there.

2. **One command per claim.** Every finding and healthy item below has an `evidenceCmd` — run it verbatim (adjust only for OS path syntax) and diff the output against the `evidenceOutput` quoted in the lens file. A mismatch means either the code moved (re-locate by name) or the claim needs revision.

3. **Count with the fence's own method where one exists.** For fence-related findings (A10-4), read the fence script's own docstring/header for what it claims to guard, then check what it actually queries (`from(...)`, table names) — do not infer coverage from the test's title alone.

4. **Exploit or mutation per finding.** For a security/bug finding, write the concrete request or mutation an attacker/operator would perform (who, what input, what response). For a fence-gap finding, write the concrete out-of-band mutation the fence would miss. Do this BEFORE reading the finder's `exploitOrMutation` field, then compare.

5. **At least 3 healthy items with a verified guard.** For each healthy claim, don't just read the property — try to break it: vary the input the way an attacker would (crafted query param, off-catalog spelling, cross-org token), and confirm the guarded code path actually rejects/narrows it. Note explicitly whether you could locate and exercise the guard test/CHECK named in `guardedBy`, or whether you're only confirming by code inspection (mark `guardVerified: true`/`false` accordingly — inspection-only is a legitimate but weaker result).

6. **Triage every prior.** For each of the 54 prior items in the three result files, classify as:
   - `closed` — the code now visibly implements the fix (cite the current line).
   - `still-open` — the described gap still reproduces at the current SHA.
   - `not-reproducible` — could not verify in either direction within the read budget (say why — file not opened, prior source truncated, etc).

7. **Severity rubric** (apply per finding):
   - CRITICAL — unauthenticated or trivially-reachable cross-tenant/cross-jurisdiction data exposure or mutation, or privilege escalation with no further gate.
   - HIGH — reachable by an authenticated-but-out-of-scope actor, no further approval/two-person gate stops the write; or a fence silently reports green over a claimed universal property.
   - MED — reachable but bounded by a second gate (approval workflow, two-person rule, narrow field exposure), or a fence gap whose blast radius is limited to an off-app/manual mutation path.
   - LOW — latent (requires an unusual input path, e.g. a legacy URL route, or a stale/off-catalog value) or a hygiene/parity issue with no live exploit demonstrated.
   - Any finding rated MED bumps the file's overall verdict to at least SOLID WITH FINDINGS; any CONFIRMED CRITICAL/HIGH bumps it to AT RISK.

## Gap round

A completeness-critic pass found that `src/modules/alerts` (7 non-test files, 691 lines) had zero reads in the main pass's coverage matrix, despite being the product's only alert/threshold machinery and writing ungeneralized per-locality counts to a durable table. This gap scope covers that module end to end, plus the two areas the main pass's `areasNotReached` had already flagged as adjacent and unopened: `/gob/suscripciones` (one of 13 unopened gob sub-views) and `lib/metrics/context.ts` / `lib/analytics/dashboards/_scope.ts` (unaudited scope layers).

**Start here:** `src/modules/alerts/application/firings/record-firings.ts:43-52` — every breach inserts an `alert_firings` row carrying `observedValue: String(ev.currentValue ?? 0)` together with `jurisdictionProvince`/`jurisdictionLocality` — a RAW count for a single locality persisted with no k-anon suppression, the exact shape `lib/metrics`'s `SuppressedCells` mechanism exists to prevent. Also note `:24` — the fleet cron sweep evaluates every subscription under a hardcoded `{ role: "admin" }` universal scope regardless of actual ownership, safe only while writes stay admin-only (verify that assumption holds at every door).

**Then follow the readers:**
