## Method

1. **Enumerate the surface.** List every migration touching `pet_events`, `case_events`, or the `credential_scanned` carve-out: `rg -ln "pet_events|case_events" db/migrations`. Read the LAST migration that `CREATE OR REPLACE`s each trigger function — that's the live definition, not the first one you find. Cross-check against `db/triggers.sql` (the bootstrap-time consolidated definitions) for drift between the two.
2. **One command per claim, evidence pasted verbatim.** For every claim you make, run the exact `rg`/`ls`/`read` command, quote its real output (line numbers included), and cite `path:line`. Never state a count or an absence from memory — rerun the command.
3. **The override GUC.** Find every setter of `app.allow_event_mutation`, `app.allow_event_mutation_actor`, `app.allow_audit_mutation(_actor)`, `app.allow_scan_purge` in the whole repo (not just `lib/` — check `scripts/`, `e2e/`, migrations). For each: is it `set local`/`is_local: true` (transaction-scoped, safe) or a bare `SET`/`is_local: false` (session-scoped, a pooled-connection leak)? Also check every RPC/SECURITY DEFINER function that sets these GUCs (`rg -n "allow_event_mutation" db/migrations`) — RPCs are a production code path, not just app code.
4. **Every UPDATE/DELETE against the event tables.** Sweep both dialects — Drizzle builder (`.delete(petEvents)`, `.update(petEvents)`) and raw SQL (`DELETE FROM pet_events`, `UPDATE pet_events`, including schema-qualified `public.pet_events` spellings) — across `app/`, `src/`, `lib/`, non-test files. For each hit found: is it inside a transaction holding the override GUC? Is the trigger's own predicate at least as strict as the app's WHERE clause?
5. **Audit-row content.** For every override branch (`pet_events_mutation_override`, `case_events_mutation_override`, `scan_event_purged`), read the `jsonb_build_object` that becomes the audit payload: which columns does it capture, and for UPDATE, does `coalesce(new.X, old.X)` resolve to the pre- or post-image? Does the actor GUC get validated as non-null before the mutation proceeds, or only logged?
6. **The cache/drift contract.** Read `lib/infra/rederive-pet-cache.ts` fully: the `CHECKED_COLUMNS` map (or equivalent), and the excluded-columns list (comment or code — note which). Compare against `getTableColumns(pets)` — is there ANY fitness test enumerating the real table columns against this map, or does the map only check itself? Then find every *consumer* of the drift report — the cron (`app/api/cron/reconcile-pet-status/route.ts`), the ops script (`scripts/detect-pet-cache-drift.ts`) — and for each, which subset of columns actually feeds an alert, versus which are computed but silently dropped. Check whether the ops script is wired into any `package.json` script, CI workflow, or `vercel.json` cron — `rg -n "detect-pet-cache-drift" package.json .github/workflows/*.yml vercel.json`.
7. **Cache-reads-as-log check.** For each cache column identified in step 6, grep its production readers (`rg -n "<columnName>" app src lib` minus tests) and check whether any dashboard/KPI/choropleth groups or filters on it directly, versus deriving from the event spine.
8. **Findings.** Every finding needs a concrete exploit or mutation-testing step (delete this guard clause / add this call site / flip this flag — what observably breaks, or fails to break, in the test suite or in production). State severity using the rubric below and justify it against the actual reachable actor (an internal operator with a direct DB connection is a materially different bar than an unauthenticated public-page visitor).
9. **Healthy — minimum 3.** For each candidate healthy property: state the property precisely, then try to break it — search for the counter-pattern the property claims doesn't exist (session-scoped setter, missing trigger on a later migration, a second unguarded mutation path) across the WHOLE repo, not just the obvious directory. Name the guard (test file + line, or fence script + how it's wired into `pnpm verify`/CI) and independently verify the guard actually asserts the property (read the test, don't just cite its filename) — mark `guardVerified: true/false`.
10. **Prior triage — every one.** For each prior finding, re-run its original evidence command (or the closest equivalent) at the current SHA and classify: closed (fixed), still-open (reproduces), or not-reproducible (the underlying code no longer exists in a form the claim applies to).

**Severity rubric:**
- **CRITICAL** — an unauthenticated actor, or any authenticated actor without special privilege, can silently rewrite or destroy ledger history with no trace.
- **HIGH** — a privileged-but-not-DBA actor (e.g. an app-level admin role) can do the same, or the append-only guarantee is entirely absent on a live deploy path (not just under-tested).
- **MED** — the guarantee holds today but is unguarded against regression (fence-gap), or an audited/accountable escape hatch exists but with a real gap in its accountability or reconstructability, reachable only by an actor who already holds elevated DB access.
- **LOW** — hygiene, dead code, or a defence-in-depth gap where every current caller already validates correctly.

Minimum bar before calling a finding CONFIRMED in your own head (this brief has no separate refuter pass — if you are the only reader, hold yourself to this): you must be able to point to the exact line that would need to change for the exploit to work, and state what — if anything — in the current test suite or fence would catch that change. If nothing would catch it, say so explicitly; that absence is itself part of the finding.
