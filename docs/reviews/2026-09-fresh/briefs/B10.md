## Method

1. **Reproduce the line-count and baseline commands above exactly.** If the numbers differ from what's quoted, the files have changed since this brief was written — use your own numbers and note the drift.
2. **Read `scripts/check-file-size.ts` in full.** Does it read `scripts/file-size-baseline.json` as a ceiling (`actual > baseline` fails) or an exact pin (`actual !== baseline` fails)? Is it wired into `pnpm verify` (`rg -n "check-file-size" package.json`)? If it's an exact pin and PanoramaConsole.tsx is already 22 lines over, either the fence is not actually running, or it silently passed a mismatch it should have caught — read the comparison logic character by character before concluding either way.
3. **Full baseline inventory.** Read `scripts/file-size-baseline.json` in full (verified 14 lines — small enough to read whole). List every pinned file and its budget; for the 2-3 largest, recompute `wc -l` and diff against the pin.
4. **Route-weight fence.** Read `scripts/check-route-weight.ts` in full — what does it measure (bundle size per route? file count? both?) and against what budget. Is it wired into `pnpm verify` (`rg -n "lint:route-weight" package.json`) — note it appears in the `verify` script AFTER `pnpm build` per the script's own ordering (`rg -n "route-weight" package.json`), meaning it likely inspects build output, not source — confirm this by reading what path it globs.
5. **Why these two files are this large.** Skim (don't deep-read) `PanoramaConsole.tsx` and `SituationalMap.tsx` for structure — are they doing one cohesive job at scale, or multiple unrelated concerns that could split along the module boundaries B01 investigates? Note this as context for a `debt` finding, not a hard requirement to fully review 8,200 combined lines.
6. **Exploit or mutation per finding.** For the baseline-drift finding, state precisely: does the NEXT commit that adds even one line to `PanoramaConsole.tsx` fail `pnpm verify`, or does the fence's comparison direction mean it silently never will again until someone manually re-pins it?
7. **At least 3 healthy items.** Candidates: `SituationalMap.tsx`'s exact baseline match (verified above), the existence of the baseline mechanism itself (vs. no size discipline at all), any other pinned file with a healthy margin.

Produce a JSON object (or equivalent structured notes) with these top-level keys:

- **findings**: array of `{id: "B10-n", title, severity: CRITICAL|HIGH|MED|LOW, kind: fence-gap|debt|convention, canonRule?, path, line, evidenceCmd, evidenceOutput(≤400ch), exploitOrMutation, fix(one line), fixClass: doc-fix|code-sdd|fence-candidate|po-decision, priorId?, priorStatus?}`
- **healthy**: array of `{title, property, path, line, evidenceCmd, evidenceOutput, whatWouldBreakIt, guardedBy, guardVerified: bool}` — minimum 3
- **priorTriage**: `[]` (no priors this run)
- **nits**: array of `{path, line, note}`
- **coverage**: `{filesRead: [...], areasNotReached: [...]}`

**Severity rubric**:
- CRITICAL: not applicable to this lens by default — a performance/size gap rarely reaches CRITICAL without a demonstrated production outage; only use it if a route-weight or bundle-size defect is shown to break a real user flow.
- HIGH: the baseline fence is proven to have a comparison-direction bug that makes it never fail on growth (a false-green class, per CLAUDE.md's "false-green gate" HIGH criterion).
- MED: a real budget drift (like the 22-line PanoramaConsole.tsx gap) with the fence's actual behavior confirmed but not yet a proven false-green; a large file with a plausible-but-undemonstrated maintainability cost.
- LOW: hygiene, a file approaching but not exceeding its budget.

This brief is meant to be runnable by hand by someone who has not seen this workflow — if a step above is ambiguous without prior context, treat that as a bug in the brief and resolve it the most literal way rather than guessing at intent.
