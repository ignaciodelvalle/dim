## Method

1. **Enum inventory.** Read the `CaseStatus` and welfare-report status enums directly in `db/schema.ts` (don't trust a doc's paraphrase) — list every value for both.
2. **Conflation sweep.** `rg -n "CaseStatus|caseStatus" src/modules/welfare lib` and vice versa — any function that accepts/compares a case status value where a welfare-report status was expected (or vice versa) without an explicit mapping.
3. **Append-only enforcement on `case_events`.** `rg -n "CREATE TRIGGER" db/migrations/*.sql | rg -i case` — confirm a trigger exists blocking UPDATE/DELETE on `case_events` analogous to `pet_events`' `0127_pet_events_append_only.sql`. If none exists, that is itself a finding — state the exploit (a case mutation that rewrites history with no audit trail).
4. **Illegal transitions.** Read every state-transition function in `src/modules/cases/domain/` and `src/modules/welfare/domain/` — build the actual transition table each function permits and compare against the domain rule (closed→open, merged→anything should be rejected). Construct the concrete call sequence for any transition that should be rejected but isn't.
5. **Custody-dispute party handling.** Read `src/modules/custody-disputes/domain/` and `application/` — can a party be added/removed such that a dispute ends up with zero or duplicate parties, and does the transfer-completion path (also read `src/modules/return-to-owner/`) require dispute resolution before releasing custody?
6. **Decomiso (seizure) flow.** Read `src/modules/decomiso/domain/` and `application/` in full (this is the newest, least-audited module here) — what triggers a seizure, what state it puts the pet/case in, and whether it's reversible through a documented path.
7. **Denuncia reference-code resolver.** Read `src/modules/welfare/domain/reference-code.ts` — how is the code generated (collision risk, guessability) and where is it consumed (public resolver? cross-reference A03's public-surface scope if useful, but this lens's job is domain correctness, not throttle coverage).
8. **Moderation flow.** Trace one full moderation decision from intake to resolution across whatever files implement it — does every mutation in the path emit a corresponding `case_events`/`pet_events` row, or can a moderation action change state with no ledger entry (the event-bypass class 13 was built to find)?
9. **Exploit or mutation per finding.** State the concrete actor + call sequence that reaches an illegal state or an unlogged mutation.
10. **At least 3 healthy items**, each with the guard traced (a domain-layer rejection, a DB constraint, a trigger) and verified.
11. **Triage every prior.**

## Output

Produce a JSON object (or equivalent structured notes) with these top-level keys:

- **findings**: array of `{id: "C01-n", title, severity: CRITICAL|HIGH|MED|LOW, kind: bug|security|convention, canonRule?, path, line, evidenceCmd, evidenceOutput(≤400ch), exploitOrMutation, fix(one line), fixClass: doc-fix|code-sdd|fence-candidate|po-decision, priorId?, priorStatus?}`
- **healthy**: array of `{title, property, path, line, evidenceCmd, evidenceOutput, whatWouldBreakIt, guardedBy, guardVerified: bool}` — minimum 3
- **priorTriage**: array of `{priorId, status: closed|still-open|not-reproducible, evidence}` covering every prior
- **nits**: array of `{path, line, note}`
- **coverage**: `{filesRead: [...], areasNotReached: [...]}`

**Severity rubric**:
- CRITICAL: a case/welfare mutation that bypasses the event log entirely with a legal/audit consequence, or an illegal transition (e.g. reopening a closed/merged case) reachable by a normal authenticated actor with no trace.
- HIGH: a custody-dispute or decomiso state that can end up inconsistent (double custody, orphaned dispute) under normal (non-malicious) operator use.
- MED: an enum conflation with a plausible but bounded defect path, a missing append-only trigger with no observed live mutation yet.
- LOW: hygiene, a transition gap with no plausible trigger given the current UI's constraints.

This brief is meant to be runnable by hand by someone who has not seen this workflow — if a step above is ambiguous without prior context, treat that as a bug in the brief and resolve it the most literal way rather than guessing at intent.
