## Method

1. **Enumerate the surface.** List every application-layer use-case under `src/modules/transfers`, `src/modules/rehome`, `src/modules/adoption`, `src/modules/caretakers`, `src/modules/foster`, `src/modules/return-to-owner`, `src/modules/custody-disputes`, `src/modules/decomiso`, plus `src/modules/cases` (dispute escalation lives there) and shared custody primitives in `lib/infra/end-pet-ownerships.ts`. For each transition, identify: initiator check, acceptor/counterparty verification, idempotency guard, locking strategy (advisory lock? row lock? none?), events written, and cache updates (`ownerships` rows, `pets.*` columns).

2. **One command per claim.** Every claim you write down needs an `rg`/`sed -n` command that reproduces it, run fresh — never assert a line number or quoted string from memory. Standard probes for this lens:
   - Counterparty verification: `rg -n 'validateRecipientMatch|matchesEmail|toOwnerId|toOwnerEmail' <file>` then read the domain rule function in full.
   - Confirmation posture: `rg -n 'enable_confirmations' supabase/config.toml`.
   - Locking: `rg -n 'acquirePetAdvisoryLock|pg_advisory_xact_lock|\.for\("update"\)|FOR UPDATE' <file>` — and check whether the SAME custody-relevant read (e.g. "who is the active owner") is locked or a plain SELECT.
   - Idempotency: `rg -n 'expectedStatus|status.*pending|updatedRows === 0|won:' <repository file>` — does the UPDATE fold the precondition into its WHERE, or read-then-write?
   - Notification fan-out: `rg -n 'notifyCaretakersOfHandoff' --glob '!*.test.ts'` — is the discard/consumption of a repository's returned handoff data checked at every call site, not just one?
   - custody-disputes infra question: `fd . src/modules/custody-disputes -e ts` (confirm no `infrastructure/` dir) then `rg -n 'from "@/db"' src/modules/custody-disputes/application/*.ts` and compare to the same sweep across all modules: `rg -l 'from "@/db"' --glob 'src/modules/*/application/*.ts' | sed 's|src/modules/\([^/]*\)/.*|\1|' | sort | uniq -c` — is it module-specific or repo-wide?
   - Ownership cache drift: `rg -n 'KNOWN GAP|SCOPED TO' scripts/detect-pet-cache-drift.ts` and compare `CHECKED_COLUMNS` in `lib/infra/rederive-pet-cache.ts` (columns) against ownership-role coverage in the drift script (which roles get a detector).
   - Public credential mid-transition: read the `(public)/p/[publicToken]` render path and confirm what it shows while a transfer/caretaker-grant is pending vs. accepted.

3. **Count with the fence's method.** For any claim about "how many files/modules do X", run the actual `rg -l` sweep and count — don't estimate. If the repo has a fence script relevant to the claim (e.g. `scripts/check-dependency-direction.ts` for module-boundary claims), read what axis IT checks before claiming a gap — a fence that checks axis A says nothing about axis B.

4. **Exploit or mutation per finding.** Every finding needs either a concrete exploit narrative (who does what, in what order, what breaks) or a mutation you'd apply to the code that a real guard should catch and doesn't. State the mutation explicitly if there's no live-data exploit to walk.

5. **>= 3 healthy items, each with a verified guard.** For every "this property holds" claim, name the guard (test file + line range) and actually open it — confirm the guard tests the SAME property being claimed, not an adjacent one. This lens found two cases where the cited guard was for a different concern than the property (see A09's cross-org accept and decomiso items) — always check the guard's actual assertions, not just its filename/existence.

6. **Triage every prior.** For each prior finding, re-run its original evidence command against current code. `closed` needs the specific line/commit that fixed it quoted; `still-open` needs current line numbers; `not-reproducible` needs to say what changed underneath it.

7. **Severity rubric** (apply consistently):
   - CRITICAL: unauthenticated or trivially-forgeable takeover of custody/titularidad, or an event spine write that lies about parties, reachable with no precondition.
   - HIGH: same class of harm but gated behind a real precondition (must know a specific value, target must be in a specific state, a toggle that's off by policy not by code).
   - MED: incorrect behavior with a bounded, non-security blast radius (wrong/missing notification, unattributed event, state disagreement between two records) — not a wrong-role access.
   - LOW: self-documented/declared debt, convention drift with a fence gap, or a lifecycle inconsistency with no exploit path.
