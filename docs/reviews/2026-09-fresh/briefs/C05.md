## Method

1. **Silent-swallow sweep.** `rg -n "catch\s*\(" lib app src/modules -g '*.ts' -g '!*test*' -A2` and spot-check a large sample (at least 30) for a catch block with no `reportError`/`throw`/dead-letter call in its body.
2. **Boot env validation.** Read `lib/infra/env.ts` in full — for each required var, is it required in production but optional locally (fail-closed correctly), or could a missing prod secret slip through with a fallback that masks the gap?
3. **Error boundaries.** Read `app/error.tsx` and `app/global-error.tsx` — do they cover Suspense/async boundaries, or only synchronous render errors? `rg -rn "Suspense" app` to find boundaries with no adjacent error boundary.
4. **Cron failure isolation.** For 3-4 cron routes under `app/api/cron/*`, read the handler — does a thrown error inside one job stop the whole route, and is the failure recorded anywhere durable (not just a 500 response Vercel logs and forgets)?
5. **Dead-letter drain confirmation.** Cross-check with C03's scope (avoid duplicate findings — this lens's angle is "is a cron failure EVER recoverable," C03's is "is the notification dedupe correct") — confirm a drain job exists and runs on a schedule (`rg -n "drain" .github/workflows app/api/cron`).
6. **`cron-health` teeth.** Read `app/api/cron/cron-health/route.ts` in full. Does it query actual job-completion timestamps/status rows, or just return 200 unconditionally (a health check that can't fail is the vacuity class B11 also looks for — flag it here if found, don't wait for B11).
7. **Web/mobile telemetry asymmetry.** Confirm via the paths above; read `apps/mobile/src/observability/sentry.ts` for a `beforeSend`/scrubbing hook and check what fields it strips before upload.
8. **The 3 a.m. trace.** Pick ONE real cron job (e.g. the daily dispatcher or a specific sub-job), and write out the concrete failure path: throw → catch → log/dead-letter/nothing → any human notification → recovery mechanism (manual rerun? automatic retry next day?).
9. **Unhandled rejections.** `rg -n "\.then\(" lib app -g '!*test*'` for any `.then()` chain with no trailing `.catch()`.
10. **Exploit or mutation per finding.** State the concrete failure scenario and what a human would (or wouldn't) ever see.
11. **At least 3 healthy items**, each with the guard traced and verified.
12. **Triage every prior.**

- **coverage**: `{filesRead: [...], areasNotReached: [...]}`

**Severity rubric**:
- CRITICAL: not typical for this lens — reserve for a silent-swallow that loses a legally/safety-relevant event (a crisis notification, an audit-log write) with zero trace anywhere.
- HIGH: a cron job that can fail silently with no dead-letter/log trace and no human ever finds out (a false-green gate, per CLAUDE.md's HIGH criterion), a `cron-health` that can never report unhealthy.
- MED: a silent-swallow on a non-critical path, boot env validation with a fallback that masks a genuinely-missing prod secret but with a bounded blast radius, an unhandled rejection with no observed crash.
- LOW: hygiene, a documented (not silent) telemetry asymmetry.

This brief is meant to be runnable by hand by someone who has not seen this workflow — if a step above is ambiguous without prior context, treat that as a bug in the brief and resolve it the most literal way rather than guessing at intent.
