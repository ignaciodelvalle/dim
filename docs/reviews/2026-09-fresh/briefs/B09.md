## Method

1. **Enumerate hot write paths.** `rg -n '\bdb\.insert\(' src/modules lib -g '*.ts' -g '!*test*'` for event inserts and other direct inserts on the concurrency-sensitive tables (`pet_events`, `case_events`, `ownerships`, appointment/turno tables).
2. **Idempotency-Key handling.** For each of the 5 confirmed `app/api/v1/*` routes above, read the full handler: is the key checked against a stored record BEFORE the write executes (so a retry returns the prior result) or only used for logging? `rg -n "idempotency" db/schema.ts` for a backing table/column.
3. **Outbox correctness.** Read `lib/events/event-outbox-enqueue.ts` and `lib/infra/outbox-drainer.ts` in full. Does the drainer claim rows with `SELECT ... FOR UPDATE SKIP LOCKED` (or equivalent), and does the status-advancing write happen INSIDE the same lock scope as the claim — the counter-example pattern to check for is a claim-then-commit followed by a SEPARATE later update, which lets a second concurrent drain re-claim the same row once the first lock releases.
4. **Ownership transfer.** Read `src/modules/transfers/application/**` for the two-phase transfer flow (also see `docs/reviews/briefs/audit-transfercustody-2phase.md`/`docs/reviews/results/audit-transfercustody-2phase.md` if present for prior coverage of this exact flow) — can two concurrent accept/propose calls both succeed and produce two live ownership records for the same pet?
5. **Lost-mode toggle.** Read `src/modules/lost/infrastructure/**` (and any `application/`/`domain/` files that exist per B01's shape audit) — is toggling lost-mode guarded by a `WHERE status = <expected>` compare-and-swap, or a plain unconditional `UPDATE`?
6. **Turnos double-booking.** `rg -rln "turno" src/modules apps/mobile/src/turnos` — find the slot-booking write and confirm a unique constraint or a locked check-then-write prevents two concurrent bookings of the same slot.
7. **TOCTOU sweep.** For each write path found in step 1, check whether the preceding read (a `SELECT` to decide the write) and the write itself run in the SAME transaction with a row lock, or as two separate round-trips with no lock — the latter is a TOCTOU gap.
8. **Exploit or mutation per finding.** State the concrete two-concurrent-request scenario and its resulting bad state (duplicate event, double-booked slot, ownership split-brain).
9. **At least 3 healthy items**, each with a verified guard (a unique constraint, a `FOR UPDATE`, an idempotency table) traced from the write site to the constraint definition.
10. **Triage every prior.**

**Severity rubric**:
- CRITICAL: a race that can double-transfer ownership or double-insert an append-only event with a legal/compliance effect, reachable by a normal retry (not a crafted attack).
- HIGH: a TOCTOU gap on a security- or custody-relevant write with a demonstrated concurrent-request reproduction, an outbox claim that can double-drain.
- MED: a race with a bounded, self-correcting effect (e.g. a harmless duplicate notification), a missing idempotency check on a low-frequency retry path.
- LOW: a theoretical race with no plausible trigger given current traffic/retry patterns, hygiene.
