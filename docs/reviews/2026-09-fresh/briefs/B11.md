## Method

1. **Reconcile the fence count** with the three commands above; state your own total and the discrepancy with "74" explicitly as a nit or doc-drift finding on the plan itself (not a code defect).
2. **Unwired-script sweep.** For every file in `ls scripts/check-*.ts`, `rg -n "<basename-without-check->" package.json` (e.g. for `check-pg-net-exposure.ts` search variants of `pg-net`) to find its `lint:*` entry, if any. List every script with zero matches — this is the authoritative unwired list, not an assumption from two examples.
3. **Vacuity check.** For 6-8 sampled fences (mix of old and new, security-relevant and cosmetic), read the actual assertion logic and ask: is there any input that makes this ALWAYS pass regardless of the property it claims to check (e.g. an empty-array `.every()` that vacuously passes, a try/catch that swallows the assertion failure)? This is the exact class CLAUDE.md's own text warns about ("two fences exit 0 while proving nothing" — `docs/agents/recommendations-2026-08-30.md` §2, read that section for the two examples already found, then find independently whether either is still vacuous at this SHA).
4. **Floor vs exact-pin audit.** `rg -n "toBeGreaterThanOrEqual|>=|\.length >" __tests__ scripts/check-*.ts` for count-based assertions — for each, determine whether a regression (fewer items than expected) would be caught (exact pin or `toBe`) or silently tolerated (a floor that only catches growth stopping, not shrinkage) — cross-reference against `docs/agents/recommendations-2026-08-30.md` §3 ("floors loosen in silence; ceilings do not") for the pattern already identified.
5. **Text-anchor fragility.** For 3-5 fences that check SQL/DB properties (RLS, triggers, SECURITY DEFINER), determine whether they parse the actual compiled migration SQL or grep for text patterns that a semantically-equivalent-but-differently-worded migration would evade (e.g. `CREATE POLICY` with different whitespace/casing, or a policy dropped and recreated under a new name that a name-based check misses — the exact class `migration-applied-is-not-closed` already documents for one case; check for others).
6. **`check-ci-lint-parity` teeth.** Read the script in full; verify it fails when a `lint:*` script exists in `package.json`'s `verify` chain but is absent from `.github/workflows/ci.yml` (or vice versa) — construct the hypothetical offending diff mentally and confirm the script's regex/parsing would actually catch it.
7. **Unwired vs wired-but-toothless.** For `check-pg-net-exposure.ts` and `check-seed-hygiene.ts`, read each in full anyway — even unwired, note what property each WOULD check if wired, since that's directly actionable backlog material (`fixClass: fence-candidate`).
8. **Exploit or mutation per finding.** For a vacuous-fence finding, construct the smallest code change that should fail the fence and show it doesn't. For an unwired-script finding, state the concrete violation that ships unnoticed today.
9. **At least 3 healthy items** — fences with real teeth, verified by reading the assertion and confirming a constructed violation would fail it.

- MED: a non-security fence is vacuous or unwired with a plausible but bounded consequence, `check-pg-net-exposure`/`check-seed-hygiene` being unwired (real gap, bounded scope).
