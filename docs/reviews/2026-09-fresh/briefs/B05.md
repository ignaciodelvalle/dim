## Method

1. **Recount the migration set** with the command above, then `ls db/migrations | sort | tail -5` to confirm the highest migration number matches (recount, don't assume 210 means migration `0210`).
2. **Forward-only / idempotency sweep.** `rg -Ln "IF EXISTS|IF NOT EXISTS" db/migrations/*.sql` to find migrations that might lack the guard, then manually confirm each flagged file actually needs one (a pure `INSERT` into a fresh table doesn't).
3. **`CREATE INDEX CONCURRENTLY` transaction hazard.** `rg -l "CREATE INDEX CONCURRENTLY" db/migrations/*.sql` then for each, check for the `-- dim:no-transaction` marker and confirm `scripts/migrate.ts` actually honors that marker (read its parsing logic, don't assume from the comment alone).
4. **Destructive steps.** `rg -ln "DROP (COLUMN|TABLE)|DELETE FROM" db/migrations/*.sql` — for each, read the full migration and classify: guarded (behind an `IF EXISTS`, preceded by a data-migration step, documented as intentional) or unguarded.
5. **SECURITY DEFINER inventory.** `rg -n "SECURITY DEFINER" db/migrations/*.sql` — for each function found, read its body for what it bypasses (RLS) and whether its `search_path` is pinned (an unpinned `search_path` on a SECURITY DEFINER function is a privilege-escalation vector via schema shadowing).
6. **Triggers.** `rg -n "CREATE TRIGGER" db/migrations/*.sql` — enumerate, and for each on `pet_events`/`case_events` cross-check against the append-only invariant (does it block UPDATE/DELETE, and does the audited-override path — `app.allow_event_mutation` — apply consistently).
7. **`scripts/migrate.ts` read in full** — checksum-tracking, `--strict` drift handling, the `[LOCAL]`/`[REMOTO]` destination banner (do not run it — read-only).
8. **`db/schema.ts` vs migration-history drift.** Spot-check 5 tables in `db/schema.ts` against their corresponding `CREATE TABLE`/`ALTER TABLE` migrations for a mismatched column, type, or constraint that `drizzle-kit push` would try to reconcile destructively.
9. **Exploit or mutation per finding.** For a destructive-step finding, state the exact DB state that triggers data loss on a re-run or partial-apply. For a SECURITY DEFINER finding, state the concrete privilege the function grants and to whom.
10. **At least 3 healthy items**, each with a verified guard (the `IF EXISTS` convention, `scripts/migrate.ts`'s checksum check, the append-only trigger itself).
11. **Triage every prior**, re-locating by migration filename since line numbers have shifted.

## Output

Produce a JSON object (or equivalent structured notes) with these top-level keys:

- **findings**: array of `{id: "B05-n", title, severity: CRITICAL|HIGH|MED|LOW, kind: bug|security|debt, canonRule?, path, line, evidenceCmd, evidenceOutput(≤400ch), exploitOrMutation, fix(one line), fixClass: doc-fix|code-sdd|fence-candidate|po-decision, priorId?, priorStatus?}`
- **healthy**: array of `{title, property, path, line, evidenceCmd, evidenceOutput, whatWouldBreakIt, guardedBy, guardVerified: bool}` — minimum 3
- **priorTriage**: array of `{priorId, status: closed|still-open|not-reproducible, evidence}` covering every prior
- **nits**: array of `{path, line, note}`
- **coverage**: `{filesRead: [...], areasNotReached: [...]}`

**Severity rubric**:
- CRITICAL: an unguarded destructive step that can drop append-only history, or a SECURITY DEFINER function with an unpinned `search_path` reachable by a low-privilege role.
- HIGH: a migration that breaks on re-run or partial-apply with no guard, in a way that could brick a deploy.
- MED: a `drizzle-kit push` drift risk, an over-broad SECURITY DEFINER grant with bounded blast radius, an index/trigger gap with a plausible but undemonstrated defect path.
- LOW: hygiene, a stale snapshot file, checksum-tracking gaps with no live exploit.

This brief is meant to be runnable by hand by someone who has not seen this workflow — if a step above is ambiguous without prior context, treat that as a bug in the brief and resolve it the most literal way rather than guessing at intent.
