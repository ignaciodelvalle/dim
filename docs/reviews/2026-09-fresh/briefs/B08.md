## Method

1. **Layering audit.** For each of the 19 `apps/mobile/src/*` subdirectories, note whether it separates view/screen from a view-model/service layer (`rg -l "ViewModel|Screen" apps/mobile/src/<dir>` as a heuristic) — this app doesn't claim hexagonal-lite, so judge against whatever internal convention is actually followed, not the web's pattern; state the convention you find before judging deviations from it.
2. **API client.** Read `apps/mobile/src/config/api.ts` and `apps/mobile/src/config/api.test.ts` in full — base URL resolution per environment, auth header attachment, error/retry handling, and whether the base URL can ever silently resolve to a relative/empty string (the exact class of bug the QR/`NEXT_PUBLIC_SITE_URL` empty-string trap already found on the web side — check for an analogous guard here).
3. **Offline credential cache.** Read every file in `apps/mobile/src/credential/`. What's persisted (AsyncStorage/SecureStore/other), for how long, and is it cleared on logout, token expiry, or a server-side erasure event? Cross-reference against `apps/mobile/src/auth/session-store.ts` (note: currently modified per git status) for the logout/session-clear path.
4. **Deep links.** `rg -rn "Linking\.|expo-linking|scheme" apps/mobile/app.config.ts apps/mobile/src` — enumerate every deep-link route and confirm each validates its params before acting (a deep link is an untrusted external input).
5. **EAS profiles.** Read `apps/mobile/eas.json` in full. For each profile's `env` block, list every key and whether `preview`/`production` point the API base and Sentry DSN at the correct (non-dev) targets. `rg -c '"env"' apps/mobile/eas.json` to confirm which profiles even declare one.
6. **`app.config.ts` secret handling.** Read the file in full. For every `process.env.*` reference, state: is this value baked into the built app bundle (readable by anyone who decompiles the app) or only used by the EAS build process itself? Flag anything secret-shaped (API keys, not just DSNs) that ends up in the former category.
7. **Sentry mobile-only.** `apps/mobile/src/observability/sentry.ts` — confirm scrubbing/PII handling (cross-reference A06's scope if that lens has run; otherwise read independently) and that the DSN wiring here matches what `app.config.ts` produces.
8. **Exploit or mutation per finding.** For a secret-exposure finding, name the concrete extraction method (decompiled APK/IPA, a public EAS build log). For an offline-cache finding, name the device-loss or shared-device scenario that exposes stale credential data.
9. **At least 3 healthy items**, each with a verified guard.

**Severity rubric**:
- CRITICAL: a real API secret (not a public DSN) shipped in the bundle, or an offline credential cache readable by another app/user with no clearing on logout.
- HIGH: a deep link that mutates state without validating its params, an EAS `preview`/`production` profile pointing at the wrong (dev) API base, a DSN/config value that leaks more than intended.
- MED: a layering inconsistency with a plausible maintainability cost, an offline cache with a longer-than-needed TTL but no cross-user exposure.
- LOW: convention drift, hygiene.
