## Method

1. **Enumerate the surface.** Start from:
   - `src/modules/auth/application/*` (login, signup, logout, password-reset/*, revoke-sessions, subject-rights/erase-subject-data)
   - `app/auth/**`, `app/(auth)/**`, `app/actions/password-reset.ts`, `app/api/v1/auth/**`, `app/api/v1/me/privacy/route.ts`
   - `middleware.ts`, `lib/supabase/{middleware,server,bearer}.ts`
   - `lib/infra/{live-user,auth-guards,role-landing,rate-limit,request-cache,operator-shift,miarg-oidc}.ts`
   - `supabase/config.toml` (auth section)
   - `apps/mobile/src/auth/**`, `apps/mobile/src/api/**`, `apps/mobile/src/config/api.ts`, `apps/mobile/eas.json`, `apps/mobile/app.config.ts`
   - `src/modules/pets/application/profile/self-deactivate-personal-account.ts` and any org/govt revocation writers (`rg -l "deactivatedAt|deletedAt" src/modules --glob '*.ts'`)
   Follow imports outward one hop where a claim needs it (e.g. what a use-case's caller actually passes).

2. **One command per claim.** Every finding and every healthy item must carry a `evidenceCmd` that is copy-pasteable (prefer `rg -n "pattern" path` or `rg -n -C N "pattern" path` for context) and an `evidenceOutput` that is the actual output of running it — never paraphrase or reconstruct from memory. Read the full function/file around a hit before asserting behavior; a grep hit alone is not evidence of behavior, only of a string's existence.

3. **Count with the fence's own method, not a guess.** For any claim about how many places do X (e.g. "only one `admin.signOut` call", "no EAS profile declares env"), run the sweep and paste the count/hit-list, not an impression. If a helper name is grep'd, also check for synonyms or wrapper functions that would do the same thing under a different name — a narrow grep concluding "the mechanism is missing" is a known failure mode here (see house convention: search the concept, not one spelling).

4. **Exploit or mutation per finding.** For every finding, state concretely: who is the actor, what precondition do they need (an already-valid session? a botnet? physical device access?), and what do they gain. For a "would this test catch a regression" claim, describe the mutation (what line would you change) and confirm the named test would fail — don't just cite that a test file exists.

5. **At least 3 healthy items, each with a real guard.** A healthy claim needs: the property in one sentence, the path:line implementing it, the specific test/fence file that would break if the property were violated (not just "there's a test file" — name the assertion), and what you tried to break it with (list the payloads/mutations attempted, even the ones that failed — that's what makes "verified" credible instead of asserted).

6. **Triage every prior.** For each numbered item in the prior results file, mark closed / still-open / not-reproducible with a fresh evidence command run against current code — don't trust the prior's own text, re-derive it.

7. **Severity rubric** (apply consistently):
   - **CRITICAL**: unauthenticated or cross-tenant full account takeover / arbitrary data access, no meaningful precondition.
   - **HIGH**: takeover or broad data exposure requiring a narrow precondition (e.g. one clicked link, a common misconfiguration).
   - **MED**: requires an already-elevated precondition (an existing valid session, botnet-scale brute force, a specific race), or weakens a defense without directly granting access.
   - **LOW**: hygiene / defense-in-depth / convention violation with no direct path to unauthorized access; debt items already tracked and reasoned about by the team.
   Refuters may vote a different severity than the finder proposed; the lens write-up should record dissent rather than silently averaging it away.

8. **Refute like an adversary, not a rubber stamp.** For every finding and every healthy claim, at least one independent pass should try to break it: re-run the evidenceCmd verbatim and confirm the output matches; look for an adjacent file, wrapper, or caller that would change the conclusion (e.g. a stricter check one layer up that neutralizes an apparent gap, or a looser one that widens it); check whether the proposed fix is even implementable against the actual library API in use (don't just trust a comment — read the cited SDK behavior). A finding that only reproduces "on paper" but is neutralized by an adjacent guard should be marked REFUTED with the neutralizing evidence quoted, not silently dropped.
