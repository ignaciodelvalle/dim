# A02 brief — RLS and DB privilege

Runnable by hand by anyone who has not seen this workflow. Reproduces the audit in `docs/reviews/2026-09-fresh/lenses/A02.md`.

## Contract

- **Read-only.** Do not run migrations, do not apply anything, do not run `pnpm` against a live DB, and do not modify any file. This is a source-code audit only.
- **SHA check first**: `git rev-parse HEAD` must be `d7dbf25f7` on `main` (or you are auditing a later commit — note the divergence and re-check every path/line cited below before trusting it).
- **Exclusions**: do not run the test suite, do not run `pnpm verify`, do not connect to Supabase (local or remote). Every claim in this lens is derivable from repo source with `rg`/`sed`/reading files — nothing here requires a live database.

## Scope and lens

RLS truth versus snapshots: enumerate policies in `db/migrations` (`rg -n 'CREATE POLICY|ALTER POLICY|ENABLE ROW LEVEL SECURITY|FORCE ROW LEVEL' db/migrations`) and compare with `db/rls.sql` and every `*_rls.sql` snapshot (are they stale decoys that an engineer would trust?). Every `SECURITY DEFINER` function (`rg -n 'SECURITY DEFINER' db/migrations`): `search_path` pinned, caller checks inside the body, and whether it is an oracle returning rows across tenants — trace the 0123 → 0190 → 0199 class to the current state. Tables created after 0130 without RLS or with permissive policies. `storage.objects` policies for every bucket. `GRANT`s to `anon` and `authenticated`. `__tests__/rls/*` as the fence: what it proves and what it cannot.

**What's new since the prior pass** (`docs/reviews/briefs/04-rls.md`): tables and policies added after migration 0130 (turnos, denuncias, decomiso, rehome, signed uploads, subject-rights RPCs 0199-0210); storage policies for the signed-upload buckets; migrations 0209 and 0210 are applied locally and on staging but **not yet on production** — treat anything gated behind them as not-yet-live in prod-only reasoning.

## Priors

- `docs/reviews/results/04-rls.md` — the prior audit's findings, 11 numbered items. Re-triage every one (see Method below); do not assume any prior status without re-checking the current tree.

## Method

1. **Enumerate the policy surface.**
   ```
   rg -n 'CREATE POLICY|ALTER POLICY|ENABLE ROW LEVEL SECURITY|FORCE ROW LEVEL' db/migrations/*.sql
   ```
   Cross-reference every `DROP POLICY` too — a policy created in one migration and dropped in a later one is closed, not live.

2. **Compare against the reference snapshots** — `db/rls.sql`, `db/welfare_rls.sql`, `db/welfare_storage.sql`, `db/cases_rls.sql`, `db/foster_rls.sql`, `db/organizations_rls.sql`, `db/scheduling_rls.sql`, `db/storage.sql`, `db/exports_storage.sql`, `db/revocations_storage.sql`. For each, check:
   - Does its own header say REFERENCE ONLY / no longer applied, or does it instruct "apply by pasting into Supabase Studio"? Both patterns can coexist in the same file — check the whole header, not just the first instruction line you find.
   - Is it actually excluded from `db-bootstrap.ts` / `deploy-provision.ts`? `rg -n '<filename>' scripts/db-bootstrap.ts scripts/deploy-provision.ts`.
   - Does it contain a policy that a later migration `DROP`ped, with no corresponding removal in the snapshot? That is a stale decoy — grep the exact policy name from the migration's `DROP POLICY IF EXISTS "..."` against the snapshot file.

3. **Every `SECURITY DEFINER` function.**
   ```
   rg -n -A2 'SECURITY DEFINER$|LANGUAGE (sql|plpgsql) (STABLE )?SECURITY DEFINER' db/migrations/*.sql
   ```
   For each: (a) is `search_path` pinned (`SET search_path = ...` in the same `CREATE FUNCTION`)? (b) is there a caller check inside the body (`auth.uid()`, role check)? (c) is it `anon`-executable — check `has_function_privilege('anon', p.oid, 'EXECUTE')`-style enumeration in the test fence, or manually trace every `GRANT EXECUTE`/`REVOKE` touching it across migrations in creation order. A function replaced by a later `CREATE OR REPLACE` keeps its ACL unless the replace also reissues GRANT/REVOKE — check whether it does.

4. **Tables after migration 0130 without RLS or with permissive policies.**
   ```
   rg -ni -o 'create table( if not exists)? (public\.)?[a-z_]+' db/migrations/013[1-9]*.sql db/migrations/01[4-9]*.sql db/migrations/02*.sql
   ```
   For each table found, confirm `ENABLE ROW LEVEL SECURITY` appears in the *same* migration file. Then read every `CREATE POLICY` on it and classify: SELECT-only? Does it also carry INSERT/UPDATE/DELETE for the owning role? Do not assume a table is SELECT-only from its first policy — read to the end of its policy block.

5. **`storage.objects` policies for every bucket.**
   ```
   rg -n "create policy" db/storage.sql db/*_storage.sql db/migrations/*.sql
   ```
   For each bucket: is it `public`? Does it set `file_size_limit`/`allowed_mime_types` at the bucket level (`rg -n 'file_size_limit|allowed_mime_types'`)? Is the INSERT/UPDATE/DELETE policy's predicate scoped to the caller (`auth.uid()` in the clause) or just the bucket name?

6. **GRANTs to `anon`/`authenticated`.**
   ```
   rg -n '(GRANT|REVOKE).*(anon|authenticated)' db/migrations/*.sql db/*.sql
   ```
   Table-level default privileges inherited from Supabase (not visible in this repo's SQL) are a real gap — note where reasoning had to substitute for enumeration.

7. **Fence audit — for each file under `__tests__/rls/`**, read the actual assertion body, not just its name or header comment:
   - Is the enumeration catalog-driven (queries `pg_class`/`pg_proc`/`pg_policies` directly) or list-driven (a hardcoded array of names)? A list-driven fence cannot see a new object that forgets to be added to the list.
   - What predicate counts as "unconditional"? (e.g. `write-path-matrix.test.ts`'s `isUnconditional()` — read its exact string comparison; a differently-spelled tautology like `(1=1)` may slip past it.)
   - What `relkind` filter is used? `= 'r'` excludes views (`v`) and materialized views (`m`) — check every RLS fence for this filter, since a bypass through a non-invoker view is invisible to any fence that filters to base tables only.
   - Does the file have a non-vacuity floor (an assertion that the catalog query itself returns a non-empty/expected-size result, so an empty result can't silently mean "nothing found" due to a broken query)?

8. **Count/classify every finding** using the severity rubric below, and write the exploit or mutation for each: for a live issue, the concrete request/actor/payload; for a fence gap, the concrete migration that would slip past undetected.

9. **Find at least 3 healthy properties** with a real guard (a specific test file/assertion that would fail if the property broke), not just "nothing bad found here." State explicitly what would break each one and whether the guard was independently verified (opened and read) or only inferred from its name/header.

10. **Triage every item in `docs/reviews/results/04-rls.md`** — for each numbered prior finding, determine: closed (re-verify the fix is actually in the current migration spine, not just claimed), still-open (cite current evidence), or not-reproducible (state why).

### Severity rubric (used throughout)

- **CRITICAL**: cross-tenant data read/write, auth bypass, secret/credential exposure, or an RLS hole reachable by `anon` with no auth required, touching PII or financial/legal data.
- **HIGH**: an authenticated-but-wrong-role write or forged-provenance write that corrupts an append-only record or a public-facing credential/compliance signal, even when confined to the actor's own tenant; or an `anon`-reachable hole with narrower blast radius than CRITICAL.
- **MED**: a fence gap with no live offending object today (the mechanism is real but nothing currently exploits it), or a doc-drift/decoy file that could mislead an engineer into reintroducing a closed hole, when independent safeguards (exclusion from bootstrap scripts, a second warning) reduce but don't eliminate the risk.
- **LOW**: debt with a narrow/environment-only window (e.g. a partial-migration-apply race that a downstream fence catches loudly), or a stale code comment whose harm is fully carried by a separate finding.

## Output

Produce JSON matching this shape (the lens/brief writer then formats it into the two markdown files):

```json
{
  "findings": [
    {
      "id": "A02-N",
      "title": "...",
      "severity": "CRITICAL|HIGH|MED|LOW",
      "kind": "security|doc-drift|fence-gap|test-theater|debt",
      "path": "repo/relative/path.ts",
      "line": 123,
      "priorId": "optional, if this matches a prior finding number",
      "priorStatus": "still-open|new",
      "evidenceCmd": "the exact command(s) run",
      "evidenceOutput": "the exact output lines, verbatim, with line numbers",
      "exploitOrMutation": "concrete actor+request+payload for a live issue; concrete future migration for a fence gap",
      "fix": "one to a few sentences, concrete",
      "fixClass": "code-sdd|doc-fix|fence-candidate"
    }
  ],
  "healthy": [
    {
      "title": "...",
      "property": "the exact invariant, stated precisely enough to falsify",
      "path": "...",
      "line": 123,
      "guardedBy": "the specific test file/assertion, or 'none' if unguarded",
      "whatWouldBreakIt": "...",
      "evidenceCmd": "...",
      "evidenceOutput": "..."
    }
  ],
  "priorTriage": [
    { "priorId": "1", "status": "closed|still-open|not-reproducible", "evidence": "..." }
  ],
  "nits": [
    { "path": "...", "line": 123, "note": "..." }
  ],
  "coverage": {
    "filesRead": ["..."],
    "areasNotReached": ["with a one-line reason each"]
  }
}
```

Every `findings[].evidenceOutput` and `healthy[].evidenceOutput` must be copy-pasted from an actual command run against the checked-out tree — never reconstructed from memory. Every path is repo-relative with forward slashes. Keep exact line numbers; re-verify them against the current file if the SHA has moved.
