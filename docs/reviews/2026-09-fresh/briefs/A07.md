# A07 — Uploads and storage (brief)

> Reproduces the audit in `docs/reviews/2026-09-fresh/lenses/A07.md`. Runnable by hand, by a human or an external read-only agent, without any prior context from the workflow that produced that file.

## Contract

- **Read-only.** Do not run `pnpm`, do not run tests, do not run builds, do not start Supabase, do not apply migrations. Every claim in the lens file was produced by reading source with `rg`/opening files — never by executing code or a gate.
- **SHA check first.** Confirm you are auditing the same tree the lens claims: `git rev-parse --short=9 HEAD` should read `d7dbf25f7` on branch `main`. If it differs, note the drift before trusting any line number below — line numbers rot.
- **Exclusions**: `pnpm verify` / `pnpm test:verified` status is explicitly out of scope for this lens (see Coverage's last "areas not reached" line) — don't run them to "check" a finding; the findings stand on read evidence alone.

## Scope and lens

> The signed-upload ticket flow (`rg -n 'signed|createSignedUploadUrl|createSignedUrl|upload' src/modules lib/media app/api apps/mobile/src`): who can mint a ticket for which path, TTL, one-time use, content-type and size validation, path traversal in object keys. Bucket inventory from migrations (`rg -n 'storage\.buckets|bucket_id|storage\.objects' db/migrations`) and whether policies are scoped only by bucket_id or also by owner/path. EXIF, HEIC and GPS stripping in `lib/media`. Orphan garbage collection and the cron that runs it. Signed-URL minting for reads: TTL, who can mint for whose object, and whether a signed URL is ever cached or logged. The mobile upload path. Report the status of each RN-4 backlog item B24-B31 (`rg -n 'B2[4-9]|B3[01]' docs/agents docs/mobile docs/superpowers`).

**What's new since any prior pass**: this lens is new in 2026-09 (no prior A07 run exists). Signed uploads landed 2026-08 (uploads-firmados gate); denuncia attachments, mobile photo capture, and the GC cron are all recent additions worth re-checking for drift on a re-run.

## Priors

None. This is A07's first run — the Prior triage table in the lens file is empty by design, not by omission.

## Method

1. **Enumerate the surface.** Run the scope's `rg` commands verbatim (adjust the `docs/` glob if `docs/agents`/`docs/mobile`/`docs/superpowers` have moved). For each upload/signing call site found, note: the bucket, the caller role that reaches it (RLS role vs. service role), and what validates the bytes before they land.
2. **One command per claim.** Every claim in the lens file carries its own `evidenceCmd` — re-run it verbatim before trusting the claim; do not paraphrase a command from memory. If a command's output differs from what's quoted, that claim is stale or wrong — say so rather than silently accepting the lens file.
3. **Count with the fence's own method**, not a impression: for findings, grep the exact claimed line and read ±10 lines of context; for "no callers" or "zero matches" claims, re-run the search — a filtered/piped grep (grep-of-a-grep) is exactly how one of this lens's own claims was refuted (see A07's "Claimed healthy, not verified" section), so always re-run the *unfiltered* command at least once.
4. **Exploit or mutation per finding.** For a `bug`/`convention` finding, construct the concrete actor + inputs that trigger it (who calls what, with what wire values) and trace it through to the actual defect, not just "the validation looks weak." For a `doc-drift` finding, show both halves: what the doc claims, and the code fact that contradicts it.
5. **At least 3 healthy items with a verified guard.** For each "healthy" candidate: state the property in one sentence, name the guard (a test or fence), then try to break the property — a different value, a different actor, a boundary case — and show why it fails. Then check whether the guard would actually catch the break you didn't find, by reading the guard's own assertions (not just its filename) — this is what separates `healthyStatus: VERIFIED` with `guardVerified: true` from a claim that merely wasn't refuted.
6. **Triage every prior.** For a lens with priors, read each one and classify: closed (verify the current code no longer has the defect), still-open (reproduce it fresh), or not-reproducible (state why the prior's claim doesn't hold at this SHA). This lens has none, so this step is a no-op here but must not be skipped on a re-run.
7. **Bucket inventory.** Cross-check every `insert into storage.buckets` in `db/migrations/*.sql` against every `create policy ... on storage.objects` in the same glob plus `db/storage.sql` and `db/revocations_storage.sql`. A bucket with zero caller-facing policies is not automatically safe — it means writes/reads must go entirely through a service-role path, which itself needs auditing (see A07's healthy item 2 for the shape of a solid one, and the "Claimed healthy" item for what an unverified assumption looks like).
8. **RN-4 backlog recount.** Don't trust the backlog doc's own status labels — recount B24-B31 from the code: for each item, find its guard (a fence, a test, or its absence) and state PARTIAL/OPEN/CLOSED from that, not from the doc text. The lens file's B24/B28 correction (doc's title implied "live," body correctly said PARTIAL) shows this catches real drift even within one document.

## Output

Produce a JSON object shaped like this (the lens file above is one rendering of it):

```json
{
  "findings": [
    {
      "id": "string",
      "title": "string",
      "severity": "CRITICAL | HIGH | MED | LOW",
      "kind": "bug | convention | doc-drift | debt | ...",
      "path": "repo-relative/path.ts",
      "line": 0,
      "evidenceCmd": "the exact command run",
      "evidenceOutput": "the exact output, not a paraphrase",
      "exploitOrMutation": "concrete actor + inputs + trace to the defect",
      "fix": "one line",
      "fixClass": "code-sdd | doc-fix | po-decision | ..."
    }
  ],
  "healthy": [
    {
      "title": "string",
      "property": "one sentence, precise enough to falsify",
      "path": "repo-relative/path.ts",
      "line": 0,
      "guardedBy": "test file or fence script, or 'none'",
      "healthyStatus": "VERIFIED | NOT VERIFIED",
      "whatWouldBreakIt": "the attacks tried and why each failed"
    }
  ],
  "priorTriage": [
    { "priorId": "string", "status": "closed | still-open | not-reproducible", "evidence": "string" }
  ],
  "nits": [
    { "path": "repo-relative/path.ts", "line": 0, "note": "string" }
  ],
  "coverage": {
    "filesRead": ["repo-relative/path.ts", "..."],
    "areasNotReached": ["string describing what was skipped and why"]
  }
}
```

**Severity rubric** (as applied in this lens):
- **CRITICAL** — remote/unauthenticated compromise of data or the system, or trivial mass PII disclosure.
- **HIGH** — authenticated privilege escalation, cross-tenant data access, or disclosure of sensitive PII to an unauthorized party.
- **MED** — a real defect exploitable by an already-scoped or already-privileged actor with bounded damage (e.g. unbounded storage writes to a private bucket, a content-validation gap on a privileged-only door, a compliance gap like retained PII post-erasure that isn't reachable by any caller role); or a doc-drift claim that would mislead an engineer into building an unsafe surface.
- **LOW** — debt, backlog status, or a gap with no direct exploit path today.

A finding is **CONFIRMED** only once at least one independent re-derivation (a second read of the same evidence, ideally by someone who did not write the finding) reproduces it without relying on the original claim's prose. A **healthy** item is `VERIFIED` only when its guard was itself read and shown to fail if the property broke (`guardVerified: true`) — a guard that merely exists but wasn't checked for teeth stays `NOT VERIFIED` (see A07-3's healthy item 4/5 for two guards that exist but were shown NOT to have teeth, and the mobile-signing item for a claim that a re-run outright falsified).
