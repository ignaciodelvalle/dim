# Brief — C04: Crons (vercel.json vs 25 route dirs, daily dispatcher, registry parity, GitHub schedules)

Runnable by hand by anyone with a checkout of `C:/dev/dim` at `main` — no prior context needed.

## Contract

Produce `docs/reviews/2026-09-fresh/lenses/C04.md` following the fixed section order (Ground truth, Verdict, Healthy, Findings, Refuted, Prior triage, Nits, Coverage). Every claim carries an `evidenceCmd` and its actual output — never a number quoted from memory. English, plain, precise; positives are stated as facts with their guard, not hedged. Paths are repo-relative with forward slashes, backticked, with line numbers.

## Scope and lens

`vercel.json` declares exactly two crons:
- `/api/cron/refresh-cube` at `0 3 * * *`
- `/api/cron/daily` at `0 4 * * *`

`Glob app/api/cron/*/route.ts` lists 25 directories. Establish, with commands, not assertions:

1. Which of the 25 are reached by `app/api/cron/daily/route.ts` — open the registry/handler map it imports and count entries with an array length, not a regex.
2. Which are reached by nothing (dead or manual-only).
3. Which are still individually reachable over HTTP, and how each authenticates (bearer/cron secret header, service-role, none).
4. The cron auth guard on EVERY cron `route.ts` — `rg -n` for the guard helper AND for routes that lack it (don't just count hits; verify no route is silently unguarded).
5. The dispatcher's failure semantics: does one job throwing stop the rest? Is the failure recorded (cron-health or equivalent)? Is there a timeout per job, and what does Vercel's `functions` block in `vercel.json` (maxDuration) allow?
6. Idempotency of each daily job on double invocation (Vercel retries) — pay special attention to any job that claims rows via `SELECT ... FOR UPDATE SKIP LOCKED`: verify the claim actually advances row status inside the SAME lock scope, not just that the phrase appears in a comment.
7. The 5 (verify this count — it may be stale) GitHub `schedule:` workflows: what each needs (secrets, env), and whether a failure notifies anyone.
8. `scripts/check-scheduled-fence-refs.ts` (`lint:sched-refs`): what it actually asserts about the cron set versus what its header/name implies.
9. Timezone: the crons run in UTC — check whether any job assumes Argentina local time (date boundaries, "today" windows). Argentina is UTC-3 with no DST.

## Method

1. Read `vercel.json` in full (cron entries + `functions` block, maxDuration pins).
2. `rg --files -g 'app/api/cron/*/route.ts' | wc -l` to get the ground-truth count of route dirs.
3. Open the daily dispatcher (`app/api/cron/daily/route.ts` and whatever it imports, e.g. `lib/infra/cron-dispatcher.ts`, `lib/infra/cron-registry.ts`). Count the handler map / job-order array by reading the array literal, not by grepping a keyword that might also match interface fields or function params.
4. For auth: sweep ALL 25 route files for the guard helper(s) in one loop (e.g. a shell for-loop printing "NO GUARD: <file>" for misses) rather than a headline grep count, so a zero-output result is itself evidence.
5. For the dispatcher's failure isolation: read the loop body for try/catch scope, what happens on throw vs. non-2xx return, and whether the per-job status is persisted incrementally (in case the whole function is later hard-killed) or only at the end.
6. For idempotency: for every job that claims work via a database lock, verify in the SAME code path whether the status-advancing write happens INSIDE the transaction that holds the lock, or in a later step. A `SELECT ... FOR UPDATE SKIP LOCKED` inside a transaction that only selects and commits does NOT prevent a second concurrent run from re-selecting the same rows once the lock releases — check for a companion `UPDATE ... status = 'processing'` (or similar) inside the same lock scope as the counter-example pattern to look for.
7. For GitHub workflows: `rg -n 'schedule:' .github/workflows/*.yml` to get the real count and cadence, then check each workflow's `on.schedule` job for a failure-notification step (Slack webhook, GitHub issue creation, etc.) — do not assume `audited:` comments alone are equivalent to a working notification.
8. For the scheduled-fence script: read its full body, not just the header comment, to see what it parses (`.github/workflows/*.yml` only, or also `vercel.json`?) and what it fails on.
9. For timezone: compute the UTC-to-ART offset for every scheduled hour (Argentina is fixed UTC-3), and separately check whether any "today" computation in a scheduled job's code path uses `toLocaleDateString`/`Intl.DateTimeFormat` (fenced) vs `setUTCHours`/`toISOString().slice(0,10)`/SQL `date_trunc` (typically NOT fenced by timezone lint rules — check the actual fence's scope, don't assume it covers these).
10. For every finding and every healthy claim, spawn one correctness refuter (fresh context, no access to the finder's conclusions) who re-derives the evidence independently and either confirms, refutes, or downgrades severity with its own reasoning and its own evidence. A CONFIRMED CRITICAL finding gets 5 refuters instead of 1.
11. Cross-check every "N of M" or count claim by running the counting command yourself and pasting its literal output — a keyword-count grep can overcount (e.g. matching an interface field or function parameter, not just array entries).

### Severity rubric

- **CRITICAL**: exploitable now, no auth/guard required, data loss or fleet-wide outage.
- **HIGH**: a real code path (not a dead one) can silently drop or corrupt scheduled work under realistic conditions (e.g. a backlogged night), and the fence meant to catch it passes anyway (false-green).
- **MED**: a real defect that needs an uncommon-but-plausible trigger (e.g. genuinely backlogged night, concurrent invocation), or a fence gap with a narrow but real blast radius.
- **LOW**: real but low-consequence — a stale comment with no runtime effect beyond misleading a future engineer, a self-check gap covered by an independent pager path, a checkability gap the tree cannot resolve on its own.
- **REFUTED / NONE**: the claim does not reproduce, or a fence the finder missed already closes it — cite that fence by name and line, and show the mutation that should have made it fail actually fails to pass.
