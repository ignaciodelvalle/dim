## Method

1. **Single write-path enforcement.** `rg -rn "\.insert\(notifications\)" app lib src/modules` — every hit must route through `createNotification` (or an equivalent single function) in `lib/infra/notification-service.ts`; any direct `db.insert(notifications)` elsewhere is a bypass finding.
2. **Dedupe key correctness.** Read the dedupe-key construction in `notification-service.ts` — for 2-3 notification types, construct the payload that WOULD collide (should be distinct) and one that WOULDN'T (should dedupe) and verify the key formula produces the correct result for both.
3. **Dead-letter drain.** Read the drain logic (likely a cron handler — `rg -rln "notification_dead_letter\|notificationDeadLetter" app/api/cron`) — is draining idempotent (won't re-notify on a retry), and does the `unresolvedIdx` index actually get used by the drain query's filter (read the WHERE clause, cross-check column order).
4. **ARCH-P silent-swallow.** `rg -n "catch" lib/infra/notification-service.ts` — for every catch block, confirm the failure either re-throws, dead-letters, or logs with `reportError`/`lib/observability` — never a bare swallow.
5. **Web push wiring.** Read `lib/infra/web-push.ts` and `lib/infra/push-subscription-store.ts` in full. Does a web-push send originate from the same `createNotification` call, or a separate code path with its own dedupe/failure handling that could diverge from the in-app guarantee?
6. **Mobile push/poll path.** Read `apps/mobile/src/notifications/notifications-view-model.ts` — does it poll `/api/v1/me/notifications`, or does the app register a push token somewhere (`rg -rln "expo-notifications\|pushToken" apps/mobile/src`)? If push-token registration exists, is there a server-side sender for it, or does the client-side code exist with no backend counterpart (a half-built feature masquerading as complete)?
7. **Quiet hours.** Confirm existence with the grep above; if found, read the implementation for what it actually suppresses (send-time delay vs. drop) and whether it applies uniformly across in-app/web-push/mobile-push.
8. **`scripts/check-notifications-service.ts`.** Read in full — what property does it actually assert, and is it wired (`rg -n "check-notifications-service" package.json` — confirmed as `lint:notifications`).
9. **Exploit or mutation per finding.** For a bypass finding, state the concrete write site and what breaks (a duplicate notification, a lost failure). For the delivery-channel gap, state which user-facing reminder never reaches its recipient today.
10. **At least 3 healthy items**, each with the guard traced and verified.
11. **Triage every prior.**

**Severity rubric**:
- CRITICAL: not typical for this lens by default — reserve for a bypass that both loses a crisis-relevant notification (lost pet, custody dispute) AND has no dead-letter trace.
- HIGH: a direct `db.insert(notifications)` bypass of the dedupe/dead-letter path on a reachable code path, a silent-swallow that loses a failed send with no trace.
- MED: a dedupe-key gap with a bounded effect (harmless duplicate), a half-built push-registration path with no server sender, quiet hours not applied to one of three channels.
- LOW: hygiene, a documented (not silent) delivery-channel limitation.
