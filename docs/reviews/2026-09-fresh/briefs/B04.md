## Method

1. **N+1 sweep.** `rg -n '\.map\(|\bfor\s*\(' lib src/modules -g '*.ts' -g '!*test*'` then manually check each for a `db.` call inside the loop body versus a batched query outside it.
2. **Fetch-then-filter.** For any read that fetches broadly then filters in JS on a tenant/jurisdiction/PII field, check whether the same predicate could be a SQL `WHERE` — the specific class CLAUDE.md calls "the jurisdiction-drift class."
3. **Transaction boundaries.** `rg -n '\.transaction\(' db lib src/modules` — for every multi-write use-case (2+ writes that must be atomic), confirm both writes are inside the same `db.transaction` callback, not sequential top-level calls.
4. **Table count and index audit.** Run the recount command above. Then for the hot-path tables named in the LENS (jurisdiction-scoped govt reads, case/event lists, panorama aggregates, notification queries), read the actual query's WHERE+ORDER BY shape (`rg -n` the query builder call) and cross-reference against `CREATE INDEX` statements in `db/migrations/*.sql` for that table — column order in a composite index must match the query's filter-then-sort order, not just cover the same columns.
5. **Cascade semantics.** `rg -n "onDelete:|references\(" db/schema.ts` for every FK touching an append-only table (`pet_events`, `case_events`) — a `cascade` here would violate the append-only invariant; confirm the actual behavior declared.
6. **`withDbBudget`/`loadWithTimeout` coverage.** Find both helpers, then spot-check 5 DB-heavy call sites (panorama aggregates, dashboard reads) for whether they're wrapped by either — a query with neither is unbounded.
7. **Repository-layer relocation.** `rg -l "from ['\"]@/db" src/modules/*/infrastructure` to confirm the hexagonal-lite repository layer is where B04's queries actually live now; treat any `lib/**` query doing the same job as a possible duplicate/drift pair, not just a leftover.
8. **Exploit or mutation per finding.** For an N+1 or missing-index finding, give the row-count scaling that makes it a real production problem (e.g. "O(n) queries per panorama render at n=200 jurisdictions").
9. **At least 3 healthy items**, each with the guard traced and verified (a fence, a test, or a structural guarantee).
10. **Triage every prior.**

**Severity rubric**:
- CRITICAL: raw SQL with interpolated user input (injection), or a cascade that silently deletes append-only event history.
- HIGH: an unbounded N+1/full-scan on a jurisdiction-scoped PII query with no `withDbBudget`/index, reachable by a normal authenticated request.
- MED: a missing composite index or fetch-then-filter pattern with a plausible but not yet demonstrated scaling problem, an over-fetch with no PII exposure.
- LOW: unused index, minor schema hygiene (missing NOT NULL with no observed bad row), hygiene.
