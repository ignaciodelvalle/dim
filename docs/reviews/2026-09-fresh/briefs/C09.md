## Method

1. **Reproduce the count** with the command above; if it differs, use your own number and note the drift.
2. **Read `e2e/README.md` in full.** It documents prerequisites (local Supabase, `pnpm db:bootstrap`), the build-then-start execution model (`next build && next start`, NOT the dev server — `playwright.config.ts`), and per-spec conventions for several files (verified: it describes `crisis-public.spec.ts`, `crisis-owner-lost-flow.spec.ts`, `chapas.spec.ts`, `api-v1-public-contract.spec.ts`, `api-v1-auth-refusals.spec.ts` in detail as of the point read). Extract its own stated rules as your checklist rather than inventing new ones.
3. **Runtime-discovered fixtures.** For each spec, `rg -n "publicToken|DIM-[A-Z0-9]{4}-[A-Z0-9]{4}|hardcoded" e2e/<file>.spec.ts` — flag any spec that hardcodes a token/id/UUID literal instead of discovering it at runtime from a listing page (the pattern `e2e/README.md` documents for `crisis-public.spec.ts` and `api-v1-public-contract.spec.ts`).
4. **Cleanup discipline.** For every spec that mutates state (creates a pet, toggles lost-mode, issues a chapa, books a turno), confirm a `finally`/`afterEach` block reverts it — `rg -n "finally|afterEach" e2e/<file>.spec.ts`. `e2e/README.md` documents `crisis-owner-lost-flow.spec.ts` reverting Michi to "found" and `chapas.spec.ts` calling `deleteTagsByLotePrefix` as the two known-good examples — use those as the bar, and flag any state-mutating spec that has NEITHER pattern.
5. **API-only vs browser seams.** `rg -ln "request\.(get|post|put|delete)" e2e/*.spec.ts` for specs using Playwright's `request` fixture (no browser) vs `rg -ln "page\.(goto|click|fill)"` for real-browser specs — classify each of the 45 and confirm the classification matches what the spec is actually testing (an API-only spec claiming to test a UI flow would be a mislabeled-coverage finding).
6. **Nightly job.** Read `.github/workflows/e2e-nightly.yml` in full — which specs does it run (all 45, or a subset), against which target (staging, per CLAUDE.md's "e2e is a separate gate... CI's own job (and nightly vs staging)"), and does a failure notify anyone or only sit in the Actions tab.
7. **Cross-tenant/authz specs.** `authz-ab-isolation.spec.ts`, `cross-tenant-isolation.spec.ts` — read both in full; confirm they exercise the actual boundary (two distinct tenant accounts, a real cross-tenant request) rather than a single-tenant happy path with an authz-sounding name.
8. **Crisis-path adequacy.** Cross-reference against C08's "e2e coverage of the crisis paths" question (avoid duplicate findings — C08's angle is "is coverage adequate at all," this lens's is "does the existing coverage follow the repo's own e2e conventions"). Read `crisis-public.spec.ts`, `crisis-owner-lost-flow.spec.ts`, `crisis-seams.spec.ts` in full.
9. **Exploit or mutation per finding.** For a cleanup-gap finding, state what a failed/aborted run leaves behind in the local DB and what a subsequent run would then see. For a hardcoded-fixture finding, state exactly when it breaks (a fresh seed, a different environment).
10. **At least 3 healthy items**, each with the guard traced and verified against `e2e/README.md`'s own stated convention.

## Output

Produce a JSON object (or equivalent structured notes) with these top-level keys:

- **findings**: array of `{id: "C09-n", title, severity: CRITICAL|HIGH|MED|LOW, kind: test-theater|debt|convention, canonRule?, path, line, evidenceCmd, evidenceOutput(≤400ch), exploitOrMutation, fix(one line), fixClass: doc-fix|code-sdd|fence-candidate|po-decision, priorId?, priorStatus?}`
- **healthy**: array of `{title, property, path, line, evidenceCmd, evidenceOutput, whatWouldBreakIt, guardedBy, guardVerified: bool}` — minimum 3
- **priorTriage**: `[]` (no priors this run)
- **nits**: array of `{path, line, note}`
- **coverage**: `{filesRead: [...], areasNotReached: [...]}`

**Severity rubric**:
- CRITICAL: not typical for this lens — reserve for an e2e cleanup gap that leaves exploitable state (e.g. a real activation code) in a shared environment.
- HIGH: a spec claiming to cover a crisis/authz path that in fact tests something narrower (mislabeled coverage that would give false confidence at the exact moment it matters), a cleanup gap that corrupts local DB state for subsequent runs.
- MED: a hardcoded fixture that will silently start failing on a re-seed, a nightly job that runs a stale/incomplete subset of specs with no one noticing.
- LOW: hygiene, a convention deviation with no demonstrated downstream effect.

This brief is meant to be runnable by hand by someone who has not seen this workflow — if a step above is ambiguous without prior context, treat that as a bug in the brief and resolve it the most literal way rather than guessing at intent.
