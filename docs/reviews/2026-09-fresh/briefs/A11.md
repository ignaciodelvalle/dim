# A11 brief — API v1 surface (mobile contract)

## Contract

Read-only. Do not edit, run `pnpm` scripts, run tests, run builds, or touch git state. Every claim you report must carry a command that anyone can rerun by hand and the exact output it produced.

Before starting, check out or confirm you are reading `main` at SHA `d7dbf25f7` (`git rev-parse HEAD`). If the SHA differs, note the actual SHA you audited against in your output — do not silently audit a different tree and call it this one.

Exclusions: do not read or report on anything under `node_modules/`, `.next/`, `.claude/`, or generated/build output. Do not invent line numbers — every `path:line` must come from a command you actually ran against the checked-out tree.

## Scope and lens

> Everything the mobile app calls: the full route inventory under `app/api/v1/**` (Glob it; list every `route.ts` with its methods), the bearer auth helper (who validates the JWT, is the user checked as live/not-erased/not-deactivated, is the token audience checked), the response envelope and error shape across routes, the rate-limit family assigned to each route, the anti-oracle rules of `docs/architecture/api-invariants.md` (existence oracles via 404 vs 403, timing, enumeration), input validation (zod schemas in `packages/contract/src/api` or inline), idempotency keys on mutating routes, versioning and unknown-field handling, CORS and cache headers, and parity between what `packages/contract/src/api` declares and what the routes actually return and what `apps/mobile/src/api` consumes.

What's new: this lens is new in 2026-09. The whole `/api/v1` surface was built for the Android pilot (2026-08); `apps/mobile/src/api` client; `packages/contract/src/api` types; rate-limit families; `Idempotency-Key` handling; mobile claims, transfers, custody, denuncias, shares, turnos endpoints. There is no old brief for this lens and no prior audit — treat every finding as new.

## Method

1. **Enumerate the surface.**
   ```
   rg --files -g "route.ts" app/api/v1 | sort
   ```
   For each file, note its exported HTTP methods:
   ```
   rg -n "^export (async )?function (GET|POST|PATCH|PUT|DELETE)" app/api/v1 -g "route.ts"
   ```
   Expect 33 route files at this SHA. If your count differs, say so explicitly — a route added or removed changes several of the counts below.

2. **Bearer auth / no cookie fallback.** For every authenticated route, confirm identity is resolved from the `Authorization` header only:
   ```
   rg -n "@/lib/supabase/server|cookies\(\)|createServerClient|createRouteHandlerClient|request\.cookies|req\.cookies" app/api/v1 --glob '!*.test.*'
   ```
   Expect zero hits. Then find every route that has NO `requireLiveUser` call and confirm each carries a written `@no-auth-required` justification:
   ```
   rg -L "requireLiveUser" app/api/v1 -g "route.ts" --files-without-match
   rg -n "no-auth-required" app/api/v1
   ```
   Then confirm every real `requireLiveUser` call passes an explicit `accessToken` (not just `{ supabase }`):
   ```
   rg -n "requireLiveUser\(" app/api/v1 -A2
   ```

3. **Response envelope.** Find the fence's discovery floor and compare it to the real file count:
   ```
   rg -n "MIN_V1_ROUTE_FILES" scripts/check-api-v1-envelope.ts
   rg --files app/api/v1 | rg -c "route.ts$"
   ```
   These two numbers must match, or the fence cannot be trusted. Then sweep for hand-built responses that bypass `apiV1Json`/`apiV1Error`, both inside and outside route files:
   ```
   rg -n "NextResponse|new Response\(|Response\.json" app/api/v1 -g "route.ts"
   rg -n "NextResponse|new Response|Response\.json" app/api/v1 --glob '!**/route.ts' --glob '!*.test.*'
   ```

4. **Rate-limit families.** Count declared per-IP buckets and compare to the test's floor and aggregate pin:
   ```
   rg -c "^  api_v1_[a-z0-9_]+: \"" lib/infra/api-v1-limits.ts
   rg -n "MIN_IP_BUCKETS = |toBe\(1[0-9]_[0-9]{3}\)" __tests__/api-v1-rate-limit-families.test.ts
   ```
   Re-derive the aggregate by hand from the family map — do not trust the reduce or the comment; sum `count × maxPerMinute` per family from source and compare to the `toBe` pin. Then check, for EVERY route spending an `authenticated-read`-family or `authenticated-write`-family IP bucket, whether it also spends the matching per-user bucket right after its `requireLiveUser` call:
   ```
   rg -n "spendBudget\(" app/api/v1 -g "route.ts" -A2
   rg -n "API_V1_AUTHENTICATED_READ_USER_LIMIT|API_V1_AUTHENTICATED_WRITE_USER_LIMIT" app/api/v1 -g "route.ts" -l
   ```
   Compare the file lists for IP-limit imports vs USER-limit imports — any route importing the IP constant for a two-budget family but not the USER constant is a candidate finding (verify by reading the handler, since a route may legitimately delegate its per-user spend into a use-case function — check the route's own docblock/comments before flagging).

5. **Anti-oracle rules (existence oracles).** Read `docs/architecture/api-invariants.md` for the stated rules (404 vs 403, timing, enumeration, retry-after). For each route with an access-resolution branch, confirm the not-permitted and not-existing cases converge on the identical status+body:
   ```
   rg -n "access.kind === \"none\"|access.kind !== \"owner\"" app/api/v1 -g "route.ts"
   ```
   For every `403` code found on the surface, trace whether it is reachable before or after access resolution succeeds — a 403 reachable BEFORE resolution (i.e., on a token the caller doesn't hold) is an existence oracle:
   ```
   rg -n "apiV1Error\(\"[a-z_]+_forbidden\"" app/api/v1 -g "route.ts" -B15
   ```
   For every `429`, confirm no `retry-after` or distinguishing header leaks which of two budgets was exhausted:
   ```
   rg -n "rate_limited" app/api/v1 -g "route.ts"
   ```
   For every route/branch handling `DbBudgetExceededError` or a "degraded" case, confirm it answers 503, never 404.

6. **Test-coverage parity.** For every route file found in step 1, confirm at least one test or e2e spec imports its handler directly:
   ```
   rg -o "@/app/api/v1/[a-zA-Z0-9/_\[\]-]*route" __tests__ e2e --no-filename | sort -u
   ```
   Diff this list against the route file list from step 1 (normalize both to the same `@/app/api/v1/...` shape). Any route file present in step 1 but absent here is a coverage gap — read that handler and note what load-bearing logic (anti-oracle branches, liveness refusals, limiter ordering) it alone carries untested.

7. **Idempotency keys.** For every mutating route accepting an `Idempotency-Key` header, confirm (a) the header is validated against a strict format before being used, and (b) the duplicate-lookup query is scoped by owner/user, not by the key alone:
   ```
   rg -n "Idempotency-Key|idempotencyKey|IDEMPOTENCY_KEY_PATTERN" app/api/v1 packages/contract/src/api -g "*.ts"
   rg -n "findDuplicateRegistration|clientIdempotencyKey" src/modules -g "*.ts" -A3
   ```
   Confirm the repository-level lookup query ANDs the key with an owner/user column, and check for an advisory lock scoped to the pair (not the key alone) if one exists.

8. **Mobile client parity.** Count `apiRequest<...>` call sites in `apps/mobile/src/api/endpoints.ts` and how many pass `expectedPayloadVersion`:
   ```
   rg -c "apiRequest<" apps/mobile/src/api/endpoints.ts
   rg -c "expectedPayloadVersion" apps/mobile/src/api/endpoints.ts
   ```
   Do NOT assume these numbers split cleanly by HTTP method — verify by hand-listing every `apiRequest<` call site's line number and checking, per site, whether an `expectedPayloadVersion` appears within the next few lines. A GET-vs-POST count (e.g. via `rg -c 'method: "POST"'`) can overcount if `performRequest` (used by unauthenticated auth flows) is not excluded — check which function each match belongs to before drawing a conclusion.
   Then compare the error-code vocabulary:
   ```
   sed -n '/API_V1_ERROR_CODES = \[/,/\] as const/p' packages/contract/src/api/errors.ts | rg -c '^\s*"[a-z_]+",'
   rg -c '^\s*case "[a-z_]+":' apps/mobile/src/api/error-copy.ts
   rg -n "default:" apps/mobile/src/api/error-copy.ts
   ```
   These two counts should match with no `default:` branch (a `default:` would hide an unmapped code instead of failing to compile).
   For the 429 retry-after affordance specifically, confirm any client-side countdown copy is actually reachable given what the server sends:
   ```
   rg -n "rate_limited\", 429," app/api/v1 -g "route.ts"
   rg -n -i "retry-after" docs/architecture/api-invariants.md lib/infra/api-v1.ts
   ```

9. **Doc drift.** Any prose paragraph that transcribes a computed number (a sum, a count, a limit) instead of pointing to the constant is a candidate LOW finding — check it against the actual computed value at this SHA.

10. **Severity rubric** (apply consistently):
    - **CRITICAL** — a live disclosure or bypass reachable today with no mitigating factor (PII leak, auth bypass, cross-tenant write).
    - **HIGH** — a live security-relevant gap with a real but narrower blast radius (e.g. an existence oracle on sensitive tokens, an unbounded read of non-public data).
    - **MED** — a real gap that is not itself a live exposure today (missing throttle on non-PII data, a demonstrated but not-yet-triggered undetectable-regression path, an untested handler carrying load-bearing guard logic).
    - **LOW** — doc drift, a fence gap that is partially compensated elsewhere, dead/unreachable code with a misleading comment.
    - Style-only or one-line issues with no behavioral claim go in **Nits**, not Findings.

11. **Healthy claims.** Produce at least 3 (this lens produced 6) "healthy — verified" write-ups, each naming: the property in one sentence, a `path:line` anchor, the guard that enforces it (a fence script or test file), and — critically — what you actually tried to break it with (the specific evasion you swept for) and the command+output proving the evasion doesn't work. A healthy claim without a "what would break it" sweep is not verified, it's an assertion.

12. **Prior triage.** None to do for this lens (see Priors above) — leave the table empty with a note.

## Gap round

The base pass above read `apps/mobile/src/api` only — the shared client, not any of the five feature flows built on top of it. This gap round covers what the base pass never opened.

**Scope:** `apps/mobile/src/claims`, `custody`, `denuncias`, `shares` and `transfers` — five directories, 7,605 lines (`find apps/mobile/src/{claims,custody,denuncias,shares,transfers} -name '*.ts*' | xargs wc -l`), the client side of exactly the mutating routes the base pass left unopened: `/me/pet-claims`, `/pets/{token}/move` and `/return`, `/welfare-reports`, `/pets/{token}/shares`, `/me/transfers`. Together they drive the whole 14-tester Android pilot.

**Method:**

1. **Enumerate the five flows.** For each directory, list its view model and screen files:
   ```
   rg --files apps/mobile/src/{claims,custody,denuncias,shares,transfers} --glob '!*.test.*'
   ```

2. **Disciplined-negative sweep first** (cheap, narrows the rest of the budget):
   ```
   rg -n "AsyncStorage|SecureStore|MMKV|console\.(log|warn|error|info)|captureException|addBreadcrumb|Clipboard|Share\.share" apps/mobile/src/{claims,custody,denuncias,shares,transfers} --glob '!*.test.*'
   rg -n -i "dni" apps/mobile/src
   ```
   Read every hit — a disciplined comment or a single deliberate `Share.share` call is expected; a real `console.log`/`Clipboard`/persistence hit is a finding.

3. **Request-body parity, per flow.** For each of the five, find the view model's command-building function(s), then diff the object it posts against (a) the zod schema the matching route parses and (b) the wire type in `packages/contract/src/api`:
   ```
   rg -n "InputSchema.safeParse|CommandInputSchema" app/api/v1/{welfare-reports,pets/[publicToken]/{move,return,shares},me/{pet-claims,transfers}} -g '*.ts'
   rg -n "safeParse|build[A-Z][a-zA-Z]*\(" apps/mobile/src/{claims,custody,denuncias,shares,transfers} -g '!*.test.*'
   ```
   For each screen, confirm it calls its view model's builder and branches on `.ok`/`.data` rather than hand-constructing the request object (`TransferInitiateScreen.tsx:85-92` is the correct shape to compare against). A screen that types its dispatch to the contract type but skips the runtime `safeParse` is a candidate finding — check whether the bypass is exploitable (a structural field is still caught by TypeScript; a runtime-only refinement like a trim/max-length is not).
   A cross-tenant finding shape to watch for specifically: a field the client sends that the route silently drops, or an id (`petId`, `transferId`, `orgId`, `shareToken`) the client puts in the body where the server should derive the actor/tenant from the bearer token instead.

4. **Libreta share token exit path.** Read `apps/mobile/src/shares/SharesScreen.tsx` in full, particularly around the share-URL construction and the `Share.share` call:
   ```
   rg -n "libretaShare|shareToken|Share\.share|Linking\." apps/mobile/src/shares --glob '!*.test.*'
   ```
   Establish: the token's TTL (`shares-view-model.ts` expiry options), whether revoke is scoped by row id or by the token itself (check `revoke_libreta_share`'s command shape and the pet-narrowing query it goes through server-side — `src/modules/pets/application/libreta-share/find-share-for-pet.ts`), and what the `Share.share` promise's rejection handler does with the URL (does it get logged, captured, or dropped silently).

5. **Client error-path PII trace, given A06-2.** A06-2 (prior finding) established mobile Sentry has no `beforeSend`/`beforeBreadcrumb`. For each of the five flows, find every `setNotice`/`setError`/failure-render call site and classify it: does it render a fixed sentence keyed on an error code (safe), or does it interpolate server-supplied text (check whether that text can name a third party — another user's name, initials, pet, or address)?
   ```
   rg -n "setNotice\(|setError\(|failureMessage\(" apps/mobile/src/{claims,custody,denuncias,shares,transfers} -g '!*.test.*' -B2
   ```
   Read the function each interpolated value comes from server-side (e.g. an `ack.reason`/`ack.ownerInitials`-shaped field) and confirm what data it can carry by reading its constructor, not just its type.

6. **Severity rubric:** same as the base pass (CRITICAL/HIGH/MED/LOW as defined above). A body field the client controls that lets it assert a fact the server should derive independently (jurisdiction, ownership, identity) is MED unless a compensating check exists elsewhere reachable at equal or lower cost — check for that compensating path before voting MED, since it changes the severity materially (see A11-G1's split refuter vote for a worked example).

7. **Healthy claims, gap round.** Same bar as the base pass — a property, a `path:line`, a named guard, and a concrete "what would break it" sweep with command+output. Aim for at least 3.
