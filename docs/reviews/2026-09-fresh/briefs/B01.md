## Scope and lens

NEW lens (no prior run). `docs/architecture/hexagonal-lite.md` defines four layers per module — `domain/` (pure, no `@/db`/`drizzle-orm`/`next`), `application/` (use-cases, orchestration), `infrastructure/` (the only place issuing Drizzle queries), `actions.ts` (thin `"use server"` controllers: parse input, auth guard, invoke use-case, redirect) — with the inward dependency rule enforced by Biome's `noRestrictedImports` on `src/modules/*/domain/**`. Audit every module under `src/modules/*` against this shape: which layers exist, which are missing, and whether a module missing `actions.ts`/`infrastructure/` is calling `@/db` directly from `app/` instead (the drift the doc's dependency-rule table is meant to prevent). The `auth` module is the priority read — it is security-critical and (per the count below) one of the thinnest.

## Method

1. **Recount the module list and shapes** with the command above; do not trust this brief's table without re-running it.
2. **Read `docs/architecture/hexagonal-lite.md` in full** for the dependency-rule table (which layer may import what) and the Biome enforcement claim (`rg -n "noRestrictedImports" biome.json` — confirm the glob actually targets `src/modules/*/domain/**`, not a narrower or stale pattern).
3. **For each outlier module**, read every file in it and classify: (a) the missing layer's responsibility is genuinely absorbed by a thinner shape appropriate to the module's size (state why), or (b) the missing layer means a heavier one (`actions.ts`, or a route/page in `app/`) is doing the missing layer's job — e.g. issuing `@/db` queries directly where `infrastructure/` would normally sit. `rg -n "from ['\"]@/db|from ['\"]drizzle-orm" src/modules/<m>/**/*.ts` per module to check.
4. **`auth` first.** Read every file under `src/modules/auth/`. Cross-reference against `lib/supabase`/`lib/infra` for wherever auth-adjacent logic actually lives outside the module — if `src/modules/auth` is a thin shim over logic that lives elsewhere, name the real location and assess whether that split is intentional (documented) or drift.
5. **Domain purity spot-check.** For 3 modules with a `domain/` layer, `rg -n "from ['\"]@/db|from ['\"]drizzle-orm|from ['\"]next" src/modules/<m>/domain/**/*.ts` — should be empty. Any hit is a fence-gap finding (Biome's rule not catching it) or a bypass (a lint-disable comment) — check which.
6. **Fat-`actions.ts` regression check.** The doc's own "why" table cites a 2,919-line `app/actions/events.ts` shrunk to a 142-line shim as the motivating case. `wc -l` every module's `actions.ts` and flag any that has regrown past a few hundred lines with business logic inlined (a `rg -c` for `db\.` calls inside `actions.ts` itself, which should be zero per the layer table).
7. **Exploit or mutation per finding.** For a layering violation, state the concrete consequence (an untestable rule, a DB call unreachable by a pure unit test, a bypass of the auth-boundary edge) — not just "this breaks the pattern."
8. **At least 3 healthy items.** For a module that fully matches the shape, name the guard (Biome rule, or absence of a matching anti-pattern) and what would break it.

**Severity rubric**:
- CRITICAL: a `domain/` file imports `@/db`/`drizzle-orm` at runtime with no Biome guard catching it AND the query is security-relevant (auth, ownership).
- HIGH: `auth` or another security-critical module bypasses the layering in a way that puts the auth boundary check outside `actions.ts`'s guard step (e.g. a use-case that trusts a caller-supplied role).
- MED: a non-security module's missing layer causes a real testability/maintainability gap (business rule untestable without a DB) with no live bug demonstrated.
- LOW: cosmetic shape drift (e.g. a `__tests__/` folder missing but the module has equivalent tests elsewhere) or debt with no near-term risk.
