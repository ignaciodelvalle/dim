# D05 brief — Pitch-claims verification

## Contract

Read every factual claim in two documents — the government-personas pitch deck and the project README — and classify each one TRUE, PARTIAL, or FALSE against the code at a pinned commit, with evidence a non-engineer reviewer could hand to a fact-checker. Output two files: a lens (`docs/reviews/2026-09-fresh/lenses/D05.md`) carrying every claim's evidence and verdict, and this brief.

## Scope

Two documents:
- `docs/design/handoffs/2026-07-07-govt-personas-pitch.md` — the deck used to demo miMAR to government officials (personas, journeys, capability ledgers, roadmap).
- `README.md` — the repo's front door: stack, portals, architecture, contributor setup.

**Claim definition**: any sentence, table row, or bullet that asserts something checkable about the system — a route exists, a guard enforces a scope, a number is correct, a capability is live, a gap is real. Persona wishlists ("what an official wants") and pure opinion are not claims and are excluded (noted under Coverage → areas not reached where relevant).

## Classification rules (verbatim from the data)

- **TRUE** — the claim reproduces in code exactly as stated, with no material qualifier needed.
- **PARTIAL** — the claim is substantially right but overstates, understates, or omits something a reader would need to act on it safely (a redirect the deck doesn't mention, a casing error, a scope narrower than implied, an omission that under- or over-sells).
- **FALSE** — the claim's central assertion does not hold: the thing described does not exist, doesn't work the way stated, or is stale to the point of being actively misleading (e.g. calling a shipped feature a future gap).

Refuter policy: 1 correctness refuter on every claim the finder called TRUE, escalated to a 3-lens panel (correctness, user-path, official-reading) if that refuter contests the class; the 3-lens panel runs directly on every claim the finder called PARTIAL or FALSE. Final class = majority of refuter votes; a tie keeps the finder's original class and is marked CONTESTED.

## Method

1. Finder pass: read both documents end to end, extract every claim, classify each independently, cite an `evidenceCmd` (and its output) grounding the verdict in a specific file/line.
2. Refuter pass: one or three fresh-context lenses per claim (per the policy above) re-run the finder's exact evidence command, verify it reproduces byte-for-byte, then independently walk the code from the angle of their lens:
   - **correctness** — does the cited mechanism actually work as described, including edge cases the finder didn't check?
   - **user-path** — can the actor named in the claim (owner, vet, govt official, anonymous visitor) actually reach and use what's claimed, end to end, through real UI/routes?
   - **official-reading** — read literally by a non-technical government reader, does the sentence need a qualifier (flag/stub/pilot/role-limit) it doesn't carry?
3. Each vote reports `classificationVote`, `confidence`, a reason, its own evidence, and a `safeWording` — the sentence a deck or README could safely print instead.
4. Majority of votes decides `finalClass`; the lens document reports both the finder's original class and the final class, flags `changed: true` when refutation moved it, and `contested: true` on any tie.
5. Compile into the lens format: TRUE claims as a table; PARTIAL/FALSE claims with full per-claim detail (source, quote, why, evidence, one line per vote, safe wording); a `for limites-honestos.md` section translating every non-TRUE claim into one plain English sentence of what cannot be affirmed today; a Coverage section listing every file read and areas the audit did not reach.
